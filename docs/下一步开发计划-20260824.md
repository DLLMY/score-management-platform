## 2. 代码层面主要问题或风险

### 2.1 🔴 前端测试覆盖缺口（最高风险，与 2026-08-21 基线一致）

- **位置**：`frontend/src/**/*.test.*`（16 个，多为组件级）+ `tests/e2e/*.spec.ts`（9 个） vs **196 个源文件 / 125 个页面 / 79,307 行**。
- **影响**：`stores/*`、`PermissionGuard` 死锁/超时分支、`ScoreEntry`/`ScoreChart`/`RankBoard` 数值展示、`api.ts` 信封归一化均无自动化回归保护，易在后续重构中静默回退。
- **量化**：本轮 B3 战役已补强 `useClientFilter`/`useListFetch`/`format` 等 24 个用例，但 store/守卫/评分展示仍是盲区。

### 2.2 🟠 综合分重算静默失败（数据正确性）

- **位置**：`backend/api/scores/records_routes.py:302/908/1046`（单条/批量/删除创建路径）。
- **问题**：`CompositeScoreService.recalculate_user_score(user_id)` 被 `except Exception: pass` 静默吞掉 → 积分记录已落库但综合分未重算 → **综合分与明细长期静默漂移**，用户无感知；同文件 `:752-759` 却 `logger.warning`，处理不一致。
- **同源**：`records_routes.py:318/897` 审计/缓存失效也是 `except:pass`（最佳努力，风险低，至少应 `logger.warning`）。

### 2.3 🟠 前端类型闸门薄弱

- **位置**：`frontend/tsconfig.json:12` `"strict": false`（`noUnusedLocals/Parameters` 亦 false）；全仓 `any` **60 处**（其中 `services/api.ts` 44 处）。
- **影响**：`strict:false` 使 `any` 滥用无编译期拦截，是 `api.ts` 响应类型混乱、运行时错误的根因；`any` 经 `api.ts` 向全站扩散。
- **修复取向**：不一次性全量 `strict:true`（爆炸式报错），而是**先收敛 `any` 到 0 再逐步开启 `strict`**（见任务 T5）。

### 2.4 🟠 列表端点未分页（规模化性能）

- **位置**：后端 `api/**/*_routes.py` 中多个列表端点用 `.all()` 全表读（含 `students`/`scores`/`devices` 等规模化表）；`M9` 分页 helper 已建 38 处使用，但仍有未覆盖点。
- **数据**：本轮 Grep `.all()` 命中 100+ 文件（含 services/tests/scripts 合法用法），风险集中在**路由列表端点**；规模化表无分页会在数据增长后引发内存尖峰 + 延迟。
- **修复取向**：对规模化表强制 `paginate()`，复用 `M9` helper。

### 2.5 🟠 ML 重依赖硬编码膨胀

- **位置**：`backend/requirements.txt` 将 `torch`/`transformers`/`xgboost`/`catboost`/`gensim` 全硬编码为硬依赖；Grep 确认 `xgboost`/`catboost`/`gensim` 全仓无 import（仅 `torch`/`transformers` 用于 NLP）。
- **影响**：镜像体积数十 GB、冷启动慢、CI 安装久；Web 服务与算力依赖强耦合。
- **修复取向**：拆 `optional` extras（如 `[ml]`）或运行时 lazy import，主镜像不含 ML 重依赖。

### 2.6 🟡 维护性余债（中/低，可排期）

| 位置 | 问题 | 严重 |
| --- | --- | --- |
| `frontend/src/pages/{OpsCenter,SystemMetrics,SecurityAudit,FrontendTelemetry}.tsx` | fetch 失败静默 `return null`，无错误态 UI | 🟠（4 页） |
| `backend/api/scores/records_routes.py`(1050 行) / `algorithm_routes.py`(1242 行) | 路由文件过大，读路径与大段编排仍留路由（薄路由约定部分违反） | 🟠 |
| `backend/requirements.txt:50-51` + `excel_utils.py` | `xlrd`/`xlwt` 占位 import 无真实使用 | 🟡 |
| `frontend/package.json:15` | `web-vitals` 声明零引用（死依赖） | 🟡 |
| `config.py`/`config_init.py`/`utils/security.py` 等 5 处 | 密钥/配置源分散（生产环境有长度校验，非安全高危） | 🟡 |
| `backend` 多处 `except Exception: pass`（基础设施/缓存/审计辅助） | 异常被静默，排障困难 | 🟡 |
| `package.json` eslintConfig | 仍引用 `react-app`/`react-app/jest`（CRA 残留，项目已迁 Vite） | 🟡 |

## 3. 按优先级排序的开发任务

> 任务编号 T1–T12。P0=本迭代立即；P1=本迭代内；P2=下迭代；P3=持续改进。
> 每条均含「预期目标 / 验收标准」。保持零回归铁律：前端 `tsc --noEmit`+`eslint`+`vitest`；后端定向 pytest + `scripts/run_regression.sh` 全绿。

### P0 · 立即（本迭代，数据与测试正确性）

#### T1 综合分重算不再静默失败
- **目标**：消除 `records_routes.py:302/908/1046` 三处 `except:pass` 对 `recalculate_user_score` 的吞异常。
- **验收**：① 改为 `except Exception as e: logger.error(...)` 并返回状态标记（如响应附 `composite_score: "recalculate_failed"`）；② 或移入 Celery 异步任务 + 对账；③ 与 `:752-759` `logger.warning` 风格统一；④ 补 pytest 断言重算异常时不污染主数据落库；⑤ 跑通 `test_scores_routes` + `run_regression.sh`。

#### T2 前端关键路径测试补强（store / 守卫 / 评分展示）
- **目标**：把单测从 16 扩到 ≥40，覆盖 top-20 高频页面业务逻辑。
- **验收**：① 新增 `stores/*` 行为测试（权限缓存 5 分钟 + `defaultPermissionsForRoles` 兜底）；② `PermissionGuard` 超时/恢复分支测试；③ `ScoreEntry`/`ScoreChart`/`RankBoard` 数值展示测试；④ `api.ts` 信封归一化单测（含 `getErrorMessage` error_code 友好文案）；⑤ `vitest run --pool=forks` 全绿，CI 前端 job 通过。

### P1 · 本迭代内（规模化 + 类型 + 安全加固）

#### T3 列表端点强制分页
- **目标**：对 `students`/`scores`/`devices` 等规模化表列表端点用 `paginate()`（复用 `M9` helper）。
- **验收**：① 规模化表列表端点全部带分页参数（page/page_size）；② 既有缓存端点（`@cached_api`）分页键正确；③ 前端对应列表页支持分页 UI（或用 `useListFetch`）；④ 定向 pytest + `run_regression.sh` 全绿。

#### T4 综合分重算异步化（T1 的进阶）
- **目标**：批量录分（`records_routes:301,907`）同步重算改为 Celery 异步入队，写路径立即返回。
- **验收**：① 写路径仅入队 + 返回；② 异步任务执行重算并对账；③ 批量导入延迟随用户数不再线性增长；④ 不动既有契约。

#### T5 前端类型闸门收敛（any → 0，再逐步 strict）
- **目标**：先收敛全仓 60 处 `any`（重点 `api.ts` 44 处）到 0，再开启 `strict`。
- **验收**：① `api.ts` 响应类型用泛型/`unknown`+运行时校验替代 `any`；② 全仓 `any` grep 计数 = 0；③ `tsc --noEmit` 0 错误（保持 `strict:false` 不引入爆炸改动）；④ 后续迭代再开启 `strict`。

#### T6 security_routes 默认密钥 fail-closed
- **目标**：`API_SECRET_KEY`/`SECRET_KEY` 缺失时 `raise RuntimeError`（与 JWT 处理一致）。
- **验收**：① 缺失即启动失败；② 现有测试 `test_security_routes` 全绿；③ `run_regression.sh` 全绿。
