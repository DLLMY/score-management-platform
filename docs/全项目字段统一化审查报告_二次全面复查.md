## 1. P0 —— 关键不一致（建议优先处理）

### P0-1 学生标识字段分裂：`student_id` ↔ `user_id`
- **涉及**：全仓（Score / ScoreRecord / MentalHealthAlert / RiskWarning / ActivityRegistration / StudyGroupMember / HomeworkSubmission / Notification / 学生聚类等）
- **当前差异**：
  - 用 `student_id`（FK→`user.id`）：`Score`(`models/__init__.py:639`)、`ParentContact.parent.py:9`、`MentalHealthRecord`/`MentalHealthAlert`、`ActivityRegistration`、`StudyGroupMember`、`ImprovementPlan`、`HomeworkSubmission`。
  - 用 `user_id`（同指 `user.id` 但**无统一 FK**）：`ScoreRecord:186`、`StudentCluster:1216`、`CompositeScore:1230`、`RiskWarning:1247`、`Notification`/`Approval`/`NLPMatchResult`。
  - 学号概念由 `User.card_id`(String(50), unique, 注释"学号/卡号", `student_routes.py:31,77`) 承担；**全仓无 `student_number` 列**（禁止再引入）。
- **统一方案**：以 `user.id` 为唯一外键，统一字段名为 `student_id` 并加 `ForeignKey("user.id")`；`ScoreRecord.user_id` 改名为 `student_id`；保留 `card_id` 作业务学号展示。

### P0-2 科目表示法不一致：`Score.subject`(自由文本) ↔ `subject_id`(整型)
- **涉及**：`Score`(`models:640`) / `Subject`(`models:149`) / `ScoreRecord.subject_id`(`models:192`) / 前端 `api.ts:914`(`subject_id:number`) vs `api.ts:1200`(`subject:string`)
- **统一方案**：`Score` 废弃自由文本 `subject`，改为 `subject_id` FK→`Subject.id`（消除字符串歧义、便于聚合）。

### P0-3 RBAC 双源 + 角色四分表示
- **涉及**：`RolePermission.permissions`(CSV 文本, `models:496-504`) vs `RolePermissionMapping`(行式 `role_code+permission_code`, `models:706-714`)；`Role`(旧表, `models:215-218`) / `Admin.role`(字符串) / `AdminRole` / `RolePermission`
- **当前差异**：
  - 鉴权引擎 `utils/permission.py:205,230,238` 只读取 `RolePermissionMapping`；`RolePermission.permissions`(CSV) 为冗余、需 `seed_rbac.py` 手动同步，**两源不一致时 UI 权限展示与真实权限背离**。
  - 角色表示四分：`AdminRole`+Mapping（鉴权用）、遗留 `Admin.role` 字符串（`permission.py:181,310,338` 仍读）、`Role` 旧表经 `/api/roles` 返回 `{id,name,permissions}`（`roles_routes.py:33`）与 `/api/rbac/roles` 的 `{role_code,role_name}` 冲突、前端菜单门控用 `admin.role`(`App.tsx:180`/`Sidebar.tsx:244`)。
- **统一方案**：
  - 删除 `RolePermission.permissions`(CSV)，角色权限唯一真源 = `role_permission_mappings` 聚合。
  - 下线 `Role` 旧表与 `/api/roles`；`Admin.role` 由 `AdminRole` 派生；前端统一消费 `role_code` 作主键（`PermissionManagement.tsx:51-56` 已对齐 rbac，仅需弃用 `/api/roles` 分支）。
  - ⚠️ 与 F11 一致：`role_permission` 表本体保留（活动角色目录），仅清理其冗余 `permissions` 列与 `Role` 旧表。

### P0-4 审批流双实现（请假 vs 通用审批）
- **涉及**：`Approvals.tsx` → `Approval` 模型(`approvals_routes.py:30,225,343`，状态 `pending/approved/rejected`)；`AttendanceManage.tsx` 内"请假审批" → 独立 `LeaveApplication` 模型(`attendance_routes.py:91` `/leaves/<id>/approve`，`attendance_service.py:105`)
- **当前差异**：两套数据模型、路由、页面完全分离，状态逻辑双份维护；`LeaveApplication` 实为审批的一种子类。
- **统一方案**：`LeaveApplication` 继承/并入统一 `Approval`（`approval_type='leave'`），或抽公共审批服务，单一审批中心 + 类型区分。

### P0-5 F9 合并后通知/告警「路由层+前端层」契约未统一
- **涉及**：`notifications_routes.py`(user) / `admin_notifications_routes.py`(admin) / 前端 `stores/index.ts` / `types/index.ts` / `Dashboard.tsx`
- **当前差异**：
  - 用户通知出参(`notifications_routes.py:42-62`) 仅返回 id/user_id/title/content/type/status/phone/created_at/sent_at，**缺 `is_read`/`priority`/`extra_data`/`recipient_type`**（模型已含，`notification_model:11-23`）。
  - 前端类型双轨：`read:boolean`(`types/index.ts:232`) 与 `is_read?:boolean`(`:233`) 共存；store 用 `read`(`stores/index.ts:644,656`) → 未读数/优先级全失效。
  - 告警 `Alert` 字段前后端错配：后端出参 `alert_type`(`devices_routes.py:737,820`)，前端 `Alert` 接口用 `type?`(`api.ts:1453`)，且前端缺 `is_read`/`source`。
- **统一方案**：
  - 用户通知出参补齐 `is_read`/`priority`/`extra_data`/`recipient_type`；前端弃用 `read` 统一 `is_read`。
  - 告警前端字段对齐 `alert_type`/`is_read`/`source`（或后端改 `type`，二选一并固化）。
  - 明确统一端点 + `recipient_type` 过滤策略，固化 admin/user 双端点契约（不破坏既有 `/api/admin_notifications/*` 路径）。

### P0-6 心理预警 vs 风险预警近重复实体
- **涉及**：`MentalHealthAlert`(`mental_health.py:18-28`) vs `RiskWarning`(`models:1241-1258`)
- **当前差异**：语义同构（类型+级别+消息+处理），但标识字段(`student_id`/`user_id`)、`severity`(Integer)/`risk_level`(String)、状态表达(布尔/`status`+`is_resolved`)全不一致。
- **统一方案**：合并为统一 `Incident`/`Alert` 实体（`type`/`level`/`message`/`resolved` 三态），复用 F9 已统一的 `Alert` 骨架。

## 2. P1 —— 中优先级不一致

### P1-1 全局状态枚举四处发散（无统一常量）
- `Exam.status`='draft'(`:607`)、`Score.status`='pending'(`:644`)、`CompositeScore.status`='active'(`:1253`)；前端 `api.ts:1422` Exam 状态 `'draft'|'published'|'closed'`、`api.ts:1443` 审批 `'pending'|'approved'|'rejected'`；考勤 `present/absent/late/leave`(`attendance_service.py:124-127`)。
- 建议：抽 `STATUS` / `APPROVAL_STATUS` / `ATTENDANCE_STATUS` 全局枚举常量，前后端共用。

### P1-2 成绩数值类型 Float/Integer 混用
- `Score.score` Float(`:641`)、`Subject.score` Float(`:167`)、`ScoreRecord.score_change` **Integer**(`:188`)、`ScoreRankRule.min_score/max_score` Integer(`:203-204`)、前端 `api.ts:1201` `score: number | string`。
- 建议：考试分=Float、行为分 `score_change` 改 Float、前端 `score` 收敛为 `number`（移除 `number|string`）。

### P1-3 时间字段命名规范缺失
- 事件时间各自命名：`ContactLog.contact_time`/`ActivityRegistration.registered_at`/`StudyGroupMember.joined_at`/`HomeworkSubmission.submitted_at`/`Score.entered_at`。
- `updated_at` 在 MentalHealthRecord/Activity/StudyGroup/CultureRecord/StudyGuide/HomeworkAssignment/StudyGroupMember/StudyGroupScore/ImprovementPlan **均缺失**（ParentContact 有）；前端 `Diagnostics.tsx:102` 用 `create_time`（非模型）。
- 建议：统一 `created_at` / `*_at` 事件时间 / `updated_at` 三字段规范，子表补 `updated_at`。

### P1-4 告警/通知 severity、priority 枚举三层无真源
- `Alert.severity`：后端默认 `info`(`:549`)；前端 `types/index.ts:741` `high|medium|low`、`DeviceManagement` `critical|error|warning|info`、`SecurityAudit` 五值；`alert_service.py` 用 `level`(info/warning/error)（见 P0-5 设备组）。
- `Notification.priority`：后端默认 `normal`(`:284`)、admin 枚举 high/medium/low(`admin_notifications_routes.py:28`)、前端含 `urgent`(`types/index.ts:234`/`Dashboard.tsx:1011`)。
- 建议：`severity ∈ {info,warning,error,critical}`、`priority ∈ {normal,low,medium,high,urgent}`，前后端共用枚举常量。

### P1-5 设备在线判定前后端冲突
- `Dashboard.tsx:275` `is_online = updatedStatus==='online'`（基于推送 status）vs 后端 `Device.is_online`(`models:434-441`，按 `last_heartbeat` 时效)；前端 `Device` 同存 `is_online` 与陈旧 `status`(`:163`)。
- 建议：前端直接采用后端 `is_online`，移除本地 status 派生。

### P1-6 规则实体四套独立重复
- `ScoreRule`(`rules_routes.py:19`) / `ScoreRankRule`(`rank_routes.py:8`) / `TimeRule`(`time_rules_routes.py:7`, `models:347`) / `ScoreCategory`(`categories_routes.py`)；字段高度相似(`name/description/is_active`)。另 `nlp_routes.py:263` `/rules` 与 scores `/rules` 同路径不同蓝图（路由命名混淆）。
- 建议：统一规则基类 `BaseRule`，或显式区分命名空间避免 `/rules` 冲突。

### P1-7 配置散落四套
- `SystemConfig`(单表) / `NotificationConfig`(回灌 `current_app.config`, `notification_config_store.py:5,30`) / `MQTTConfig` / `WarningConfig` 各自独立；前端 `Settings.tsx:67-80` 仅覆盖 `SystemConfig`。
- 建议：抽象统一 `ConfigStore`（按 domain 命名、共用读写 API），`Settings` 各 tab 对应 domain 而非散表。

### P1-8 前端类型 ↔ 后端出参缺字段（静默丢字段）
- `StudyGroupMember.joined_at`：前端要求 string(`types/index.ts:1333`)，后端 `study_group_service.py:101-104` 仅返回 `{student_id, student_name}` → `joined_at` 恒 undefined。
- `ParentContact` 前端缺 `created_at`(`:1179-1189`)，后端返回(`parent_service.py:94`)。
- `Activity`/`CultureRecord` 前端缺 `class_name`(`:1389,:1425`)，后端均返回。
- 建议：补齐后端序列化或前端类型，避免静默丢字段。

### P1-9 通知内容必填校验不一致
- admin POST 必填 `message`(`admin_notifications_routes.py:24`)；user POST 不校验(`notifications_routes.py:64-78`)；batch 必填(`notifications_routes.py:179`)。
- 建议：统一「标题+内容必填」。

### P1-10 通知契约形状不一致
- 前端标 `Promise<Notification[]>`(`api.ts:3812`)，后端返回分页对象 `{notifications,total,...}`(`notifications_routes.py:42`)；仅 `getUnread` 兼容(`api.ts:3815`)。
- 建议：前端按对象解包或后端统一返回数组。

## 4. 重复服务 / 重复逻辑合并建议

| 重复簇 | 成员 | 重叠度 | 合并建议 |
|---|---|---|---|
| **NLP 解析** | `nlp_parser_service`(base) / `nlp_enhanced_service`(base 超集+BM25+语义) / `nlp_fast_parser`(快速路径) | 高 | 收敛为同一 Parser 的三种**策略**（base/enhanced/fast），由 `nlp_service` 按场景选择 |

| **NLP ML** | `nlp_ml_service`(训练引擎) / `nlp_enhanced_service`(内嵌 MLIntentClassifier) | 中 | enhanced 内嵌分类器改为**依赖** `nlp_ml_service`，避免两套 ML |

| **预测三件套** | `score_predict_service` / `prediction_service` / `risk_predict_service` | ≈70% | 三者均实现 `predict_batch`+`train_*`+连续正负向辅助（`score_predict:130` vs `risk_predict:212`），合并为统一预测服务 |
| **分数分布** | `score_predict_service.get_score_distribution`(:310) / `score_distribution_service.get_distribution_statistics`(:114) | 高 | 合并为一处分布计算 |
| **排名逻辑** | `analysis_service.get_class_ranking`(:155)/`get_student_ranking`(:218) / `rank` 路由 / `composite_score_service._update_rankings`(:478) | 中 | 收敛到单一排名服务 |
| **MQTT** | `mqtt_service`(代理转发 `mqtt_manager`) / `mqtt_manager`(真实现) | 高 | 删 `mqtt_service` 代理层，`publish_ota_command`/`get_mqtt_config_from_db` 收敛到 `mqtt_manager` 一处；`mqtt_management_service`(配置/日志) 与 `mqtt_message_service`(业务消息) 职责清晰保留 |
| **综合分 vs 生态分** | `composite_score_service`(学术+行为+考勤，存 CompositeScore) / `score_ecosystem_service`(行为币，改 User.current_score) | 中 | 域不同但都改写"积分"，需明确边界与命名（避免"score"歧义） |

**净效果**：NLP 簇净减 2~3 文件；预测三件套合一；MQTT 代理层删除；排名逻辑合一。
