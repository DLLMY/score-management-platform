## 2. F1 — OTA 多设备类型隔离（推荐主推）

### 2.1 缺口实证

| # | 证据 | 说明 |
|---|---|---|
| 1 | `models/device_models.py:135-148` `FirmwareVersion` 字段全集 = `version/description/file_path/file_size/md5/min_compatible_version/is_mandatory/is_active/created_at/created_by` | **无 `device_type` / 目标类型维度** |
| 2 | `services/ota_negotiation_service.py:94-102` `get_latest_active_firmware()` → `FirmwareVersion.query.filter(is_active).order_by(created_at.desc()).first()` | 取"全局最新 active"，**不区分设备类型** |
| 3 | `services/ota_negotiation_service.py:218-244` `negotiate(device, reported)` 调用上者 | 门铃设备会被判"落后于手机箱固件"→ `action="upgrade"` |
| 4 | `api/devices/firmware_routes.py:208-237` `/ota/check` 同样取全局最新 active | 设备自查亦串型 |
| 5 | `models/device_models.py:81` `Device.device_type` **已存在**；`services/mqtt_manager.py:430/448-449` 注册链路**已解析并落库** | 类型信息**已有，只是固件侧没用它** |
| 6 | `apps/firmware/esp32/doorlock/doorlock.ino:975-993` 心跳 payload 含 `fw_version` 但**无 `device_type`**；全文**无** `TOPIC_OTA` / `verifyOtaSignature` / `ota/register` | 门铃固件**未接入** OTA 链路 |

**风险定性**：一旦 doorlock 设备注册（哪怕不订阅 OTA），后端 `try_auto_negotiate` 会把它判为"需升级"并把 `ota_status` 置 `pending`，随后向它下发 **phonebox 固件地址**；若门铃侧未来订阅 OTA，则会**刷错固件变砖**。这是"无缝 OTA"从单机型走向多机型时**必然引爆**的架构缺口。

**当前规模**：dev 库 `device` 表 0 行、`firmware_versions` 0 行 → **无存量数据迁移风险**，现在是最佳施工窗口。

### 2.2 方案（分 5 阶段，可独立回滚）

#### 阶段 A — 数据模型：给固件加类型维度
- `FirmwareVersion` 新增 `device_type = db.Column(db.String(50), index=True)`，**nullable**（`NULL` 语义 = 兼容任意类型，保持向后兼容）。
- 唯一约束从 `version unique` 调为**复合唯一 `(device_type, version)`**（同名版本可跨机型共存）；若不想动约束，退路是保留全局唯一但上传时前置校验"同 type 版本已存在"。
- 迁移脚本参照既有范式 `scripts/migrate_add_ota_state.py`：**幂等**（先 `PRAGMA table_info` 判列是否存在再 `ALTER TABLE ADD COLUMN`）。
- `to_dict` 增加 `device_type` 字段（注意：`FIRMWARE_FIELDS` 白名单在 `firmware_routes.py:11-22`，**须同步加入**，否则响应不含新字段）。

#### 阶段 B — 协商层：按类型过滤
- `get_latest_active_firmware(device_type=None)` 加形参：`if device_type: query = query.filter(or_(FirmwareVersion.device_type == device_type, FirmwareVersion.device_type.is_(None)))`。
- `negotiate(device, reported_version)` 内改为传 `getattr(device, "device_type", None)`；`no_firmware` 分支语义扩展为"该类型无固件"。
- `negotiate_all_devices(...)` 逐设备按其 `device_type` 协商（现为统一取一个 latest，**须改为按设备分组**，否则灰度计数会错）。
- `_execute_push` 二次协商自动继承新逻辑（已复用 `negotiate`），**零改动**。

#### 阶段 C — 路由层：上传/列表/自查带类型
- `POST /api/firmware/upload`：接受 `device_type` 表单字段（缺省 `None` = 通用）；重名校验改为按 `device_type + version`。
- `POST /api/firmware/versions`（`create_firmware_version`）：`data` 透传 `device_type`。
- `GET /api/firmware/versions`：支持 `?device_type=` 过滤。
- `GET /api/firmware/ota/check`：在取 latest 前先按 `device.device_type` 过滤（**此端点是设备自查主入口，必须改**）。
- `POST /api/firmware/batch-upgrade` / `<id>/ota-upgrade`：`target_version="latest"` 解析时按目标设备类型取；批量时**校验 device_ids 的类型一致性**（混型直接 400，防误刷）。
- ⚠️ 契约影响：`/ota/check`、`/versions` 响应可能新增 `device_type` 键 → 须**同步更新 G5 OpenAPI 快照**（`verify_openapi_contract.py --update`，先备份 `.bak`），这是本方案唯一的契约面变更，须显式确认。

#### 阶段 D — 固件侧：doorlock 接入（可独立排期，见 F3）
- `doorlock.ino` 心跳/注册 payload 加 `"device_type":"doorlock"`；`#define DEVICE_TYPE "doorlock"`。
- 订阅 `phonebox/ota/<client_id>`（可参数化为 `<prefix>/ota/<id>`）、移植 `verifyOtaSignature`（与 phonebox 同密钥算法 HMAC-SHA256 `{id}:{version}:{url}`）、回报 `started/completed/failed`。
- 若本文档本轮只做后端隔离（阶段 A–C），门铃侧可**暂缓**——因缺类型过滤才是风险源，补齐后门铃即使注册也不会被误推。

#### 阶段 E — 前端：固件管理页
- `pages/firmwareManagement/*`：版本列表加「适用机型」列 + 类型筛选；上传表单加机型下拉。
- `pages/deviceManagement/OTAModal.tsx` / `BulkOTAModal.tsx`：选设备后按类型限定可选版本（防混型刷机）。

### 2.4 风险与规避

1. **契约漂移**（唯一实质风险）：`/ota/check` 加类型过滤后，**单机型部署行为不变**（`device_type` 全为 `phonebox` 或无过滤命中同一版本）；但响应新增键会破 G5 → 阶段 C 前先跑 `--strict` 留基线，改动后 `--update` 并人工 diff。
2. **复合唯一约束**：SQLite `ALTER` 不便改约束 → 用"应用层校验 + 新索引"替代（`CREATE UNIQUE INDEX IF NOT EXISTS ux_fw_type_version ON firmware_versions(device_type, version)`），避免重建表。
3. **`negotiate_all_devices` 分组改造**是本次逻辑改动最大点 → 必须有专门单测覆盖"混合类型设备群"的 checked/eligible/scheduled 计数。
4. **回滚**：每阶段独立 commit（待授权），阶段 A 可仅删列/删索引回滚；阶段 B 因是纯函数改动，`git revert` 即可。
