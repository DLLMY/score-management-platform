# ESP32 对接开发文档 02 — 设备识别、注册与认证

> 文档版本：v1.0
> 编写日期：2026-09-12
> 事实来源：`apps/backend/models/device_models.py`、`services/mqtt_manager.py`、`services/mqtt_message_service.py`、`utils/validation.py`、`api/devices/devices_routes.py`

> **核心结论（请先读）**：当前后端**没有设备凭证体系**。设备 `device_id` 由设备自行决定，

## 二、设备唯一标识（device_id）生成规则

### 2.1 后端格式约束（硬性）

`utils/validation.py::validate_device_id` + `ValidationRules`：

| 规则 | 值 |
|------|-----|
| 正则 | `^[a-zA-Z][a-zA-Z0-9_]{5,63}$` |
| 最小长度 | **6** |
| 最大长度 | **64** |
| 首字符 | **必须是字母** |
| 允许字符 | 字母、数字、下划线 `_` |

**合法示例**：`esp32_box_001`、`phoneboxA01`、`PB_2026_0001`
**非法示例**：`001box`（数字开头）、`box-001`（连字符）、`box 001`（空格）、`a1`（太短）、`box001`（5 位，太短）

> ⚠️ **`validate_device_id` 目前只被部分 REST 端点调用**。MQTT 路径
> （`_process_heartbeat` / `_process_ota_register`）**不校验 `device_id` 格式**——
> 只要 `device_id` 字段存在，就会自动创建设备。
> **因此设备侧必须自律遵守上述正则**，否则会污染设备表（产生无法被前端正常展示的记录）。

### 2.2 推荐生成方案

后端**不生成** `device_id`，由设备侧自行确定。推荐优先级：

#### 方案 A（★ 推荐）— 芯片唯一 ID 派生

ESP32 出厂烧录了唯一 MAC，可用于派生稳定 ID：

```cpp
#include <esp_system.h>

// 取 6 字节 base MAC，转 12 位十六进制
String getChipIdHex() {
  uint8_t mac[6];
  esp_read_mac(mac, ESP_MAC_WIFI_STA);
  char buf[13];
  snprintf(buf, sizeof(buf), "%02X%02X%02X%02X%02X%02X",
           mac[0], mac[1], mac[2], mac[3], mac[4], mac[5]);
  return String(buf);
}

// 生成符合后端正则的 device_id（首字符字母 + 长度 ≥6）
String buildDeviceId() {
  return String("pb") + getChipIdHex();   // 例：pb7C9EBDA1F2C4（14 位，全合法）
}
```

**优点**：刷同一份固件到任意板子都得到不同 ID，无需人工台账。
**注意**：`pb` 前缀保证首字符是字母；长度 14 满足 6-64。

#### 方案 B — 编译期宏（小批量、可控流水号）

```cpp
// platformio.ini
// build_flags = -D DEVICE_ID=\"pb20260001\"
#ifndef DEVICE_ID
  #define DEVICE_ID "pb00000000"
#endif
```

**优点**：ID 语义化、便于台账。
**缺点**：固件不再通用，每台需单独编译。

#### 方案 C — NVS 首次开机生成 + 持久化

```cpp
#include <Preferences.h>

String loadOrCreateDeviceId() {
  Preferences prefs;
  prefs.begin("pbcfg", false);
  String id = prefs.getString("device_id", "");
  if (id.length() == 0) {
    uint8_t mac[6];
    esp_read_mac(mac, ESP_MAC_WIFI_STA);
    char buf[16];
    snprintf(buf, sizeof(buf), "pb%02X%02X%02X%02X%02X%02X",
             mac[0], mac[1], mac[2], mac[3], mac[4], mac[5]);
    id = String(buf);
    prefs.putString("device_id", id);
    Serial.printf("[CFG] device_id 首次生成并持久化: %s\n", id.c_str());
  }
  prefs.end();
  return id;
}
```

**优点**：兼顾「自动生成」与「后续可人工改写」（改 NVS 即可换 ID）。
**推荐生产使用**。

### 2.3 命名建议（多设备可读性）

推荐结构化命名，便于运维一眼看出归属：

```
pb{ChipID}                       pb7C9EBDA1F2C4          （通用，推荐）
pb{教学楼}{教室号}{序号}          pbA10101                （人工规划）
pb{年份}{流水号}                  pb20260001              （按批次）
```

> **不要**在 `device_id` 中放中文、空格、连字符、点号——违反正则，且会在 MQTT topic 中引发歧义。

### 2.4 device_id 与 clientId 的关系

| 用途 | 值 | 说明 |
|------|-----|------|
| MQTT `clientId` | `device_id`（或 `device_id-{chipid}`） | 必须全局唯一 |
| 上行 `device_id` 字段 | `device_id` | 后端按此查/建设备 |
| 下行 OTA topic | `phonebox/ota/{device_id}` | 定向升级 |

**强烈建议三者统一为同一个字符串**，减少心智负担与拼写错误。

## 三、设备注册流程

### 3.1 现状：上报即注册（无凭证）

后端有**两条**自动注册路径，都是「收到上报 → 查不到就建」。**没有任何密钥、证书、白名单校验**。

#### 路径 1 — 心跳自动注册（主路径）

topic `phonebox/heartbeat`，由 `MQTTManager._process_heartbeat` 处理：

```
收到心跳
  ├─ Device.query.filter_by(device_id=...).first()
  ├─ 存在 → 更新 status / last_heartbeat / wifi_signal / uptime
  │                / box_*_status / system_state / device_type(条件写)
  ├─ 不存在 → Device(
  │              device_id = 上报值,
  │              name      = f"设备 {device_id}",
  │              status    = 上报 status,
  │              last_heartbeat = now,
  │              ... 其余同上报
  │           ) → INSERT
  └─ 触发 try_auto_negotiate(device)  ← OTA 版本协商
```

#### 路径 2 — OTA 主动注册（推荐设备开机时调用）

topic `phonebox/ota/register` 或 `phonebox/ota/{device_id}/register`，
由 `MQTTManager._process_ota_register` 处理：

```
解析 payload.device_id
  （若无，则取 topic 第 3 段 —— 即 phonebox/ota/{device_id}/register 的 {device_id}）
  ├─ 更新 Device: status="online" / last_heartbeat=now
  │               / fw_version / platform / device_type
  └─ 触发 try_auto_negotiate(device)
```

> ⚠️ **`_process_ota_register` 只更新已存在设备的 `device_type`**，
> 若设备尚未注册，仅更新 `fw_version`/`platform` 等（不创建设备）。
> **因此设备开机顺序必须是：先发 `phonebox/heartbeat`（触发建记录），再发 `phonebox/ota/register`。**

### 3.2 推荐注册时序（设备侧）

```
上电
 │
 ├─ 1. 连 WiFi
 │
 ├─ 2. 连 MQTT（clientId = device_id）
 │
 ├─ 3. 订阅下行 topic（见文档 01 §3.3）
 │
 ├─ 4. 发送首条心跳（触发后端自动建 Device 记录）
 │      topic: phonebox/heartbeat   qos: 0
 │      { device_id, status:"online", fw_version, platform,
 │        device_type:"phonebox", box_a_status, box_b_status }
 │      等待 ~1s 让后端落库
 │
 ├─ 5. 发送 OTA 注册（补全 device_type + 触发版本协商）
 │      topic: phonebox/ota/register   qos: 1
 │      { device_id, fw_version, platform, device_type }
 │
 ├─ 6. 拉取积分规则列表（缓存到本地）
 │      topic: score/rules/query   qos: 1
 │
 └─ 7. 进入主循环
        ├─ 每 30s 发心跳
        ├─ 监听 phonebox/unlock/* 处理开箱
        ├─ 监听 phonebox/ota/{device_id} 处理升级
        └─ 每 30min 重发 phonebox/ota/register 刷新版本与协商
```

### 3.4 设备类型（device_type）取值约定

**当前后端没有枚举约束**，`device_type` 是自由字符串（`String(50)`）。
为与后端既有代码（`wol` 类型）保持一致，建议约定：

| device_type | 含义 | 由谁写入 |
|-------------|------|---------|
| `phonebox` | ESP32 手机箱 **（本文档目标设备）** | 设备注册上报 |
| `wol` | 网络唤醒设备（无实体固件） | 后端 `device_service.create_wol_device` 自动设 |
| `doorlock` | 门锁（**规划中，尚未支持 OTA**） | — |

> 🔴 **重要风险**：`FirmwareVersion` 表**没有 `device_type` 维度**。
> 若未来接入 `doorlock`，全局「最新 active 固件」会被误推给门锁设备。
> 详见《06-差异同步与优化方案》§1。

## 四、认证机制

### 4.1 现状：三层认证，均为「弱认证」

| 层 | 机制 | 强度 | 说明 |
|----|------|------|------|
| **MQTT 接入层** | Broker 用户名 + 密码 | 中（若配置） | 所有设备**共用同一组**凭证（如 `phoneboxtest` / `123456`）。**当前开发库甚至是匿名 + 明文。** |
| **设备身份层** | `device_id` 字符串 | **弱** | 无密钥、无签名、无证书。任何人知道 `device_id` 即可冒充该设备上报。 |
| **业务接口层** | 双 JWT（管理员 / 学生） | 强 | 但**设备不走这条**——设备走 MQTT，不持有 JWT。 |

### 4.2 固件下载端点的匿名化（重要设计决策）

`GET /api/firmware/download/{id}` **是匿名的**（无 `@requires_permission`）。

**原因**（代码注释原文）：设备的 HTTP 客户端（`HTTPClient`）**不携带认证头**，
原实现加了 `requires_permission` 导致 **OTA 全链路 401**。

**替代安全保证**（三重）：

1. **仅 GET 二进制**：无写入、无副作用
2. **realpath 目录校验**：`os.path.realpath(file_path)` 必须位于 `uploads/firmware/` 下，防路径穿越
3. **OTA 指令 HMAC 签名**：指令中携带 `signature`，设备验签通过才下载（见文档 04 §4）

```
GET /api/firmware/download/{id}
  ├─ firmware = FirmwareVersion.query.get_or_404(id)      # 不存在 → 404
  ├─ 文件不存在 → 404
  ├─ realpath 不在 uploads/firmware/ 下 → 403
  └─ send_file(..., mimetype="application/octet-stream")
```

> 🔴 **安全影响**：`firmware.id` 是连续整数，**可被枚举**。
> 任何知道服务器地址的人都能遍历下载全部固件（虽然无法篡改，但固件泄露可能被逆向）。
> 缓解方案见《06》§6（建议：改为随机 token 下载路径）。

### 4.3 OTA 检查接口的「软认证」

`GET /api/firmware/ota/check?device_id=X&current_version=Y`：

```python
device = Device.query.filter_by(device_id=device_id).first()
if not device:
    return APIResponse.error(message="Device not registered", status_code=401)
```

**这是全系统唯一的「设备身份校验」**：只有**已注册**的 `device_id` 才能查询更新。
但 GET 请求无需任何密钥——枚举 `device_id` 即可探测。

### 4.4 推荐的安全增强（自研方案，供后续排期）

以下为**建议方案**，当前**未实现**（差异清单见《06》§4）：

#### 增强 1 — Device 表新增 `device_secret`

```python
# models/device_models.py 追加列
device_secret = db.Column(db.String(64), nullable=True)      # 随机 32 字节 hex
secret_issued_at = db.Column(db.DateTime, nullable=True)
```

设备侧预置或首次注册时下发，此后所有上行携带：

```json

  "nonce": "a1b2c3d4",
  "sig": "HMAC_SHA256(device_secret, device_id|ts|nonce|payload_hash)"
```

后端校验：`|now - ts| ≤ 300s`（防重放）+ `nonce` 未用过 + 签名匹配。

#### 增强 2 — device_id 白名单

`SystemConfig` 增加 `device_whitelist_enabled`，
开启后 `_process_heartbeat` / `_process_ota_register` 对未预登记 `device_id` **拒绝注册**：

```python
# services/device_service.py 建议新增
def is_device_authorized(device_id: str) -> bool:
    """设备白名单校验（新增开关，默认关闭以保持现行为）。"""
    if not _whitelist_enabled():
        return True
    return Device.query.filter_by(device_id=device_id).first() is not None
```

```
GET /api/firmware/download/{id}?token={expire_ts}.{hmac}
```

`token = f"{expire_ts}.{HMAC_SHA256(OTA_SIGNING_SECRET, f'{id}:{expire_ts}')}"`
其中 `expire_ts` 为签发时 `now + 300s`。设备验签 + 校验未过期。

> 增强 1/2/3 全部**向后兼容**（开关默认关闭），可在灰度期逐步开启。
> 完整实现步骤见《06-差异同步与优化方案》§4、§6。

## 五、多设备在线识别

### 5.1 后端权威在线判定

```python
# services/heartbeat_service.py
def is_device_online(device, now=None, default_timeout_seconds=60) -> bool:
    if device is None:
        return False
    if device.last_heartbeat is None:
        return False                                    # 从未上报 → 离线
    now = now or datetime.now()
    threshold = device.heartbeat_timeout or default_timeout_seconds
    if (now - device.last_heartbeat).total_seconds() > threshold:
        return False                                    # 超时 → 离线
    return device.status == "online"                     # 且 status 必须是 online
```

**三个必要条件**：

1. `last_heartbeat` 非空（至少上报过一次）
2. `now - last_heartbeat ≤ heartbeat_timeout`（默认 30s）
3. `device.status == "online"`

> **设备侧影响**：
> - 心跳周期必须 **< `heartbeat_timeout`**，即 < 30s。**推荐 15~25s**（留抖动余量）。
> - 心跳里 `status` 必须发 `"online"`，否则永远判离线。

### 5.2 心跳超时巡检（自动告警）

`heartbeat_service.check_heartbeat_timeout(timeout_seconds=60)`：

```sql
SELECT * FROM device
WHERE last_heartbeat IS NOT NULL
  AND last_heartbeat < :threshold
  AND status = 'online'
  AND alert_enabled = TRUE
```

对每台超时设备：
- 若不存在未解决的 `heartbeat_timeout` 告警 → **创建 Alert**（`severity=warning`, `source=device`）
- `device.status = "offline"`
- `device.last_error = "心跳超时"`

**触发方式**：

| 方式 | 说明 |
|------|------|
| `GET /api/devices/heartbeat-timeout-check` | 手动触发 |
| Celery 定时任务 | 建议 30~60s 周期 |

### 5.3 多设备并发接入要点

| 关注点 | 说明 |
|--------|------|
| **clientId 唯一** | 否则设备互踢（见文档 01 §2.4） |
| **订阅数上限** | EMQX 单客户端订阅数上限 ~10。设备侧订阅 8 个 topic（见文档 01 §3.4），在限额内 |
| **下行 topic 冲突** | `phonebox/points/result` / `score/*/result` 是**共享** topic，多设备都会收到 → **设备必须用 `card_id` / `request_id` / `client_id` 过滤** |
| **定向 topic** | `phonebox/ota/{device_id}` 与 `phonebox/unlock/{box_id}` 是**按设备分发**的，无冲突 |
| **心跳洪流** | 后端已用「双连接分流」隔离，设备侧无需特殊处理 |
| **消息顺序** | MQTT 不保证跨 topic 顺序；同一 clientId 的 QoS1 消息保序 |

### 5.4 设备侧「共享 topic 过滤」范式

```cpp
void onMqttMessage(char* topic, byte* payload, unsigned int len) {
  StaticJsonDocument<768> doc;
  DeserializationError err = deserializeJson(doc, payload, len);
  if (err) { Serial.printf("[MQTT] JSON 解析失败: %s\n", err.c_str()); return; }

  String t = String(topic);

  // —— 共享 topic：必须先确认是发给自己的 ——
  if (t == "phonebox/points/result") {
    const char* cardId = doc["card_id"] | "";
    if (!isLocalCard(cardId)) return;          // 不是本机刷的卡 → 丢弃
    handlePointsResult(doc);
    return;
  }

  if (t == "score/add/result" || t.startsWith("score/add/result/")) {
    // 若订阅了定向 topic，只有带自己 clientId 后缀的才处理
    if (t.startsWith("score/add/result/") && !t.endsWith(String("/") + MQTT_CLIENT_ID))
      return;
    handleScoreAddResult(doc);
    return;
  }

  // —— 定向 topic：收到即可处理 ——
  if (t.startsWith("phonebox/ota/")) { handleOtaCommand(doc); return; }
  if (t.startsWith("phonebox/unlock/")) { handleUnlockResult(doc); return; }
  if (t == "phonebox/control/restart") { handleRestart(doc); return; }
}
```

## 七、设备侧注册与识别自检清单

- [ ] `device_id` 满足 `^[a-zA-Z][a-zA-Z0-9_]{5,63}$`（首字母 + 6-64 位）
- [ ] `device_id` 与 MQTT `clientId` **一致**（推荐）
- [ ] `device_id` 持久化到 NVS，重启不变
- [ ] 出厂批量烧录时**不会**产生重复 `device_id`（用 ChipID 派生可保证）
- [ ] 开机时序：连 MQTT → 订阅 → **首条心跳** → `phonebox/ota/register`
- [ ] 心跳里 `status = "online"`
- [ ] 心跳周期 < 30s（推荐 15~25s）
- [ ] 心跳携带 `fw_version`（语义化）+ `platform` + `device_type`
- [ ] `device_type` 取 `phonebox`
- [ ] 每 30min 重发 `phonebox/ota/register`（刷新版本、触发协商）
- [ ] 共享 topic（`phonebox/points/result`、`score/*/result`）有过滤逻辑
- [ ] 收到广播 `phonebox/control/restart` 时有防误重启保护（见《06》§5）
