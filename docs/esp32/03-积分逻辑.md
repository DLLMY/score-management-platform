# ESP32 对接开发文档 03 — 积分逻辑

> 文档版本：v1.0
> 编写日期：2026-09-12
> 事实来源：`services/mqtt_message_service.py`、`services/unlock_validator.py`、`services/device_service.py`、`api/devices/box_routes.py`、`models/score_models.py`、`utils/score_utils.py`
>
> **核心结论（请先读）**：系统里有**四条互不相同的积分写入路径**，语义、幂等性、审批行为都不同。
> 设备侧接错路径会直接导致「分数没变 / 分数变了两次 / 学生投诉」。
> **ESP32 手机箱应按本文档 §2 的「路径选型矩阵」选择。**

---

## 一、积分体系总览

### 1.1 四条写入路径对比（选型矩阵）

| # | 路径 | Topic / API | 立即生效？ | 幂等？ | 需审批？ | 校验频率限制？ | 手机箱推荐用途 |
|---|------|------------|-----------|--------|---------|--------------|--------------|
| **P1** | 直接加分 | `score/add` (MQTT) | ✅ **是** | ✅ **是**（`msg_id`） | ❌ 否 | ✅ `daily_limit` + `min_interval` | ★★★ **刷卡加分首选** |
| **P2** | 申请加/减分 | `phonebox/points/add` `phonebox/points/sub` (MQTT) | ❌ 否（建 Approval） | ❌ **否** | ✅ 是 | ❌ 否 | 学生自助申请（需老师确认） |
| **P3** | 积分盒子验证 | `POST /api/box/verify` (REST) | ✅ 是 | ❌ **否** | ❌ 否 | ✅ `daily_limit` + `min_interval` | 不推荐设备侧用（有安全隐患，见 §5） |
| **P4** | 开锁扣分 | `phonebox/unlock/{box}` (MQTT) | ✅ 是（**扣分**） | ❌ 否（靠限额约束） | ❌ 否 | ✅ 日/周限额 + 各种门槛 | ★★★ **开箱必用** |

> ⚠️ **P1 与 P2 语义容易混淆**：
> - `score/add` = **直接改分**，立即生效，带幂等
> - `phonebox/points/add` = **提交申请**，不动分数，创建 `Approval` 待审
>
> 两者 topic 前缀不同（`score/` vs `phonebox/points/`），但都属"加分"业务，**最易接错**。

### 1.2 积分数据模型

| 表 / 模型 | 作用 | 关键字段 |
|-----------|------|---------|
| `User` | 学生当前分数 | `current_score` (Float) |
| `ScoreRule` | 积分规则模板 | `name`、`score`、`daily_limit`、`min_interval`、`is_active` |
| `ScoreCategory` | 规则分类 | `name`、`color` |
| `ScoreRecord` | **积分流水（唯一审计源）** | `student_id`、`rule_id`、`score_change`、`description`、`operator`、`created_at` |
| `ScoreRankRule` | 分数段位（影响开锁门槛） | `min_score`、`unlock_min_score`、`weekly_unlock_limit` |
| `Approval` | 审批单 | `student_id`、`type`、`score_change`、`status` |
| `ProcessedMessage` | MQTT 幂等表 | `message_id` (UNIQUE)、`record_id`、`new_score`、`client_id` |
| `SystemConfig` | 全局分数上下限 | `min_score`、`max_score` |

## 二、积分获取方式

### 2.1 方式一览（按业务场景）

| 场景 | 路径 | 触发条件 | 典型分值 |
|------|------|---------|---------|
| **课堂表现加分** | P1 `score/add` | 老师在后台/APP 操作 | +1 ~ +10 |
| **设备刷卡加分** | P1 `score/add` 或 P3 `POST /api/box/verify` | 学生在积分盒子刷卡 | 由 `ScoreRule.score` 决定 |
| **学生自助申请** | P2 `phonebox/points/add` | 学生在设备上申请 | 学生填，老师审 |
| **开箱扣分** | P4 `phonebox/unlock/{box}` | 学生刷卡开手机箱 | **固定 -10** |
| **手动调整** | REST 后台 | 老师直接改分 | 任意（受上下限约束） |

### 2.2 积分上下限（全局钳制）

由 `SystemConfig.min_score` / `SystemConfig.max_score` 约束，通过 `utils/score_utils.py::atomic_score_update` 在 **SQL 层**原子钳制：

```python
def atomic_score_update(user_id, delta, min_score=None, max_score=None):
    expr = User.current_score + delta
    if min_score is not None:
        expr = func.max(expr, min_score)      # 不低于下限
    if max_score is not None:
        expr = func.min(expr, max_score)      # 不高于上限
    # → UPDATE user SET current_score = expr WHERE id = :user_id
```

**原子性**：整个 `UPDATE ... SET score = max(min(score + delta, max), min)` 在**单条 SQL** 内完成，
并发安全，不会丢更新。

> ⚠️ **旧文档 `docs/MQTT_INTEGRATION.md`（已于 2026-09-12 归档）声称「最小值 0，最大值 100」——这是过时的**。
> 实际上下限由 `SystemConfig` 表运行时决定，且 `ScoreRule.score` 是 **Float**（可为 0.5 等小数）。
> 请以 `GET /api/system/config` 或直接查表为准。

## 三、路径 P1 — 直接加分 `score/add`（★ 推荐）

### 3.1 上行

**Topic**：`score/add`  **QoS**：`1`

```json
{
  "msg_id": "msg_pb7C9EBDA1F2C4_17_add",
  "client_id": "pb7C9EBDA1F2C4",
  "user_id": 1,
  "rule_id": 5,
  "rule_name": "主动回答问题",
  "score_change": 5,
  "description": "课堂表现优秀",
  "operator": "李老师"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `msg_id` | string | **强烈建议** | 幂等键，见 §3.3 |
| `client_id` | string | 建议 | 决定回包 topic 后缀 |
| `user_id` | int | **是**（除按卡号场景） | 学生 ID |
| `rule_id` | int | 三选一 | 精确匹配 `ScoreRule.id` |
| `rule_name` | string | 三选一 | **模糊匹配** `like('%name%')` |
| `score_change` | number | 三选一 | 直接指定分值（可为负？→ 见 §3.5） |
| `description` | string | 否 | 流水描述；**不传则用规则名** |
| `operator` | string | 否 | 操作人，默认 `"MQTT System"` |

**三选一寻址优先级**（后端 `handle_score_add`）：

```
if rule_id      → _handle_score_by_rule_id      # 优先级 1
elif rule_name  → _handle_score_by_rule_name    # 优先级 2
elif score_change is not None → _handle_score_by_score_change  # 优先级 3
else            → 报错 "缺少加分依据"
```

### 3.2 下行

**Topic**：若有 `client_id` → `score/add/result/{client_id}`；
否则 → `score/add/result`

```json
{
  "success": true,
  "msg_id": "msg_pb7C9EBDA1F2C4_17_add",
  "message": "加分成功: 主动回答问题 (+5分)",
  "new_score": 92.5,
  "record_id": 1234,
  "rule_name": "主动回答问题",
  "undo_code": "UNDO_1234"
}
```

**失败样例**：

```json
{
  "success": false,
  "msg_id": "msg_pb7C9EBDA1F2C4_17_add",
  "message": "Daily limit reached (3/3)"
}
```

| 失败消息 | 触发条件 |
|---------|---------|
| `User not found` | `user_id` 不存在 |
| `Rule not found or inactive` | `rule_id` 无对应或 `is_active=False` |
| `Rule name not found` | `rule_name` 模糊匹配无结果 |
| `Daily limit reached (x/y)` | 当日同规则累计达 `daily_limit` |
| `Too frequent, wait Ns` | 距上次同规则使用不足 `min_interval` 分钟 |
| `缺少加分依据...` | 三选一都没给 |

### 3.3 幂等机制（P1 独有，务必使用）

后端 `handle_score_add` 开头：

```python
record = ProcessedMessage.query.filter_by(message_id=msg_id).first() if msg_id else None
if record:
    # 直接返回上次结果，不重复加分
    response = {
      "success": True,
      "message": "Message already processed (idempotent)",
      "msg_id": msg_id,
      "new_score": record.new_score,
      "record_id": record.record_id,
      "undo_code": f"UNDO_{record.record_id}",
    }
    publish_mqtt(response_topic, json.dumps(response))
    return
# ... 正常处理，成功时 INSERT ProcessedMessage(message_id=..., record_id=..., new_score=...)
```

**行为**：

- **不带 `msg_id`** → 每次都是新加分（**不幂等**）
- **带 `msg_id` 且首次** → 正常加分 + 落 `ProcessedMessage`
- **带 `msg_id` 且重复** → 返回上次 `new_score` / `record_id`，**不重复加分**，`message` 为 `"Message already processed (idempotent)"`

**设备侧最佳实践**：

```cpp
#include <Preferences.h>

// 持久化自增序号，断电重启不重复
uint32_t nextSeq() {
  Preferences prefs;
  prefs.begin("pbseq", false);
  uint32_t seq = prefs.getUInt("seq", 0) + 1;
  prefs.putUInt("seq", seq);
  prefs.end();
  return seq;
}

String makeScoreMsgId(const char* action) {
  return String("msg_") + DEVICE_ID + "_" + String(nextSeq()) + "_" + action;
}

// 发送加分
String msgId = makeScoreMsgId("add");
doc["msg_id"] = msgId;
doc["client_id"] = DEVICE_ID;
doc["user_id"] = userId;
doc["rule_id"] = ruleId;
// → publish("score/add", ...)
// → 收不到回包时可安全重发同一条（msg_id 相同 → 幂等）
```

> ★ **这是 P1 最大的价值**：可以在网络抖动时**安全重试**，不会重复加分。

### 3.4 频率限制规则

由 `ScoreRule` 两个字段控制，后端 `check_rule_limit` 强制：

| 字段 | 含义 | 判定逻辑 | 拒绝消息 |
|------|------|---------|---------|
| `daily_limit` | 当日同规则累计上限（**0 = 不限**） | 统计当日 `ScoreRecord` 中 `rule_id` 相同的条数 | `Daily limit reached (today/limit)` |
| `min_interval` | 距上次同规则使用的最小间隔（**分钟**，**0 = 不限**） | 查该学生该规则最近一条 `ScoreRecord.created_at` | `Too frequent, wait Ns` |

**统计口径**（`ScoreRecord` 按 `created_at` 落在自然日 `[00:00:00, 23:59:59.999999]`）：

```python
today_count = ScoreRecord.query.filter(
    ScoreRecord.student_id == user_id,
    ScoreRecord.rule_id == rule_id,
    ScoreRecord.created_at >= start_of_day,      # 今日 00:00:00
    ScoreRecord.created_at <= end_of_day,        # 今日 23:59:59.999999
).count()
if today_count >= rule.daily_limit:
    return False, f"Daily limit reached ({today_count}/{rule.daily_limit})"
```

### 3.5 `score_change` 路径与负分

若用 `score_change` 直接指定分值：

- 后端 `_handle_score_by_score_change` **不校验正负**
- 负值将**直接扣分**（无审批、无限额、无门槛）
- 🔴 **设备侧禁止用负 `score_change` 扣分**——扣分应走 P4（开锁）或 P2（申请，需审批）
- 建议设备侧对 `score_change` 做 `> 0` 的本地 assert

## 四、路径 P2 — 申请加/减分（走审批）

### 4.1 语义

**不会立即修改分数**。后端创建一条 `Approval` 记录（`status="pending"`），
老师在后台审批后才真正改分。

### 4.2 上行 — 申请加分

**Topic**：`phonebox/points/add`  **QoS**：`1`

```json
{
  "msg_id": "msg_pb7C9EBDA1F2C4_18_padd",
  "client_id": "pb7C9EBDA1F2C4",
  "card_id": "20230001",
  "amount": 5,
  "device_id": "pb7C9EBDA1F2C4",
  "request_id": "req_0018"
}
```

### 4.3 上行 — 申请减分

**Topic**：`phonebox/points/sub`  **QoS**：`1`

```json
{
  "msg_id": "msg_pb7C9EBDA1F2C4_19_psub",
  "client_id": "pb7C9EBDA1F2C4",
  "card_id": "20230001",
  "amount": 3,
  "device_id": "pb7C9EBDA1F2C4",
  "request_id": "req_0019"
}
```

> 🔴 **字段名是 `amount`，不是 `points`！**
> 后端 `handle_points_add` / `handle_points_sub` 读取的是 `data.get("amount", 0)`。
> 传 `points` 会被当成 `0`，直接返回 `"Amount must be greater than 0"`。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `card_id` | string | **是** | 学生卡号（**不是 `user_id`**） |
| `amount` | number | **是** | 申请分值，**必须 > 0**；减分也用正数 |
| `device_id` | string | 建议 | 记入审批单描述，便于溯源 |
| `request_id` | string | 建议 | 原样回包，便于设备关联请求 |

### 4.4 下行（两条路径统一）

**Topic**：`phonebox/points/result`（**固定**，无后缀）

**加分成功**：

```json
{
  "success": true,
  "message": "Request submitted for approval, awaiting admin confirmation",
  "card_id": "20230001",
  "user_name": "张三",
  "requested_amount": 5,
  "request_id": "req_0018",
  "approval_id": 77,
  "status": "pending"
}
```

**减分成功**：结构同上（`requested_amount` 为申请的正数值）。

**失败**：

| 失败消息 | 触发条件 |
|---------|---------|
| `Please provide card ID` | 缺 `card_id` |
| `Amount must be greater than 0` | `amount` 缺失、为 0 或负数 |
| `Card not registered, user not found` | 卡号查不到用户 |

### 4.5 生成的 Approval 记录

| 字段 | 加分路径 | 减分路径 |
|------|---------|---------|
| `student_id` | `user.id` | `user.id` |
| `type` | `"score_add"` | `"score_sub"` |
| `title` | `"Device score add request"` | `"Device score subtract request"` |
| `description` | `"Device {device_id} requests to add +{amount} points for {user.name}"` | `"Device {device_id} requests to subtract -{amount} points from {user.name}"` |
| `score_change` | `+amount` | `-amount` |
| `status` | `"pending"` | `"pending"` |

### 4.6 ⚠️ P2 无幂等（重要风险）

`handle_points_add` / `handle_points_sub` **不检查 `msg_id`，不写 `ProcessedMessage`**。

**后果**：同一条请求发 N 次 → 创建 N 条 `Approval` → 老师误批多次 → 重复加分。

**设备侧规避方案**：

```cpp
// 1. 发送前记录 request_id
// 2. 收到回包后（按 request_id 匹配）标记完成
// 3. 未收到回包的重试，必须在 60s 内且最多 2 次
// 4. 更稳的做法：改为走 P1（score/add）——但那就失去了"审批"语义
```

> 根治方案见《06-差异同步与优化方案》§7（给 P2 补 `msg_id` 幂等）。

## 五、路径 P3 — 积分盒子验证（REST，不推荐设备侧使用）

### 5.1 接口

```
POST /api/box/verify
Authorization: Bearer {admin_jwt}       ← 需要 device.manage 权限
Content-Type: application/json

{
  "card_id": "20230001",
  "device_id": "pb7C9EBDA1F2C4",
  "rule_id": 5
}
```

### 5.2 行为

| `rule_id` | 行为 |
|-----------|------|
| 提供 | 校验规则 → 校验限额 → `box_add_score(user, rule)` **立即加分** |
| 不提供 | 仅做身份验证，返回用户信息 |

**响应（加分）**：

```json
{
  "success": true,
  "message": "积分添加成功 +5",
  "data": {
    "user": { "id": 1, "name": "张三", "card_id": "20230001", "current_score": 92.5 }
  }
}
```

**校验链**：

```
1. card_id / device_id 缺失          → 400 "缺少必要参数"
2. 用户不存在                        → 404 "未找到用户"
3. 设备不存在                        → 404 "设备不存在"
4. device.status != "online"        → 400 "设备离线"
5. rule 不存在或 !is_active          → 400 "规则不存在或未启用"
6. device.admin_id 存在 且
   rule.created_by != device.admin_id → 403 "规则权限不足"
7. check_rule_limits(user_id, rule_id) 失败 → 400（具体消息）
8. box_add_score(user, rule)         → 加分
```

### 5.3 为什么设备侧不该用 P3

| 问题 | 说明 |
|------|------|
| **需要 JWT** | `@requires_permission("device.manage")` — ESP32 需持有管理员 JWT，**极度不安全**（固件可被逆向提取） |
| **无幂等** | `box_add_score` 不写 `ProcessedMessage`，重试会重复加分 |
| **需要 HTTPS + 证书** | 增加固件复杂度与内存占用 |
| **需要知道 `rule_id`** | 设备侧要么硬编码，要么先查规则（多一次往返） |
| **服务端设备在线校验用 `device.status`** | 而在线判定权威逻辑是 `is_device_online()`（还看 `last_heartbeat`）→ 可能不一致 |

> ✅ **结论**：ESP32 加分一律走 **P1（`score/add`，MQTT，QoS1，带 msg_id）**。
> P3 仅用于「后台管理员在网页上手动刷卡加分」场景。

## 六、路径 P4 — 开锁扣分（★ 手机箱核心）

### 6.1 触发

设备向 `phonebox/unlock/{box_id}` 发布开箱请求后，后端在校验通过时执行：

```
UnlockValidator.record_unlock(user)
  ├─ user.today_unlock_count += 1
  ├─ user.weekly_unlock_count += 1
  ├─ 扣 10 分（UNLOCK_COST）
  ├─ 写 ScoreRecord(
  │     student_id = user.id,
  │     rule_id    = None,
  │     score_change = -10,
  │     description = "开锁扣分",          ← 固定字符串
  │     operator    = "MQTT System"
  │  )
  └─ db.session.commit()
```

### 6.2 核心常量

| 常量 | 值 | 说明 |
|------|-----|------|
| `MIN_SCORE` | **80** | 默认开锁最低分数门槛 |
| `UNLOCK_COST` | **10** | 每次开箱扣分 |
| `WEEKLY_LIMIT` | **5** | 每周开箱次数上限 |
| `DAILY_LIMIT` | **10** | 每日开箱次数上限 |

> **可被 `ScoreRankRule` 覆盖**：
> - `ScoreRankRule.unlock_min_score` — 该分数段的最低开锁分（`NULL` 则用全局 80）
> - `ScoreRankRule.weekly_unlock_limit` — 该分数段的周限额（`NULL` 则用全局 5）

### 6.3 校验链（`UnlockValidator.validate_unlock`）

严格按顺序判定，**第一个失败即返回**：

```
1. 卡号查不到用户              → (False, "card_not_found")
2. user.is_active == False     → (False, "user_inactive")
3. 黑名单检查
   ├─ is_blacklisted=True 且
   │  (blacklist_until is None → 永久  或  blacklist_until > now)
   │                            → (False, "blacklisted")
   └─ blacklist_until 已过期 → 自动解除，继续
4. 分数门槛
   min_required = ScoreRankRule.unlock_min_score (该生所在段) 或 MIN_SCORE(80)
   if user.current_score < min_required → (False, "score_low")
5. 周限额
   weekly_limit = ScoreRankRule.weekly_unlock_limit 或 WEEKLY_LIMIT(5)
   if user.weekly_unlock_count >= weekly_limit → (False, "weekly_limit")
6. 日限额
   limit = user.daily_unlock_limit if not None else 5      ← 硬编码回落 5
   if user.today_unlock_count >= limit → (False, "daily_limit_exceeded")
7. 时间窗口（TimeRule）
   若配置了 TimeRule 规则但当前时间不匹配 → (False, "not_in_time_window")
   （day_of_week = -1 表示每天）
8. 全部通过 → (True, "ok")
```

> 🔴 **重要实测更正（2026-09-12 逐行核对 `unlock_validator.py` L128-137）**：
>
> ```python
> @staticmethod
> def _check_daily_limit(user: User) -> bool:
>     today = date.today()
>     if user.last_unlock_date != today:
>         user.today_unlock_count = 0
>         user.last_unlock_date = today
>     # R2 复核修复: daily_unlock_limit/today_unlock_count 历史数据可能为 NULL → None 比较 TypeError
>     limit = user.daily_unlock_limit if user.daily_unlock_limit is not None else 5
>     used = user.today_unlock_count or 0
>     return used < limit
> ```
>
> **日限额的实际取值**：
> - 优先 `user.daily_unlock_limit`（模型默认 **5**）
> - 为 `None` 时**硬编码回落 5**（**不是** `DAILY_LIMIT = 10`！）
> - **`UnlockValidator.DAILY_LIMIT = 10` 在本方法中从未被使用**（它只出现在
>   `get_unlock_status` 的展示分支）
>
> **周限额的实际取值**（L85-90）：
> ```python
> weekly_limit = (rank.weekly_unlock_limit
>                 if rank and rank.weekly_unlock_limit is not None
>                 else UnlockValidator.WEEKLY_LIMIT)         # ← 用常量 5
> ```
> 即**日限额用「用户级 5」，周限额用「段位级 or 常量 5」**。
> 详见《06-差异同步与优化方案》§8。

### 6.4 周期重置机制

| 计数 | 重置时机 | 判定方式 |
|------|---------|---------|
| `today_unlock_count` | 每日 | 比较 `user.last_unlock_date` 是否为今天；不是则清零 |
| `weekly_unlock_count` | 每周（ISO 周） | 比较 `user.week_start_date` 的 `YYYY-Www` 字符串；不同则清零 |

ISO 周跨周重置实现（`_check_weekly_limit`）：

```python
current_week = now.strftime("%Y-W%W")     # 例 "2026-W37"
stored_week = user.week_start_date.strftime("%Y-W%W") if user.week_start_date else None
if stored_week != current_week:
    user.weekly_unlock_count = 0
    user.week_start_date = now
```

### 6.5 扣分记账（审计字符串不可改）

`ScoreRecord.description` **固定为 `"开锁扣分"`**。

> 🔴 **不可更改**：统计代码用 `like('%开锁%')` 匹配开箱流水。
> 改成别的字符串会导致**开箱统计全部归零**。

`ScoreRecord.rule_id` 为 `None`（不关联规则），`operator` 为 `"MQTT System"`。

### 6.6 开锁结果的 reason 码全集

设备侧应把 `reason` 直接映射为蜂鸣/屏幕提示（详见文档 01 §6.3）。

| reason | 含义 | 是否可重试 |
|--------|------|-----------|
| `ok` | 校验通过（`validate_unlock` 返回） | — |
| `success` | 成功扣分并开箱 | — |
| `query_ok` | 查询成功（`phonebox/query`） | — |
| `manual` | 后台手动开箱 | — |
| `card_not_found` | 卡未注册 | ❌ |
| `user_inactive` | 账号停用 | ❌ |
| `blacklisted` | 黑名单 | ❌ |
| `score_low` | 分数低于门槛 | ❌（需先加分） |
| `weekly_limit_exceeded` | 周次数用尽 | ❌（等下周） |
| `daily_limit_exceeded` | 日次数用尽 | ❌（等明天） |
| `not_in_time_window` | 不在 TimeRule 允许时段窗口 | ⏳（到窗口再来） |
| `not_in_time` | 不在全局 TimeRule 允许时段 | ⏳ |
| `class_in_session` | 正在上课（硬拦截） | ⏳（下课后可） |
| `teacher_disabled` | 班主任关闭本班自助开箱 | ❌（找班主任） |

> ⚠️ **`validate_unlock` 返回的 reason 是小写下划线形态**
> （`score_low` / `weekly_limit_exceeded` / `daily_limit_exceeded` / `not_in_time_window` / `ok`），
> 而 `mqtt_message_service` 在部分分支使用简写（`weekly_limit` / `daily_limit` / `time_window` /
> `not_in_time` / `class_in_session` / `teacher_disabled`）。
> **设备侧匹配时应做包含判断（如 `reason.find("limit") >= 0`），不要做精确全等**。
> 详见《06-差异同步与优化方案》§17。

## 八、设备侧积分交互范式

### 8.1 场景 A：学生刷卡加分（推荐走 P1）

```cpp
void onCardSwiped(const String& cardId) {
  // 1. 查询学生（用 phonebox/points/query 只读，不扣分）
  StaticJsonDocument<256> q;
  q["msg_id"]      = makeMsgId("pquery");
  q["client_id"]   = DEVICE_ID;
  q["card_id"]     = cardId;
  q["request_id"]  = String("req_") + millis();
  String out; serializeJson(q, out);
  mqtt.publish("phonebox/points/query", out.c_str(), /*retain=*/false);
  // → 等待 phonebox/points/result，取 user_name / new_points，校验 card_id 匹配
  // → 展示给用户确认后，再进入步骤 2
}

void onStudentConfirmAdd(int userId, int ruleId) {
  StaticJsonDocument<384> a;
  a["msg_id"]    = makeScoreMsgId("add");   // 持久化自增，跨重启不重复
  a["client_id"] = DEVICE_ID;
  a["user_id"]   = userId;
  a["rule_id"]   = ruleId;                  // 或 rule_name / score_change
  a["operator"]  = DEVICE_ID;               // 便于溯源
  String out; serializeJson(a, out);
  mqtt.publish("score/add", out.c_str(), /*retain=*/false);
  // → QoS1，未收到回包可安全重发（msg_id 相同 → 幂等）
}
```

### 8.2 场景 B：学生刷卡开箱（P4）

```cpp
void onUnlockRequest(const String& cardId, const char* boxId) {
  StaticJsonDocument<256> u;
  u["msg_id"]    = makeMsgId("unlock");
  u["client_id"] = DEVICE_ID;
  u["box_id"]    = boxId;                   // "A" 或 "B"
  u["card_id"]   = cardId;
  // 可选：传本地时间，否则后端用服务器时间
  struct tm t; if (getLocalTime(&t, 100)) {
    u["hour"] = t.tm_hour;
    u["minute"] = t.tm_min;
  }
  String out; serializeJson(u, out);
  mqtt.publish(String("phonebox/unlock/") + boxId, out.c_str(), /*retain=*/false);

  // ★ 绝不盲目重发！只等一次，超时则提示"网络异常，请重试"
}
```

### 8.3 场景 C：申请加分（P2，需审批）

```cpp
void onStudentRequestAdd(const String& cardId, int amount) {
  StaticJsonDocument<320> p;

}
```

## 九、积分逻辑自检清单

- [ ] 加分统一走 `score/add`（P1），**不使用** `POST /api/box/verify`（P3）
- [ ] 每条 `score/add` 携带 `msg_id`，且**持久化自增**（断电不重复）
- [ ] `score/add` 使用 **QoS 1**
- [ ] 收到 `undo_code` 后**持久化到 NVS**
- [ ] 申请加/减分使用 `phonebox/points/{add|sub}`，字段名是 **`amount`**（非 `points`）
- [ ] 申请类请求**限制重试次数**（后端无幂等）
- [ ] 不修改 `ScoreRecord.description` 中的 `"开锁扣分"` 字样
- [ ] `phonebox/unlock/*` **绝不盲目重试**
- [ ] 收到 `reason=score_low` 时展示 `current_score`，引导用户先加分
- [ ] 开机拉取一次 `score/rules/query` 并缓存（建议 30min 刷新）
- [ ] 本地按规则的 `daily_limit` / `min_interval` 预判，减少无效请求
- [ ] 所有积分 payload 的 `score_change` 为**正数**（负分走开锁或申请）
