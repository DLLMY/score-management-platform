## 一、心跳与在线判定

### 1.1 心跳报文（回顾，详见文档 01 §6.2）

**Topic**：`phonebox/heartbeat`  **QoS**：`0`  **周期**：建议 15~25s

```json
{
  "device_id": "pb7C9EBDA1F2C4",
  "status": "online",
  "timestamp": 1757680000,
  "wifi_signal": -55,
  "uptime": 86400,
  "box_a_status": "closed",
  "box_b_status": "closed",
  "system_state": 1,
  "fw_version": "1.0.0",
  "platform": "esp32",
  "device_type": "phonebox",
  "free_heap": 187432,
  "battery_level": 100,
  "temperature": 36.5,
  "last_error": "",
  "error_count": 0
}
```

### 1.2 在线判定公式（后端权威）

```python
# services/heartbeat_service.py::is_device_online
(last_heartbeat IS NOT NULL)  AND
(now - last_heartbeat <= heartbeat_timeout)  AND
(status == "online")
```

| 条件 | 说明 |
|------|------|
| `last_heartbeat` 非空 | 至少上报过一次心跳 |
| 时效性 | 默认阈值 `heartbeat_timeout = 30` 秒 |
| `status == "online"` | **心跳里的 `status` 字段必须发 `"online"`** |

### 1.3 关键参数

| 参数 | 默认 | 说明 | 设备侧影响 |
|------|------|------|-----------|
| `Device.heartbeat_timeout` | **30 秒** | 超时阈值 | 心跳周期必须 < 30s |
| `is_device_online` 的 `default_timeout_seconds` | 60 秒 | `heartbeat_timeout` 为空时的回落值 | — |
| `OTA_ROLLOUT_JITTER_SEC` | 30 | 与心跳无关 | — |

> 🔴 **心跳周期建议 15~25 秒**，留出网络抖动余量。
> 如果设成正好 30s，任何一次抖动都会导致设备被误判离线并触发告警。

### 1.4 心跳超时巡检

**接口**：`GET /api/devices/heartbeat-timeout-check`  权限 `device.view`

**后端逻辑**（`check_heartbeat_timeout(timeout_seconds=60)`）：

```sql
SELECT * FROM device
WHERE last_heartbeat IS NOT NULL
  AND last_heartbeat < (now - timeout)
  AND status = 'online'
  AND alert_enabled = TRUE
```

对每台命中设备：

1. 若不存在「未解决的 `heartbeat_timeout` 告警」→ **创建 Alert**
   - `alert_type = "heartbeat_timeout"`
   - `severity = "warning"`
   - `message = "设备 {name} 心跳超时"`
   - `source = "device"`
2. `device.status = "offline"`
3. `device.last_error = "心跳超时"`

**响应**：

```json
{
  "success": true,
  "data": {
    "timeout_devices": [
      {
        "device_id": "pb7C9EBDA1F2C4",
        "name": "高一(1)班手机箱",
        "last_heartbeat": "2026-09-12T20:12:03",
        "heartbeat_timeout": 30
      }
    ],
    "total_timeout": 1,
    "alerts_created": 1
  }
}
```

> **告警去重**：同一设备同一类型未解决的告警**只创建一条**，不会重复刷屏。

### 1.5 心跳状态汇总（含在线/离线/超时分类）

`heartbeat_service.get_device_heartbeat_status(device_id=None)`：

```json
{
  "devices": [
    {
      "device_id": "pb7C9EBDA1F2C4",
      "name": "高一(1)班手机箱",
      "status": "online",
      "last_heartbeat": "2026-09-12T21:05:33",
      "heartbeat_timeout": 30,
      "is_timeout": false,
      "last_error": null,
      "alert_enabled": true
    }
  ],
  "total": 12,
  "online": 11,
  "offline": 1,
  "timeout": 1
}
```

> **统计口径修正**（代码注释）：`online` 按 `status == "online" AND NOT is_timeout` 统计，
> 避免「心跳超时但尚未被巡检标记为 offline」的设备虚增在线数。

### 1.6 心跳历史查询

| 接口 | 说明 |
|------|------|
| `GET /api/devices/{id}/heartbeats?page=1&per_page=50` | 按内部 id 查 |
| `GET /api/devices/device/{device_id}/heartbeats` | 按 device_id 查 |

**响应**：

```json
{
  "heartbeats": [
    {
      "id": 9981,
      "device_id": "pb7C9EBDA1F2C4",
      "timestamp": "2026-09-12T21:05:33",
      "status": "online",
      "wifi_signal": -55,
      "uptime": 86400,
      "box_a_status": "closed",
      "box_b_status": "closed",
      "system_state": 1,
      "received_at": "2026-09-12T21:05:34"
    }
  ],
  "total": 2880,
  "page": 1,
  "per_page": 50,
  "pages": 58
}
```

> **存储量提示**：25s 周期 → 每天 3456 条/设备。50 台设备 → 17 万条/天。
> 建议对 `device_heartbeat` 表做**定期归档**（系统已有 `operation_log_archives` 模式可参考）。

## 二、箱体（Box）状态

### 2.1 两个箱体

| 箱体 | 字段 | 语义（业务约定） |
|------|------|----------------|
| **A 箱** | `box_a_status` | **班主任远程开箱**（无需验证积分） |
| **B 箱** | `box_b_status` | **需要验证积分**（学生自助） |

> 约定来自 `POST /api/devices/{id}/remote-control` 的注释：
> `unlock_a` = "打开A箱（班主任远程开锁，无需验证）"
> `unlock_b` = "打开B箱（需要验证积分）"

### 2.2 状态取值

| 值 | 含义 |
|----|------|
| `closed` | 关闭（**默认值**） |
| `open` | 打开 |

> 后端未做枚举强校验；设备侧上报时请**严格使用 `open` / `closed`**。

### 2.3 状态上报

在心跳中携带即可：

```json
{
  "device_id": "pb7C9EBDA1F2C4",
  "status": "online",
  "box_a_status": "closed",
  "box_b_status": "open"
}
```

后端 `_process_heartbeat` / `handle_heartbeat_message` 会直接覆盖写入（**不判空，会写 `None`**）。

> ⚠️ **心跳中 `box_a_status` / `box_b_status` 缺失时会写成 `None`**，
> 前端展示会变成空。**设备侧必须每次都带上这两个字段。**

## 三、远程控制

### 3.1 单设备远程控制

**接口**：`POST /api/devices/{id}/remote-control`  权限 `device.edit`

**请求**：

```json
{ "action": "restart" }
```

| action | 语义 | 在线要求 | 后端实现 |
|--------|------|---------|---------|
| `restart` | 重启设备 | ✅ 需在线 | 广播 `phonebox/control/restart`，payload `{"command": "restart"}` |
| `unlock_a` | 打开 A 箱（班主任，免验证） | ✅ 需在线 | 向 `phonebox/unlock/A` 发**空字符串 payload** |
| `unlock_b` | 打开 B 箱（学生，需验证） | ✅ 需在线 | 向 `phonebox/unlock/B` 发 `{"result":"true","reason":"manual","current_score":999}` |

> ⚠️ **在线判定用的是 `device.status != "online"`**（不是权威的 `is_device_online()`）。
> 若设备心跳超时但 `status` 字段仍是 `online`，远程控制会「以为在线」而实际上发出去没人收。
> 详见《06-差异同步与优化方案》§10。

**`unlock_a` / `unlock_b` 的特殊行为**（`_start_smart_unlock`）：

```python
# 后台线程执行，共发送 3 次，每次间隔 500ms
for attempt in range(3):
    publish_mqtt(topic, payload)
    if attempt < 2:
        time.sleep(0.5)
```

**设计动因**：确保设备在可接收状态时能收到（设备可能正在处理上一次刷卡）。

**响应**：

```json
{
  "success": true,
  "message": "A箱智能开锁指令已发送（后台执行，共发送3次）",
  "data": { "action": "unlock_a", "device_id": "pb7C9EBDA1F2C4" }
}
```

> 🔴 **`unlock_a` 的 payload 是空字符串 `""`** —— 设备侧必须能处理**空 payload**（不能直接 JSON 解析）。
> 收到 `phonebox/unlock/A` 的空消息 = 开 A 箱。

### 3.2 批量设备远程控制

**接口**：`POST /api/devices/batch-control`  权限 `device.edit`

**请求**：

```json
{ "device_ids": [1, 2, 3], "action": "restart" }
```

> 注意 `device_ids` 是**内部 `Device.id`（整数）**，不是 `device_id` 字符串。

### 3.3 通用命令下发

**接口**：`POST /api/mqtt/command`  权限 `device.manage`

**请求**：

```json
{
  "device_id": "pb7C9EBDA1F2C4",
  "command": "open_phonebox",
  "params": {}
}
```

| command | 合法值 |
|---------|--------|
| `open_door` | ✅ |
| `open_phonebox` | ✅ |
| `restart` | ✅ |

**下发 topic**：

- 有 `device_id` → `phonebox/command/{device_id}`（**定向**）
- 无 `device_id` → `phonebox/command`（**广播**）

**下发 payload**：

```json
{
  "command": "open_phonebox",
  "timestamp": "2026-09-12T21:05:33.123456",
  "params": {}
}
```

> ⚠️ **设备侧必须订阅 `phonebox/command/{device_id}` 与 `phonebox/command`** 才能收到此类指令。
> 这两个 topic **未在文档 01 的订阅清单中**（因为它们是后期新增的通用通道）。
> **建议设备侧一并订阅。**

### 3.4 手动开锁（MQTT 直发）

**接口**：`POST /api/mqtt/unlock`  权限 `manage_devices`

**请求**：

```json
{
  "box_id": "B",
  "response": { "result": "true", "reason": "manual", "current_score": 999 }
}
```

| box_id | 下发 |
|--------|------|
| `"A"` | `phonebox/unlock/A` + **空 payload** |
| 其他 | `phonebox/unlock/{box_id}` + `{"result","reason","current_score"}` |

## 四、告警（Alert）

### 4.1 告警模型关键字段

| 字段 | 说明 |
|------|------|
| `device_id` | 关联设备（字符串） |
| `alert_type` | 类型，设备类目前有 `heartbeat_timeout` |
| `severity` | `info` / `warning` / `critical` |
| `message` | 告警文本 |
| `source` | 来源，设备类为 `"device"` |
| `is_resolved` | 是否已解决 |

### 4.2 告警接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/devices/alerts?resolved=false&severity=warning` | 告警列表 |
| GET | `/api/devices/{id}/alerts` | 某设备告警历史 |
| POST | `/api/devices/{id}/alerts/{alert_id}/resolve` | 解决告警 |

### 4.3 设备侧错误上报（触发告警的数据源）

设备通过心跳的 `last_error` + `error_count` 上报：

```json
{
  "device_id": "pb7C9EBDA1F2C4",
  "status": "online",
  "last_error": "card reader timeout",
  "error_count": 7
}
```

> ⚠️ **当前后端只把 `last_error` / `error_count` 落库，不会自动生成 Alert**。
> 自动告警目前**只有心跳超时一种**。
> **若需设备主动告警**，需后端新增逻辑（见《06-差异同步与优化方案》§11）。

### 4.4 设备侧告警上报建议（当前可行方案）

由于后端不自动生成设备告警，设备侧可通过**让心跳超时**间接触发告警，
或**调用后台接口**记录（但设备无法持有 JWT）。

**推荐做法**：设备在 `last_error` 中写明确的错误文本，
由后端的告警巡检任务（后续新增）或运维人员通过 `GET /api/devices/{id}` 查看：

```
GET /api/devices/{id}  →  查看 last_error / error_count
```

## 六、WOL（网络唤醒）——非 ESP32 设备

### 6.1 说明

WOL 用于唤醒**支持网络唤醒的电脑/服务器**，**与 ESP32 手机箱无关**，但同属设备域，
设备侧无需实现（`device_type = "wol"`，无实体固件）。

### 6.2 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/wol/wake` | 唤醒单台（按 MAC） |
| POST | `/api/wol/wake/batch` | 批量唤醒 |
| POST | `/api/wol/validate` | 校验 MAC 格式 |
| GET | `/api/wol/status/{mac_address}` | 查询状态 |
| GET | `/api/wol/devices` | WOL 设备列表 |
| GET/PUT/DELETE | `/api/wol/devices/{device_id}` | WOL 设备 CRUD |

### 6.3 与 ESP32 的隔离

WOL 设备通过 `device_service.create_wol_device` 创建：

```python
device_id   = f"wol-{mac}"
device_type = "wol"
```

> ⚠️ **`wol-` 前缀含连字符 `-`**，与 `validate_device_id` 的正则
> `^[a-zA-Z][a-zA-Z0-9_]{5,63}$` **不兼容**！
> 说明 WOL 设备**不走 `validate_device_id` 校验**（内部直建）。
> **ESP32 设备侧请勿模仿此命名**（必须用下划线）。

## 七、班主任手机箱自助开箱策略

### 7.1 策略模型（`PhoneBoxPolicy`）

| 字段 | 类型 | 说明 |
|------|------|------|
| `class_info_id` | FK，**UNIQUE** | 一个班一条策略 |
| `allow_self_unlock` | Boolean | **本班自助开箱总开关** |
| `unlock_windows` | JSON | 预设允许时段列表 |
| `override_until` | DateTime | **一键临时放行截止时间** |
| `updated_by` | FK → admin | 最后修改人 |
| `updated_at` | DateTime | — |

### 7.2 判定优先级（`phonebox_policy.evaluate`）

```
1. override_until > now              → ALLOW_OVERRIDE（最高优先，可越过上课硬拦截）
2. 当前时间在 unlock_windows 内        → ALLOW_WINDOW
3. allow_self_unlock == False        → BLOCK（reason="teacher_disabled"）
4. 无策略 / 不在时段 / 未放行          → DEFER（交给全局 TimeRule + 课表）
```

| decision | 常量 | 效果 |
|----------|------|------|
| `ALLOW_OVERRIDE` | `allow_override` | **跳过**全局 TimeRule 与课表硬拦截，直接进扣分 |
| `ALLOW_WINDOW` | `allow_window` | 同上 |
| `BLOCK` | `block` | 拒绝，`reason="teacher_disabled"` |
| `DEFER` | `defer` | 保持原有全局逻辑（未配置策略的班级完全无感） |

### 7.3 `unlock_windows` 格式

**归一化后存储格式**：

```json
[
  { "day": -1, "start_hour": 10, "start_minute": 0, "end_hour": 10, "end_minute": 20 },
  { "day": 0,  "start_hour": 12, "start_minute": 0, "end_hour": 12, "end_minute": 30 }
]
```

| 字段 | 取值 |
|------|------|
| `day` | `-1` = 每天；`0`~`6` = 周一~周日 |
| `start_hour` / `end_hour` | 0~23 |
| `start_minute` / `end_minute` | 0~59 |

**兼容写法**（`normalize_windows` 也接受）：

```json
{ "day": -1, "start": "12:00", "end": "12:30" }
```

**约束**：

- 结束时间**不能早于**开始时间（`(sh,sm) > (eh,em)` → 报错）
- 不支持跨午夜窗口（与 `OTA_QUIET_WINDOWS` 不同）

### 7.4 策略接口

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/api/phonebox-policy?class_info_id=X` | `phonebox.unlock.manage` | 读取策略 |
| PUT | `/api/phonebox-policy` | `phonebox.unlock.manage` | 更新总开关/时段 |
| POST | `/api/phonebox-policy/override` | `phonebox.unlock.manage` | 一键放行 N 分钟 |
| POST | `/api/phonebox-policy/cancel-override` | `phonebox.unlock.manage` | 取消放行 |

**`class_info_id` 读取规则**（`_read_class_info_id`）：

- 优先读 **query string**：`?class_info_id=X`
- 回落读 **JSON body**：`{"class_info_id": X}`

**班级隔离**：

- 班主任只能管理**自己 `primary_class_id`** 的班级
- `admin` / `super_admin` 可管理任意班级

**管理范围**：

| 角色 | 允许的 `class_info_id` |
|------|---------------------|
| `teacher` | 只能是自己 `primary_class_id`；不传则默认自己班级 |
| `admin` / `super_admin` | 任意班级；**必须显式指定** `class_info_id` |

**响应（无策略时）**：

```json
{
  "success": true,
  "data": {
    "class_info_id": 3,
    "exists": false,
    "allow_self_unlock": false,
    "unlock_windows": [],
    "override_until": null,
    "override_active": false,
    "updated_by": null,
    "updated_at": null
  }
}
```

> **注意 `exists: false` 时 `allow_self_unlock` 为 `false`**（修正过：原实现返回 `true`，
> 导致前端显示"已开启"但实际行为是 `DEFER`，界面误导）。

**一键放行请求**：

```json
{ "minutes": 30, "class_info_id": 3 }
```

- `minutes` 必须为正整数
- 效果：`override_until = now + 30min`

```json
      }

  }
```


**实现说明**：

```python
# is_online 是运行时计算，无法下推 SQL → 先全表过滤再内存分页
devices = Device.query.options(joinedload(Device.class_info), joinedload(Device.admin)).all()
online_devices = [d for d in devices if d.is_online]
total = len(online_devices)
page_items = online_devices[(page-1)*per_page : page*per_page]
```

**性能边界**：

| 设备规模 | 表现 |
|---------|------|
| ≤ 500 台 | 无感知（全表 `joinedload` + 内存过滤） |
| 500 ~ 2000 台 | 建议提高 `cached_api` TTL，或改为 SQL 近似过滤 + 内存精算 |
| > 2000 台 | 需重构（见 §8.5 优化建议） |

### 8.5 多设备扩展性优化建议

当设备规模增长到 500+ 时，推荐以下优化（按收益排序）：

| # | 优化 | 收益 |
|---|------|------|
| 1 | **`online` 判定下推 SQL**：`last_heartbeat > now - timeout AND status='online'` 可用索引（`ix_device_last_heartbeat` 已存在），再用 Python 精确复算 | 从 O(N) 全表降到 O(log N + 页大小) |
| 2 | **提高 `cached_api` TTL**：在线列表 30s → 60s | 降低 DB 压力 |
| 3 | **心跳表分区/归档**：按天分表或定期删除 7 天前数据 | 控制表体积 |
| 4 | **WebSocket 增量推送**：后端已有 `send_device_status`，前端订阅即可，无需轮询 | 消除轮询 |
| 5 | **批量状态查询接口**：`POST /api/devices/status/batch` 传 `device_ids` 列表 | 减少请求数 |

> 完整方案见《06-差异同步与优化方案》§13。

### 9.1 实时推送机制

心跳到达时，后端会通过 WebSocket 推送设备状态：

```python
# MQTTManager._handle_telemetry
if topic == "phonebox/heartbeat" and data.get("device_id"):
    from services.websocket_service import send_device_status
    send_device_status(data["device_id"], {
        "device_id":      data.get("device_id"),
        "status":         data.get("status"),
        "wifi_signal":    data.get("wifi_signal"),
        "uptime":         data.get("uptime"),
        "box_a_status":   data.get("box_a_status"),
        "box_b_status":   data.get("box_b_status"),
        "system_state":   data.get("system_state"),
        "last_heartbeat": data.get("timestamp"),
    })
```

**推送字段**：`device_id`、`status`、`wifi_signal`、`uptime`、`box_a_status`、`box_b_status`、`system_state`、`last_heartbeat`

> **设备侧影响**：无需实现，但需保证心跳中这些字段**全部非空**，
> 否则前端实时面板会显示空白。

### 9.2 前端在线读取设备的两条路径

## 十二、设备侧功能自检清单

- [ ] 心跳周期 15~25s（< `heartbeat_timeout` 30s）
- [ ] 心跳 `status` 恒为 `"online"`（除非真的异常）
- [ ] 心跳**每次**都带 `box_a_status` / `box_b_status`（避免写成 `None`）
- [ ] 心跳带 `wifi_signal` / `uptime` / `system_state`（WebSocket 面板需）
- [ ] 订阅 `phonebox/command/{device_id}` **和** `phonebox/command`
- [ ] 能处理 `phonebox/unlock/A` 的**空 payload**（= 开 A 箱）
- [ ] 能处理 `phonebox/control/restart` 广播（`{"command":"restart"}`）
- [ ] 收到重启指令时有本地保护（如升级中/开箱中不重启）
- [ ] `last_error` / `error_count` 在异常时上报
- [ ] 箱体状态严格用 `open` / `closed`
