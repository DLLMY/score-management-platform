## 差异 1：`FirmwareVersion` 无 `device_type` 维度 🔴

### 现象

`FirmwareVersion` 表**没有** `device_type` 列，`negotiate()` 与 `/ota/check` 都只取
「全局最新 active 固件」，**不区分设备类型**。

### 证据

```python
# services/ota_negotiation_service.py::get_latest_active_firmware
def get_latest_active_firmware():
    """返回最新 active 固件（按 created_at 倒序）。无则返回 None。"""
    return (
        FirmwareVersion.query.filter(FirmwareVersion.is_active)
        .order_by(FirmwareVersion.created_at.desc())
        .first()
    )
```

```python
# apps/backend/api/devices/firmware_routes.py::OTACheck.get
latest_firmware = (
    FirmwareVersion.query.filter(FirmwareVersion.is_active)
    .order_by(FirmwareVersion.created_at.desc())
    .first()
)
```

`FirmwareVersion` 列清单（`models/device_models.py`）：

```
id, version, description, file_path, file_size, md5,
min_compatible_version, is_mandatory, is_active, created_at, created_by
```

**无 `device_type`**。

### 影响

| 场景 | 后果 |
|------|------|
| 只有 `phonebox` | 无影响（当前状态） |
| 新增 `doorlock` 设备 | **doorlock 会被推送 phonebox 固件 → 设备变砖** |
| 同类型不同硬件版本（如 ESP32 vs ESP32-S3） | 无法区分固件 |

> 用户已明确 **OTA 相关延期**，但**接入第二种设备类型前必须修此项**。

### 同步方案

**步骤 1 — 模型加列**

```python
# models/device_models.py::FirmwareVersion
device_type = db.Column(
    db.String(50), nullable=True, index=True,
    comment="适用设备类型（phonebox / doorlock）；NULL = 通用"
)
```

**步骤 2 — 迁移脚本**（SQLite）

```sql
ALTER TABLE firmware_versions ADD COLUMN device_type VARCHAR(50);
CREATE INDEX ix_firmware_versions_device_type ON firmware_versions(device_type);
-- 存量数据回填为 phonebox（当前唯一类型）
UPDATE firmware_versions SET device_type = 'phonebox' WHERE device_type IS NULL;
```

**步骤 3 — 协商按类型过滤**

```python
# services/ota_negotiation_service.py
def get_latest_active_firmware(device_type=None):
    q = FirmwareVersion.query.filter(FirmwareVersion.is_active)
    if device_type:
        # 匹配同类型 或 通用（NULL）
        q = q.filter(
            db.or_(FirmwareVersion.device_type == device_type,
                   FirmwareVersion.device_type.is_(None))
        )
    return q.order_by(FirmwareVersion.created_at.desc()).first()
```

```python
def negotiate(device, reported_version):
    latest = get_latest_active_firmware(getattr(device, "device_type", None))   # ← 传入
    ...
```

**步骤 4 — `/ota/check` 同样过滤**

```python
device = Device.query.filter_by(device_id=device_id).first()
latest_firmware = (
    FirmwareVersion.query
    .filter(FirmwareVersion.is_active)
    .filter(db.or_(FirmwareVersion.device_type == device.device_type,
                   FirmwareVersion.device_type.is_(None)))
    .order_by(FirmwareVersion.created_at.desc())
    .first()
)
```

**步骤 5 — 上传接口接受 `device_type`**

```python
# api/devices/firmware_routes.py::FirmwareUpload.post
device_type = request.form.get("device_type", "phonebox")   # 默认 phonebox 保持兼容
# → create_uploaded_firmware(..., device_type=device_type)
```

**改动范围**：

| 文件 | 改动 |
|------|------|
| `models/device_models.py` | +1 列 |
| migration 脚本 | 新增 |
| `services/ota_negotiation_service.py` | `get_latest_active_firmware` 签名 + `negotiate` |
| `api/devices/firmware_routes.py` | `OTACheck` / `FirmwareUpload` / `BatchUpgrade` / `FirmwareOTAUpgrade` |
| `services/firmware_service.py` | `create_firmware_version` / `create_uploaded_firmware` |

**风险**：中（改动面广，涉及 4 处固件查询；需回归全量 OTA 相关测试）
**兼容性**：✅ 向后兼容（`device_type` 可空 + 默认 `phonebox`）

## 差异 2：无设备端回滚机制 🔴

### 现象

- 无 A/B 分区切换逻辑
- 无「回滚到指定版本」API
- `FirmwareVersion` 无 `is_stable` / `rollback_to` 等标记

### 证据

`FirmwareVersion` 列清单中无任何回滚相关字段；
`DeviceFirmwareUpdate.status` 仅 `pending`/`in_progress`/`completed`/`failed`；
`negotiate()` 只在 `latest.version > reported_version` 时返回 `upgrade`。

**手工回退的障碍**：设备当前 `1.2.3`（故障版），想回退到 `1.2.2` 时：

```python
# negotiate 会判定 up_to_date（因为 1.2.2 < 1.2.3），拒绝推送
if compare_versions(reported_version, latest.version) >= 0:
    return {"action": "up_to_date", "latest_version": latest.version}
```

除非把 `1.2.2` 的 `created_at` 弄成最新且 `1.2.3` 置 `is_active=False`
—— 但 `created_at` 是上传时间，**无法自然变新**，只能改库。

### 影响

| 场景 | 后果 |
|------|------|
| 新固件导致功能异常 | 无法通过后台一键回退 |
| 新固件导致**启动失败**（变砖） | 只能现场 USB 刷机（若未做设备端回滚） |
| 灰度批次出问题 | 只能等冷却后推「更高版本号」的修复固件 |

### 同步方案

**A. 设备侧必须实现（优先，见文档 04 §8.2）**

```cpp
esp_ota_mark_app_valid_cancel_rollback();       // 自检通过
esp_ota_mark_app_invalid_rollback_and_reboot(); // 自检失败 → 回滚
```

**要求**：分区表为双 app 分区（`app0` / `app1`）。

**B. 后端增强（推荐）**

**B1 — 模型加列**

```python
# models/device_models.py::FirmwareVersion
is_stable   = db.Column(db.Boolean, default=False, comment="标记为稳定版本（回滚目标候选）")
rollback_to = db.Column(
    db.Integer, db.ForeignKey("firmware_versions.id"), nullable=True,
    comment="本版本出故障时建议回退到的版本 ID"
)
```

**B2 — 新增回滚 API**

```python
# api/devices/firmware_routes.py
@ns_firmware.route("/rollback")
class FirmwareRollback(Resource):

    @ns_firmware.doc("rollback_firmware", description="回滚设备到指定版本")
    @ns_firmware.response(200, "Success")
    @requires_permission("device.manage")
    def post(self):
        """回滚指定设备到目标版本（绕过 negotiate 的「只升不降」判定）。

        与 ota-upgrade 的差异：
          - 允许目标版本 < 设备当前版本（真正的降级）
          - 强制 force=True
          - 写 rollback 类型的 OperationLog，便于审计
        """
        data = request.get_json() or {}
        device_ids    = data.get("device_ids", [])
        target_version = data.get("target_version")
        reason        = data.get("reason", "")

        if not device_ids or not target_version:
            return APIResponse.bad_request(message="device_ids 与 target_version 为必填项")

        firmware = FirmwareVersion.query.filter_by(
            version=target_version, is_active=True
        ).first()
        if not firmware:
            return APIResponse.error(
                message="Target version does not exist or is not active", status_code=404
            )

        url = build_download_url(firmware, request)
        sig = sign_ota_command(firmware, url)
        results = []
        for device_id in device_ids:
            device = Device.query.filter_by(device_id=device_id).first()
            if not device:
                results.append({"device_id": device_id, "status": "device_not_found"})
                continue
            payload = {
                "id": firmware.id,
                "url": url,
                "download_url": f"/api/firmware/download/{firmware.id}",
                "version": firmware.version,
                "md5": firmware.md5,
                "is_mandatory": True,
                "force": True,                    # ← 强制，绕过本地推迟
                "action": "rollback",             # ← 新增动作标识
            }
            if sig:
                payload["signature"] = sig
            mqtt_manager.publish_ota_command(device_id, payload)
            results.append({"device_id": device_id, "status": "rollback_sent"})

        # 审计
        from utils.audit_log import write_operation_log
        write_operation_log(
            "firmware_rollback", "firmware", firmware.id,
            f"Rollback {len(device_ids)} devices to {target_version}; reason={reason}",
        )
        return APIResponse.success(data={
            "success": True,
            "message": f"Rollback commands sent to {len(device_ids)} devices",
            "results": results,
        })
```

**B3 — 设备侧处理 `action="rollback"`**

```cpp
const char* action = doc["action"] | "update";
// "update" 与 "rollback" 都执行同一套下载+校验+写入流程
// 差异：rollback 时清空 NVS 中的「升级后置」标志，避免误判为新增功能
if (strcmp(action, "rollback") == 0) {
  Serial.println("[OTA] 收到回滚指令");

```

> **关键点**：`rollback` 指令**必须 `force: true`**，因为设备侧通常会用
> `compare_versions` 判断「目标版本是否更新」，降级会被本地拒绝。

**B4 — 灰度异常自动回滚建议（进阶）**

```python

    """若某固件近 window_minutes 内失败率 > threshold → 自动触发回滚。"""
    # 1. 统计 DeviceFirmwareUpdate(to_version=fw.version, status in (completed, failed))
    # 2. 失败率 > threshold 且样本量 >= 5
    # 3. 找 firmware.rollback_to 或最近的 is_stable 版本

```

**改动范围**：

| 文件 | 改动 |
|------|------|
| `models/device_models.py` | +2 列 |

## 差异 3：心跳双路径字段不一致 🟠

### 现象

同一条 `phonebox/heartbeat`，两条处理路径写入的字段**不同**。

### 证据

**路径 A** — `services/mqtt_message_service.py::handle_heartbeat_message`（Celery 兜底/同步路径）

```python
# 接受的字段（第 306-320 行）
device_id, timestamp, status, wifi_signal, uptime,
box_a_status, box_b_status, system_state,
fw_version, platform, free_heap, last_error, error_count
# ↑ 无 device_type / battery_level / temperature
```

**路径 B** — `services/mqtt_manager.py::_process_heartbeat`（主路径）

```python
# 额外处理 device_type（条件写）
if device_type:
    device.device_type = device_type
```

**而** `services/heartbeat_service.py::update_device_heartbeat`（第三处实现）

```python
if heartbeat_data:
    if "wifi_signal"      in heartbeat_data: device.wifi_signal   = ...
    if "battery_level"    in heartbeat_data: device.battery_level = ...
    if "temperature"      in heartbeat_data: device.temperature   = ...
# ↑ 只处理 3 个字段，且不会更新 box_*_status / system_state / fw_version
```

### 影响

| 字段 | 后果 |
|------|------|
| `device_type` | 若走了路径 A，设备类型丢失 → 前端筛选失效 / OTA 类型判断失效 |
| `battery_level` | 若走了路径 A，电量不更新（**实际从未被主路径写入**） |
| `temperature` | 同上 |

### 同步方案

**统一到单一实现**（推荐）：

```python
# services/heartbeat_service.py —— 升级为唯一心跳处理入口
_HEARTBEAT_DEVICE_FIELDS = (
    "status", "wifi_signal", "uptime", "box_a_status", "box_b_status",
    "system_state", "fw_version", "platform", "device_type",
    "free_heap", "battery_level", "temperature", "last_error", "error_count",
)

def apply_heartbeat_to_device(device, data: dict) -> None:
    """把心跳字段统一写入 Device（单一事实来源）。

    规则：字段在 payload 中存在（非 None）才覆盖，避免缺失字段被写成 None。
    """
    for field in _HEARTBEAT_DEVICE_FIELDS:
        if field in data and data[field] is not None:
            setattr(device, field, data[field])
    device.last_heartbeat = datetime.now()
    device.updated_at = datetime.now()
```

然后让 `mqtt_message_service.handle_heartbeat_message` 与
`mqtt_manager._process_heartbeat` **都调用它**。

**关键改进点**：从「存在才覆盖」改为「**输入键存在且非 None 才覆盖**」，
避免当前 `device.box_a_status = box_a_status` 在字段缺失时写成 `None`。

**改动范围**：

| 文件 | 改动 |
|------|------|
| `services/heartbeat_service.py` | +`apply_heartbeat_to_device` |
| `services/mqtt_message_service.py` | `handle_heartbeat_message` 改调统一函数 |
| `services/mqtt_manager.py` | `_process_heartbeat` 改调统一函数 |

**风险**：中（心跳是高频路径，需专项回归 + 灰度观察）

## 差异 4：无设备认证凭证体系 🔴

### 现象

`device_id` 是**唯一身份**，且：
- 无密钥
- 无签名（MQTT 层）
- 可被枚举
- `_process_heartbeat` / `_process_ota_register` **上报即注册**

### 证据

```python
# services/mqtt_manager.py::_process_ota_register
device = Device.query.filter_by(device_id=device_id).first()
if not device:
    device = Device(device_id=device_id, name=f"设备 {device_id}", status="online")
    db.session.add(device)          # ← 任何人都能创建设备
```

代码库中**不存在** `device_token` / `device_secret` / `X-Device` 等标识（grep 无结果）。

### 影响

| 攻击 | 后果 |
|------|------|
| 伪造心跳 | 伪造设备在线状态、污染统计 |
| 伪造 OTA 注册 | 伪装成低版本触发推送（DoS） |
| 枚举 `device_id` 查 `/ota/check` | 探测设备清单（得 401 = 存在） |
| 伪造 `score/add` | **任意加分**（MQTT 账号密码若泄露） |

### 同步方案（分三阶段，全部向后兼容）

#### 阶段 1 — 白名单开关（最低成本，立即可做）

```python
# utils/system_config.py 或复用 SystemConfig 表
def is_device_whitelist_enabled() -> bool:
    from models import SystemConfig
    cfg = SystemConfig.query.filter_by(key="device_whitelist_enabled").first()
    return bool(cfg and cfg.value == "true")
```

```python
# services/mqtt_manager.py::_process_heartbeat
if not device and is_device_whitelist_enabled():
    logger.warning("[MQTT] 拒绝未登记设备注册: %s", device_id)
    return
```

**默认关闭** → 现行为零变化；开启后仅允许后台预先登记的设备接入。

#### 阶段 2 — 设备密钥 + HMAC 签名

**模型**：

```python
# models/device_models.py::Device
device_secret    = db.Column(db.String(64), nullable=True)   # 随机 hex
secret_issued_at = db.Column(db.DateTime, nullable=True)
last_seen_ts     = db.Column(db.BigInteger, nullable=True)   # 防重放
```

**设备侧签名**：

```
sig = HMAC_SHA256(device_secret, f"{device_id}|{ts}|{nonce}|{payload_json}")
```

**上行 payload 追加**：

```json
{
  "device_id": "...",
  "ts": 1757680000,
  "nonce": "a1b2c3d4",
  "sig": "...",
  ...原有字段
}
```

**后端校验**：

```python
def verify_device_signature(device, data: dict) -> tuple[bool, str]:
    """校验设备签名。返回 (通过, 原因)。

    宽容策略：device.device_secret 为 None 时跳过（灰度期未发放密钥的设备）。
    """
    if not device.device_secret:
        return True, "no_secret_configured"          # 灰度兼容

    ts    = data.get("ts")
    nonce = data.get("nonce")
    sig   = data.get("sig")
    if not all([ts, nonce, sig]):
        return False, "missing_signature_fields"

    if abs(time.time() - int(ts)) > 300:             # ±5 分钟
        return False, "timestamp_out_of_window"

    payload_for_sig = {k: v for k, v in data.items() if k not in ("sig", "nonce", "ts")}
    msg = f"{device.device_id}|{ts}|{nonce}|{json.dumps(payload_for_sig, sort_keys=True)}"
    expected = hmac.new(device.device_secret.encode(), msg.encode(), hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, sig):
        return False, "signature_mismatch"
    return True, "ok"
```

#### 阶段 3 — 密钥下发流程

```
后台创建/导入设备
  ↓
生成 device_secret（secrets.token_hex(32)）
  ↓
方式 A：导出设备台账（含密钥），人工烧录 NVS
方式 B：设备首次上报时后端下发（需先通过白名单 + 临时口令）
```

### 改动范围

## 差异 5：重启指令广播不含 `device_id` 🔴 **（最高危）**

### 现象

`POST /api/devices/{id}/remote-control` 的 `action=restart` **忽略**了 `{id}`，
下发到**广播 topic** 且 payload **不含 `device_id`**。

### 证据

```python

    result = publish_mqtt(restart_topic, '{"command": "restart"}')   # ← 无 device_id！

```

**注意**：函数签名接收 `device`，但**函数体内完全没用到 `device.device_id`**。

### 影响

| 场景 | 后果 |
|------|------|
| 后台想重启 1 台设备 | **全部在线设备一起重启** |
| 设备侧无法判断是否该重启 | 要么全重启，要么全忽略 |

> 🔴 **这是当前最危险的设计缺陷**。若生产环境有人点了「重启设备」，
> 会导致全校手机箱同时掉线。

### 同步方案

**方案 A（最小改动，推荐立即执行）— payload 带 `device_id`**

```python
    """发送重启指令（定向到指定设备）。"""
    restart_topic = f"phonebox/control/restart/{device.device_id}"    # ① 定向 topic
    payload = json.dumps({
        "command": "restart",
        "device_id": device.device_id,                                 # ② 带标识
        "timestamp": int(time.time()),
    })
    result = publish_mqtt(restart_topic, payload)
    if result:
        return APIResponse.success(
            message="重启指令已发送",
            data={"action": action, "device_id": device.device_id},
        )
    return APIResponse.server_error(message="MQTT发送失败，请检查连接")
```

**方案 B（保留广播能力）— 双路径**

```python
def _send_device_restart(device, action):

        topic = f"phonebox/control/restart/{device.device_id}"
        payload = {"command": "restart", "device_id": device.device_id,
                   "timestamp": int(time.time())}
    else:
        # 显式全量广播（需单独的管理接口 + 二次确认）
        topic = "phonebox/control/restart"
        payload = {"command": "restart", "target": "all",

```

**改动范围**：

| 文件 | 改动 |

**风险**：低（改动小、影响明确）

### 证据（`services/unlock_validator.py` 逐行核对）

**日限额实际使用**（L128-137）：

```python
DEFAULT_DAILY_UNLOCK_LIMIT = 5

def _check_daily_limit(user: User, daily_limit: int | None = None) -> bool:

    限额优先级：
      1. 显式传入的 daily_limit（由 validate_unlock 按段位规则解析）

                       else UnlockValidator.DEFAULT_DAILY_UNLOCK_LIMIT)
```

## 差异 13：`GET /api/devices/online` 全表加载 🟡

### 现象

```python
# api/devices/devices_routes.py::OnlineDevices.get
devices = Device.query.options(
    joinedload(Device.class_info), joinedload(Device.admin)
).all()                                    # ← 全表加载
online_devices = [d for d in devices if d.is_online]   # ← 内存过滤
total = len(online_devices)
page_items = online_devices[start : start + per_page]
```

`is_online` 含 `(now - last_heartbeat) <= heartbeat_timeout`，无法直接下推 SQL
（因为 `heartbeat_timeout` 是**每行不同**的列值）。

### 影响

| 设备数 | 单次请求开销 |
|--------|-------------|
| 100 | 可忽略 |
| 1000 | ~1000 次 ORM 对象构造 + 2 次 joinedload |
| 5000 | 明显变慢（数百 ms ~ 秒级） |

### 同步方案

**两段式过滤：SQL 粗筛 + 内存精算**

```python
from sqlalchemy import or_, and_, func
from datetime import datetime, timedelta

@ns_devices.route("/online")
class OnlineDevices(Resource):
    def get(self):
        page, per_page = get_pagination(default=50)

        # ① SQL 粗筛：用一个「上界阈值」把明显离线的设备排除
        #    取所有设备 heartbeat_timeout 的最大值作为全局阈值（安全上界）
        max_timeout = db.session.query(func.max(Device.heartbeat_timeout)).scalar() or 60
        cutoff = datetime.now() - timedelta(seconds=max_timeout)

        candidates = (
            Device.query
            .options(joinedload(Device.class_info), joinedload(Device.admin))
            .filter(
                Device.last_heartbeat.isnot(None),
                Device.last_heartbeat >= cutoff,       # ← 用 ix_device_last_heartbeat 索引
                Device.status == "online",
            )
            .all()
        )

        # ② 内存精算：按每台设备各自的 heartbeat_timeout 逐台判定
        online_devices = [d for d in candidates if d.is_online]
        ...
```

**收益**：绝大多数离线设备在 SQL 层被排除，内存处理量从 O(全表) 降到 O(近期心跳设备数)。

**进一步优化（可选）**：若 `heartbeat_timeout` 绝大多数为默认 30，
可加一个**统一阈值配置**（`SystemConfig.device_heartbeat_timeout_default`），
届时可直接 SQL 过滤 + 分页，彻底 O(页大小)。

**风险**：低

## 差异 14：`phonebox/unlock/A` payload 为空字符串 🟡

### 现象

```python
# api/devices/devices_routes.py
_UNLOCK_SPECS = {
    "unlock_a": ("phonebox/unlock/A", ""),      # ← 空字符串 payload
    "unlock_b": ("phonebox/unlock/B",
                 '{"result": "true", "reason": "manual", "current_score": 999}'),

```

### 影响

设备侧若直接 `deserializeJson(payload)`，空字符串会返回 `EmptyInput` 错误。
虽不崩溃（若正确处理了错误分支），但可能导致**开箱指令被忽略**。

### 同步方案

**后端侧统一 payload 格式**（推荐）——让 A 箱也带 JSON：

```python
_UNLOCK_SPECS = {
    "unlock_a": (
        "phonebox/unlock/A",
        '{"result": "true", "reason": "manual", "current_score": null, "box": "A"}',
    ),
    "unlock_b": (
        "phonebox/unlock/B",
        '{"result": "true", "reason": "manual", "current_score": 999, "box": "B"}',
    ),
}
```

**设备侧兼容处理**（必须做，无论后端是否改）：

```cpp
void handleUnlockResult(const String& topic, const uint8_t* payload, unsigned int len) {
  // ★ 空 payload = 开 A 箱（兼容现有实现）
  if (len == 0) {
    Serial.println("[UNLOCK] 收到空 payload → 判定为 A 箱开箱指令");
    openBox('A');
    return;
  }

  StaticJsonDocument<256> doc;
  if (deserializeJson(doc, payload, len)) {
    Serial.println("[UNLOCK] JSON 解析失败");
    return;
  }
  const char* result = doc["result"] | "";
  // ★ result 是字符串 "true"/"false"
  if (strcmp(result, "true") == 0) {
    const char* box = doc["box"] | "";
    openBox((box[0] == 'B') ? 'B' : 'A');
  } else {
    showReason(doc["reason"] | "unknown");
  }
}
```

**风险**：低（后端改动需同步固件，建议先做设备侧兼容）

### 现象

`UnlockValidator.validate_unlock` 返回的 reason 与 `mqtt_message_service` 下发到设备时使用的

### 证据

**`services/unlock_validator.py` 返回的 reason**（判定层）：

|------------|

| `daily_limit_exceeded` |
| `not_in_time_window`（L116） |
| `ok`（通过） |

**`services/mqtt_message_service.py` 下发到设备的 reason**（派发层）：
