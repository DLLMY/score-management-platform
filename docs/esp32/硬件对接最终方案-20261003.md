## 3. 🔴 必须修复的错配（按优先级）

### G2 · unlock 无 `msg_id` 幂等去重（🔴 最高危，对应 §3.3 第1条）
- **现状**：`handle_unlock_message`(L236)→`_deduct_and_unlock`(L346) **直接扣分，无任何 `ProcessedMessage` 去重**；而 `handle_points_*` 已用去重机制（`_find_processed`/`_mark_processed`，L432-459）。
- **风险**：QoS1 重投 / 设备重试 → **重复扣分**（新固件实测 1.4 万重放风暴即此场景）。
- **修复**：
  - `handle_unlock_message` 提取 `msg_id = data.get("msg_id")`，构造键 `unlock:{msg_id}`；
  - 进入 `_deduct_and_unlock` 前查 `ProcessedMessage`；命中则**重发缓存结果、不再扣分**；未命中则处理并把结果（success/reason/score）写入 `ProcessedMessage.record_id` 备用。
  - `msg_id` 为空（旧设备）时跳过去重，保持历史行为（与 `_points_idempotency_key` 同策略）。
- **回归**：新增 `test_unlock_idempotency.py`，模拟同一 `msg_id` 两次上行 → 仅扣 1 次分、两次下发结果一致。

### G1 · unlock/points 下行缺 `device_id`（🔴 高，对应 §3.3 第2条 + §3.2 定向）
- **现状**：`publish_unlock_result(box_id, success, reason, score=None)`(L185) payload 仅 `{result, reason, current_score}`，**无 device_id**；`handle_query`/`handle_unlock` 的 `data` 含 `client_id`（即 device_id 来源），但未透传。
- **风险**：新固件 v1.6.0+ 收到下行校验 `device_id`；若 `box_id` 同名（多箱都叫"A"）两台订阅 `phonebox/unlock/A` → 一台刷卡两台同开（串箱）。
- **修复**：
  - `handle_query_message`/`handle_unlock_message` 提取 `device_id = data.get("device_id") or data.get("client_id")`；
  - `publish_unlock_result` 增 `device_id` 形参并加入 payload：`"device_id": device_id`（topic 仍用 `phonebox/unlock/{box_id}` 不变，device_id 仅作设备侧校验字段，零破坏性）。
- **回归**：`test_mqtt_message_service.py` 断言下行 payload 含 `device_id`；多设备同 box_id 隔离用例。

### G8 · unlock 时段判定应强制用服务器时钟（🟡 中，对应 §3.3 第4条）
- **现状**：`handle_unlock_message` 提取 `hour=data.get("hour")`/`minute=data.get("minute")` 并传给时段判定（L239-240, 251-262）。§3.3 第4条明确要求"**unlock 答案判定用服务器时钟，设备上行不带 hour/minute**"。
- **风险**：若设备仍上行 hour/minute，平台会优先用**设备时钟**（不可靠/可被篡改）→ 时段门禁失效。
- **修复**：在 `handle_unlock_message` 中**强制忽略**设备上行的 hour/minute，统一用 `datetime.now()` 构造 `check_time`（保留 `_build_policy_check_time` 的 None→服务器时钟分支即可）。
- **回归**：模拟上行 hour=3(凌晨) 但服务器为上课时段 → 仍按服务器时钟正确拦截。

### G4 · OTA 期间离线误判（🟡 中，对应 P1 #6）
- **现状**：`is_device_online` 仅靠 `last_heartbeat` 超时（60s）；OTA 下载期设备心跳中断 0.5~6 分钟属正常（§3.1 隐含），会被误判离线并触发 `notify_device_offline` 告警。
- **修复**：`Device` 加 `ota_protect_until` 字段（或可复用 `status_detail`）；`_process_ota_status` 收到 `started` 置 `+10min`；`is_device_online` 在保护窗内返回 True（不判离线）。
- **回归**：`test_device_is_online.py` 增补 OTA 保护窗用例。

### G3 · `points/result` 下行缺 `device_id`（🟢 低，G1 镜像）
- **现状**：`phonebox/points/result` 统一 topic 无 device_id（L462 起的处理链）。
- **修复**：同 G1，下行 payload 补 `device_id`，与固件 v1.6.0+ 定向对齐（单设备当前无影响，多设备必填）。

### G7 · LWT 遗嘱秒级离线感知（🟡 中，对应 §3.3 第3条）
- **现状**：现有离线判定依赖 ① `is_device_online` 心跳超时 ② `scheduled_tasks.py` 每 5 分钟扫超时设备置 offline。**全仓无独立的 LWT 订阅/处理**。`handle_heartbeat_message` 虽读 `status` 并经 `apply_heartbeat_to_device(touch_status=True)` 落库，但 LWT 是 broker 在断线后代发——需满足：设备 will topic=`phonebox/heartbeat` 且 payload 含 `device_id`+`status=offline`，且**通过 `_passes_device_auth_gate` 签名门禁**（L391）。
- **风险**：LWT 消息可能无设备签名 → 被 auth gate 拒绝 → 秒级离线失效，退化为 60s+ 超时离线（不致命但告警延迟）。
- **修复（建议）**：
  - 方案 A（推荐）：心跳 auth gate 对 `status=offline` 的 LWT 消息放行（不校验签名，因 broker 已认证接入）；
  - 方案 B：单独订阅约定 LWT topic（如 `phonebox/lwt/{device_id}`），绕过常规 auth gate 直接置离线。
- **回归**：模拟 broker 代发 offline 心跳 → 设备秒级置 offline。

### G5 · 部署强约束（⚠️ 必配）
- **现状**：`build_download_url`（L211）在 MQTT 后台线程无 request 上下文时，若无 `OTA_FIRMWARE_BASE_URL` 回退相对路径 `/api/firmware/download/{id}` → 设备无法解析 → OTA 推送失败。
- **修复**：生产 `.env` **必须**配置 `OTA_FIRMWARE_BASE_URL=https://<公网域名>`；写入 Runbook，并加启动自检（缺失则告警）。

### G6 · 文档漂移（🟢 低）
- **现状**：`docs/esp32/01-MQTT通信协议.md` 仍描述旧行为（restart 无 device_id、OTA 外链、unlock 不去重），而四份新硬件文档才是事实来源。
- **修复**：评审后同步 `01-MQTT通信协议.md` 的 §4.3/§6.11/§六 OTA 段落，避免硬件团队被旧文误导。

## 4. §4 规划项对接评估（v1.7 / v2.0 roadmap，不阻塞当前）

| 规划项 | 平台现状 | 落地工作量 | 说明 |
|---|---|---|---|
| **quiz 族**（`phonebox/quiz/req|ans|<id>`） | **零代码**（全仓无 `quiz` 订阅/处理） | 中 | 需新增订阅 + 题库服务 + 判分回写；题目 JSON ≤500B |
| **notice 下发**（`phonebox/notice/<device_id>`） | **零代码** | 低 | 纯平台推送，复用 MQTT publish；课表时机由平台 NTP 计算 |
| **W800 语音**（`w800/<id>/up|down|state`） | **零代码** | 中 | 需新增 W800 命名空间 + ASR/TTS 文本透传（ASR/TTS 由 W800 直连公网完成，平台只转发文本） |
| **考勤/多班看板**（§4.4） | 部分（tx_log + heartbeat 已存） | 低 | 纯平台聚合，零设备改动 |

> 结论：§4 全部为**新增功能**，不影响 §3 对接。建议在 §3 错配修复并验证通过后，按"notice（低）→ 看板（低）→ quiz（中）→ W800（中）"顺序排期。

## 5. 对接模式选择建议

| 模式 | 适配度 | 建议 |
|---|---|---|
| **A 直连自研**（平台按 §3/§4 实现 MQTT 客户端） | ✅ 推荐 | 本仓库 `backend/` 即此形态，落地 G1-G8 后即为生产可用 |
| **B 过渡部署**（直接部署本仓库 backend） | ⚠️ 条件性 | 仅可在 **G2+G1 修复后**用于过渡；文档声称"已全量实现 §3"与事实不符，须先修 |
| **C 混合**（backend 做 MQTT↔REST 网关） | 可选 | 平台若不想碰 MQTT 时采用；本仓库已天然支持（REST 端点完备） |

**建议路径**：先用 **A 模式 + 修复 G1/G2/G8/G4/G7** 达到 §3.3 四件事全满足 → 再视需要迭代 §4（B/C 作为备选）。
