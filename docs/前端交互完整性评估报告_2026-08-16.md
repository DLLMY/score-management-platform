# 前端交互完整性与可靠性评估报告（2026-08-16）

> 审查对象：`frontend/src` 全部前端（56 个页面 / 64 条路由 / 50 个 Sidebar 菜单 / 27 个 hooks / 统一 store）。
> 方法：4 个并行子代理按维度静态扫描 + 主代理对关键疑点逐项人工复核（grep/读码验证，排除误报）。**本次为静态代码审查 + 逻辑推演，非浏览器实测**；涉及运行时行为的结论标注「待实测」。
> 维度：1 导航路由 / 2 表单提交 / 3 交互响应 / 4 反馈机制 / 5 异常处理 / 6 状态一致性 / 7 响应式。

## 0. 总体印象

前端**公共设施优秀**：42/57 页面接入统一 Toast；Skeleton / EmptyState / ErrorState / PermissionGuard / NetworkStatus（全局断网提示，App.tsx:249/379 双挂载）/ useForm / useModal / useOptimisticUpdate 等基础设施齐全；分页组件边界干净（`Pagination.tsx:50` 0/1 页不渲染）；Dashboard 空态完整（无数据不崩且有引导）。

核心 CRUD 链路整体可靠；**主要风险集中在三块**：① 路由恢复路径（404 兜底 + 跳转方式）；② 危险操作与提交防抖；③ 认证/通知状态双轨不同步。

## 1. 七个维度逐一结论

### 1) 页面导航与路由跳转 — ⚠️ 严重隐患 2 处
- ✅ 56 个页面全部注册路由、无文件缺失、无未注册页面；47 个菜单 path 全部有对应路由。
- 🔴 **无 `path="*"` 404 兜底**（App.tsx 全量 grep 无 NotFound / path="*"）→ 任何未知路径（手输 URL、悬空链接、跳转失败）主体空白，无提示、无恢复入口。
- 🔴 **HashRouter 下 6 处 `window.location.href` 无 `#` 跳转**（Sidebar.tsx:316/320/504、ErrorBoundary.tsx:125、ScoreEntry.tsx:884、api.ts:674/679）：整页导航到无 hash 的服务器路径。其中 **401 处理（api.ts:674/679）**：刷新令牌失败 → `clearAuthData()` → `href='/login'` → hash 丢失 + 无兜底路由 → **用户到不了登录页，卡在空白/404**（token 过期属高频场景）。
- 🟡 4 个路由无 Sidebar 入口（App.tsx:335-337/347 teacher-tools / semester-report / rank-board / import-config），仅 URL 直达（部分为设计使然，从其他页面进入）。
- 🟡 权限错配 4 处：Sidebar 菜单用细权限（`study_group.view` 等，Sidebar.tsx:396-400）、路由守卫用 `class.view`（App.tsx:360-366）→ 有细权限无 class.view 时「菜单可见、点击被拒」。

### 2) 表单输入、校验与提交流程 — ⚠️ 中等
- ✅ 13 个页面用 useForm；多数表单有基础校验；Login/Notifications/Profile 等用 `<form onSubmit>`（支持回车）。
- 🟡 **无校验直发**：NLPManagement.tsx:479（关键词可空、score_value 无范围）、Profile.tsx:134（三字段全空可提交）、Settings.tsx:106（数值无 min/max，可存 min>max）。
- 🟡 **数值边界缺失**：StudyGroups.tsx:427（可 +99999 分）、PhoneBoxPolicy.tsx:102（可放行 99999 分钟）。
- 🟡 **提交无 loading/防连点**（5 处）：MentalHealth.tsx:624、StudyGroups.tsx:608、Notifications.tsx:477、ActivityManage.tsx:531、AttendanceManage.tsx:661（请假 775 同理）。
- 🟡 **弹窗关闭不重置**：Notifications.tsx:425（发送表单残留）、Profile.tsx:519（改密残留旧密码）。

### 3) 按钮、链接等交互元素响应 — ⚠️ 中等
- ✅ Button 组件 disabled 有 `opacity-50 cursor-not-allowed`（Button.tsx:176）；绝大多数按钮反馈及时（toast 覆盖 42 页）。
- 🟡 **危险操作无二次确认（5 处）**：Settings.tsx:134 恢复默认（覆盖全部系统配置）、SeatingChart.tsx:138 自动排列（覆盖整张座次表）、WakeOnLan.tsx:156 删除设备 + :73 批量唤醒、ScoreEntry.tsx:498 确认全部成绩、DataSyncPage.tsx:59 执行修复（自动建班+改数据关联）。
- 🟡 **成功无提示（3 处）**：StudentPortal.tsx:154（请假成功静默）、DataSyncPage.tsx:44（检查健康无提示）、ClassCompare.tsx:81（分析成功静默）。

### 4) 加载状态、成功/失败提示 — ✅ 良好（少量缺口）
- ✅ 大部分列表/详情有 loading + Skeleton/Spinner；42/57 页接入统一 Toast；NetworkStatus 全局接线。
- 🟡 **运维类页面无 loading**（4 处）：OpsCenter.tsx:208、Diagnostics.tsx:401、SystemMetrics.tsx、RemoteNotify.tsx:245 —— 加载期间直接渲染默认值/空态，无「加载中」反馈。
- 🟡 空数据无 EmptyState 引导（RankBoard.tsx:133、Notifications.tsx:318 用纯文本「暂无数据/暂无通知」）。
- 🟡 成功反馈缺失集中在学生端与运维页（见 3）。

### 5) 异常场景（网络错误/无效输入/边界/空数据）— ⚠️ 中等
- ✅ api.ts 统一错误封装：非 2xx 转 ApiError、401 刷新令牌、网络错误归 `type='network'`（api.ts:608-785）；`Pagination` 0/1 页边界干净。
- 🟡 **业务失败当成功（2 处）**：OpsCenter.tsx:126、SystemMetrics.tsx:50 的 fetchJson 仅判 `res.ok`、剥 `data`，**不检查信封 `success===false`** → 业务失败被当成功数据展示（运维页可信度受损）。
- 🟡 **吞错静默（5 处）**：OpsCenter.tsx:132、SystemMetrics.tsx:56、SecurityAudit.tsx:53（`catch { return null; }`）、DeviceManagement.tsx:445（`// 忽略错误`）、ClassManagement.tsx:229（配置加载失败静默）。
- 🟡 **数组赋值无防护（3 处）**：StudentPortal.tsx:95、RemoteNotify.tsx:278、DeviceManagement.tsx:451 —— 响应非数组/undefined 时 setState 污染 → 渲染崩。
- 🟡 **Invalid Date 渲染（2 处）**：Diagnostics.tsx:246（timestamp 空）、ExamManagement.tsx:526（end_time 无判空，522 行 start_time 有）。

### 6) 状态管理与界面数据一致性 — ⚠️ 中等（架构性）
- 🔴→🟡 **store 形同虚设 + 登录态双源**：`useAuthStore`（stores/index.ts:119）与 `useNotificationStore`（:632）**全项目零消费者**（grep 实证）。认证走 `localStorage['admin']`（Login.tsx:91 写、App.tsx:173/180 读、Sidebar.tsx:84 读），与权限接口返回的 `roles[]`（stores/index.ts:904）是两套 → 角色/权限变更后前端不同步（需重新登录才生效）。
- 🟡 **通知角标与实际不同步**：Header.tsx:56 本地 useState + 30s 轮询；WebSocket 收通知只弹 toast 不写 store（stores/index.ts:394）→ 未读角标滞后。
- 🟡 **时间格式不统一（3 组）**：Header.tsx:136 `toLocaleDateString` vs Notifications.tsx:220 `toLocaleString`；Analysis.tsx:201 `.slice(0,10)` vs Approvals.tsx:294 `toLocaleString`；ScoreRecords.tsx:256 vs ExamManagement.tsx:522。
- 🟡 **数字格式不统一（2 组）**：平均分 `toFixed(2)`/`toFixed(1)`/原样混用（ScoreRecords:388 / AlgorithmAnalysis:1062 / RankBoard:154）；在线率 % 原样 vs `toFixed(1)`。
- 🟡 排序不一致：Dashboard.tsx:332 按 current_score 降序，UserList 主列表无排序。

### 7) 不同屏幕尺寸下的交互 — ⚠️ 轻微~中等
- ✅ 绝大多数 Modal 有 `p-4 w-full max-w-lg` 移动端适配；Sidebar.tsx:509-517 自带移动端汉堡+抽屉；未发现 `w-screen` 固定宽度页面。

- 🟡 RemoteNotify.tsx:1168/:1253 Modal `w-full max-w-md` 无 `p-4/mx-4`，窄屏面板贴边。

## 3. 前端交互完整可信度总体结论

**评分：6.5 / 10（中等偏上）**

**可信的部分**：
- 页面导航可达性完整（56 页面全注册、菜单全对应）
- 核心 CRUD 交互链路（列表/表单/提交/反馈/空态）基础设施成熟，多数页面有 toast + loading + EmptyState
- 网络错误统一封装、断网全局提示、分页边界、Dashboard 空态兜底均达标

**不可完全信任、需优先补强的部分**：
1. **路由恢复路径（S1+S2）**：一旦出现 401/退出登录/无效链接，用户会被困在空白页——这是「交互不可信」的最大来源，且 401 属高频场景。
2. **危险操作确认（M1）与提交防抖（M2）**：误操作/重复提交无防护，数据被覆盖/重复写入风险高。
3. **认证与通知状态双轨（M4）**：角色变更不同步、未读角标滞后，用户感知与后端事实可能背离。

**建议修复顺序**：S1/S2（路由兜底 + 跳转改 `navigate`/`#/path`）→ M1/M2（确认 + 防抖，改动小收益大）→ M4（认证状态收敛到单一来源）→ M5/M6/M7（异常与防护）→ L 级随版本清理。

> 备注：S2 的实际表现（401 后白屏 vs 跳转失效）依赖部署环境（dev fallback / nginx try_files），建议修复后以浏览器实测收尾验证；本报告其余结论均为静态证据。
