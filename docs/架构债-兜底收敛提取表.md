## 二、B 类：已拍板并执行（3 处 → 收敛 2 / 跳过 1）

### B1. `api/analytics/dashboard_routes.py` `DashboardStats.get` —— ✅ 已收敛（commit `ca07ee0`）

- 原兜底：`return APIResponse.error(message='仪表盘统计数据加载失败: %s' % e)`（**无 logger**，status = 400 默认）
- 问题：message **动态拼接异常细节**直返前端，属信息泄露。
- **决策：取选项 a（固定文案）** —— `@safe_handle(default_status=400, message="仪表盘统计数据加载失败，请稍后重试")`。
- 契约影响：**有意变更且已批准** —— 响应 message 不再含异常细节；`status_code` 保持 400 不变。
- 附带收益：`safe_handle` 会 `logger.exception`，原实现**完全无日志**。
- 保留项：源码中「诚实失败：不伪装成全 0 假统计」业务注释（解释为何不返回假数据）。
- 文件 CRLF 41/0 保持；py_compile + pyflakes 全绿；`%s % e` 泄露模式残留 0。

### B2. `api/devices/devices_routes.py:1333` `DeviceExport.get` —— ⏸ 永久跳过（保持原样）

- 原兜底：`APIResponse.server_error(message='设备操作失败，请稍后重试')`
  → 展开为 `error(message, code=-1, status_code=500, error_code="INTERNAL_ERROR")`
- **决策：跳过**。根因：`@safe_handle` **不支持 `error_code` 参数**，收敛必丢 `error_code: "INTERNAL_ERROR"` 字段 → 契约漂移。
- 何时可动（前置条件）：给 `safe_handle` 增加 `error_code` 透传参数（默认 `None` 向后兼容），
  属公共装饰器改动、影响面覆盖已收敛的 60+ 处端点，**需独立评审后再动**。
- 附加考量：该方法体 128 行（1333→1461），是本次清单中体量最大的，改动收益/风险比不划算。

### B3. `api/nlp/nlp_routes.py:1334` `NLPFeedbackRecord.post` —— ✅ 已零漂移收敛（commit `6bfdee4`）

> ⚠️ **取证后修正了原判断**：原表认为「删内层会让外层 500 变 400」，实际相反——
> 内层 try 包住整个方法体（1339→1422）吞掉**一切**异常，外层 `@safe_handle()`（500）**从未生效，是死代码**。
> 因此把外层改为实际兜底者即可，**契约零变化**。

- 原结构：外层 `@safe_handle()`（500，死代码）+ 内层整方法体 try（400 + 固定文案「记录失败」）。
- **决策：收敛** —— 外层改 `@safe_handle(default_status=400, message="记录失败")`，
  删内层 84 行 try 并 dedent；清理仅此一处使用的 `import traceback`；删函数内局部 `from utils.logger import logger`。
- 契约影响：**无**。异常响应同为 400 + 同一文案；`code` 同取 -1。差异仅在日志
  （原打两条含 traceback 的 error → 现由 `safe_handle` 统一 `logger.exception`），非 API 契约。
- **收官证据**：全 `api/` AST 扫描「`@safe_handle` + 整方法体 `except Exception`」死代码双兜底 = **0**，B3 为最后一处。
- 文件混合 EOL（CRLF 1645 / LF 1）原样保留，未规范化；py_compile + pyflakes 全绿。

## 四、零漂移实证（已核查，均通过）

| 核查项 | 结果 |
|---|---|
| `services/` 全目录 `abort(` / `HTTPException` / `raise NotFound\|Forbidden\|BadRequest\|Unauthorized` | **无任何命中** → `safe_handle` 的 HTTP 异常 re-raise 分支在这 26 处实际不触发，与手写 `except Exception` 行为等价 |
| 26 处 try **块内**是否藏 `abort(` / `raise HTTP` | **0 处** |
| 26 处 handler 内是否有 `rollback` / `session.commit` / `.close()` 副作用 | **0 处**（`safe_handle` 不做 rollback，若有则必须排除） |
| `APIResponse.error` 默认 `code=-1` ↔ `safe_handle` 的 `code=getattr(e,"code",-1)` | **一致** |
| 装饰器位置 | 新 `@safe_handle` 一律**最内层**（紧贴 `def`）；`requires_permission` / `cached_api` / `rate_limit` 留外层 → 403 / 429 / 缓存命中路径不经过装饰器 |
| EOL | 待逐文件确认（CRLF 文件禁用文本脚本改写） |

### 残留风险（需知情）
`safe_handle` 内部 `status = getattr(e, "status_code", default_status)`：若抛出的异常对象**自带** `status_code` 属性，
会采用异常值而非 `default_status`，而原代码是固定 500/400。普通 `Exception` 无该属性 → 取 `default_status`；
自定义业务异常若带该属性则行为不同。当前 26 处对应 service 未见抛此类异常，风险低，但属已知差异。
