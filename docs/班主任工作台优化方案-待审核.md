## 1. 现状核心结论

### 1.1 字段命名：契约一致，仅风格不统一 ✅低危

实测 12 个模块的列表/详情接口返回字段（`class_id`、`student_id`、`student_name`、`class_name`、`status` 等）与前端页面消费字段**完全一致**，均为 snake_case，未发现前后端错位。

唯一问题在 `frontend/src/services/api.ts`：
- 方法形参用 camelCase：`classId` / `studentId`（`api.ts:2570,2575`）
- 请求体 / 查询串 / TS 响应类型用 snake_case：`class_id` / `student_id` / `class_name`（`api.ts:5761,1047`）

属「同文件双风格」，建议统一（见 P2），**不涉及线协议字段改名，无契约风险**。

### 1.2 P0 权限词根错配（页面"假可用"） ⛔最高优先级

前端 5 个页面用 `class.view` 门控，但后端对应模块读写要求**完全不同词根**的权限：

| 子页（App.tsx 行） | 前端门控 | 后端实际要求 | 后果 |
|---|---|---|---|
| `/study-groups` (:747) | `class.view` | `study_group.view` / `study_group.edit` | 页面可见，取数/写全部 403 |
| `/mental-health` (:755) | `class.view` | `mental_health.view` / `.edit` | 同上 |
| `/activity` (:765) | `class.view` | `activity.view` / `.edit` | 同上 |
| `/culture` (:773) | `class.view` | `culture.view` / `.edit` | 同上 |
| `/study-guide` (:781) | `class.view` | `study_guide.view` / `.edit` | 同上 |

其余 7 个模块（seating / duty / committee / parent / homework / attendance / teacher-comments）前后端词根一致（均为 `class.*` / `homework.*` / `attendance.*` / `comment.*`），正常。

**根因**：这 5 个模块后端权限名用了「业务专属词根」，而前端路由与班主任角色授权都基于 `class.view`/`class.edit`。导致班主任能进入页面但无法操作。

### 1.3 P1 写路径班级隔离系统性缺失（越权漏洞） ⛔安全

`get_admin_class_ids(admin_id)`（`permission.py:371`）语义：`admin`/`super_admin` 返回 `[]`（调用方视空列表为「无约束，可访问全部」），普通管理员返回其 `AdminClass` 关联班级列表。

**后果**：任何持有对应 `.edit` 权限的班主任，可在 POST 体伪造 `class_id=B` 向他人班级写入考勤/作业/班委/活动/文化等记录（越权写）。读隔离仅 attendance/parent/mental_health/teacher_comment 的 list 部分落地，其余模块读也未隔离。

## 2. 整改方案（分阶段，均待审核）

### P0 — 权限词根统一（修 5 页面假可用）
**目标**：让 `class.view` 班主任能真正使用这 5 个页面。
- 方向 A（**推荐**）：后端把这 5 个模块的 `requires_permission` 由 `study_group.*/mental_health.*/activity.*/culture.*/study_guide.*` 改为 `class.view` / `class.edit`；同步 `seed_rbac`（RBAC 目录 68→需移除/合并这 5 个专属权限）。前端零改动，班主任已具备 `class.view/edit`，无需重新授权。
- 方向 B：前端 5 个页面 `PermissionGuard` 改为 `study_group.view` 等；但班主任需额外被授予这些独立权限，改动与授权面更大。

### P1 — 写路径班级归属校验（修越权）
**目标**：所有写接口校验 `class_id`/`student_id` 归属当前管理员（admin/super_admin 放行）。
- 统一新增 `_ensure_class_access(class_id)` 工具（复用 `get_admin_class_ids` 语义：空列表=全部），在 service 写方法入口调用；优先补齐 12 模块的「创建类」写接口，再补 update/delete。
- 读接口的班级过滤也应统一（当前 8 个模块 list 未隔离）。

### P2 — api.ts 命名风格统一（低风险）
**目标**：`api.ts` 方法形参由 camelCase（`classId`）统一为 snake_case（`class_id`），与线协议一致。纯内部重构，契约不变。

### P3 — 交互与展示优化（待评估）
- 评估 `WorkbenchOverview.tsx`（总览页）当前功能完整度与导航体验。
- 统一 13 个子页的班级切换交互（已通过 `useWorkbenchClass` 共享「当前班级」）。
- 需先读 `WorkbenchOverview.tsx` 与子页导航现状再定范围（本轮尚未深入）。
