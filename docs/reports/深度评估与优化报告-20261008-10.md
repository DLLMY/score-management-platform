# 深度评估与优化报告（第十轮：order_by 排序索引完备性审计 / TEMP B-TREE 残留收口）

- **日期**：2026-10-08
- **范围**：管理平台后端（Flask + SQLAlchemy + SQLite）
- **目标**：在 R7（列级 FULL-SCAN）、R8（`filter+order_by+limit` 复合索引）、R9（MQTT 连接泄漏）收口基础上，继续下沉到**「单个时间戳/枚举列倒序 listing」**这一最大量查询族——即无配对过滤、仅 `SELECT * ... ORDER BY ts DESC [LIMIT N]`（或 `(ts, id)` 复合倒序）的列表/分页查询。这类查询若排序列无单列索引，SQLite 会在内存做**全量排序溢出（USE TEMP B-TREE FOR ORDER BY）**，且 R8 的复合索引只覆盖了 `scores/exams/composite_scores` 三表，其余大表（设备心跳、固件升级、审批、限流记录、心理健康、NLP 纠错……）仍是漏洞。复用「隔离内存引擎 + EXPLAIN QUERY PLAN」实证法，零破坏修复并经全量回归收口。

## 1. 方法论（四步闭环，复用 R7/R8 隔离引擎）

1. **静态扫描**：全仓提取 130+ 处 `.order_by(...)`，归纳 (模型, 排序列, 是否复合, 是否 limit/paginate)，产出 45 条候选（覆盖大表与高频 listing 路径）。
2. **比对真实索引**：从 `db.metadata` 提取每个表的索引首列集合（含模型 `index=True` / `__table_args__` / `UNIQUE` 隐式索引），标记「排序列首列无匹配索引」的候选。
3. **隔离内存引擎实证**：最小 `Flask + sqlite:///:memory:` + `db.create_all()`（**完全不碰开发库**）。对每条候选构造 `SELECT * FROM <tbl> ORDER BY <cols> DESC LIMIT 50`，跑 `EXPLAIN QUERY PLAN`，捕捉 `USE TEMP B-TREE FOR ORDER BY`。
4. **修复 + 实证反证**：在模型层补缺失索引（单列 `db.Index` 或复合），**再次隔离引擎复跑 EXPLAIN 反证 TEMP B-TREE 消失**，再落地源码。同时把新索引纳入 `scripts/create_indexes.py` 清单（启动自举 + `verify` 闸门），并对现有 dev 库执行 `--create` 自举，确保「模型 / 现有库 / 校验闸门」三处零漂移。

## 6. 结论与运维建议

1. **R10 收口**：补齐 18 条缺失排序索引，将全仓 `order_by` 的 TEMP B-TREE 从 28 → 8（8 处为有意跳过的微型配置表）。最大受益为**持续高写入/大表**（`device_heartbeats`、`device_firmware_updates`、`rate_limit_records`、`approvals`），其倒序 listing 不再做内存全排序。
