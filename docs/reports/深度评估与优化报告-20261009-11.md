# 深度评估与优化报告 · 第十一轮（R11）：GROUP BY / 聚合索引完备性审计

> 日期：2026-10-09
> 关联：R7（列级 FULL-SCAN）、R8（filter+order+limit 复合）、R9（MQTT 连接泄漏）、R10（order_by 单列排序）
> 方法：复用隔离内存引擎 + `EXPLAIN QUERY PLAN`，完全不触碰开发库。

## 1. 摘要

本轮在 R7–R10 已铺满「列级扫描 / 过滤+排序复合 / 单列排序」索引的基础上，继续下沉到**聚合查询族**——
`GROUP BY` / `COUNT` / `SUM`。SQLite 对无索引支撑的 `GROUP BY` 与 `ORDER BY` 同理，使用
`USE TEMP B-TREE FOR GROUP BY` 在内存中做排序溢出；当分组列无索引时还会退化为全表 `SCAN`。

**核心结论**：

- **PART A（索引一致性审计）**：双处定义（模型 `__table_args__`/内联 `index=True` 经 `create_all` + `scripts/create_indexes.py` 清单经启动自举）**一致、零异构漂移、无安全可裁冗余**——16 处跨源同列定义属有意的「新建库 vs 旧库回填」双轨，须保留。此前怀疑 R10 引入「同名重复索引」经核验为解析器把 `__table_args__` 内的 `db.Index` 计了两次的**伪影**，非真问题。
- **PART B（GROUP BY 审计）**：静态扫描 `.group_by`/`func.count/sum` 共 **98 处**，归纳 **13 个聚合候选**；隔离引擎 `EXPLAIN` 实证初始 **11 已覆盖 / 2 处 TEMP B-TREE**：
  - `operation_log.operation_type` — `GROUP BY operation_type` 排序溢出，且清单有 `ix_log_operation_type` 但**模型缺失**（双处漂移，测试/新建库缺索引）。
  - `security_audits.ip_address` — `GROUP BY ip_address`（HAVING 阈值）排序溢出，两处定义都缺。
  - 2 处 `func.date(created_at)` 仍 TEMP B-TREE，但已走 `created_at` 覆盖索引且实际查询均带时间范围 `WHERE` → 排序规模受范围约束；优化需新增生成列 + 改写 schema 并给最热写入表 `score_record` 增加写惩罚，**判为低优先、超出本轮范围**。
- **修复**：补 2 个索引（零 API 契约变更、零新依赖），重跑审计 → **需补候选 = 0**。

## 2. 方法论（四步闭环，复用 R7/R8/R10 隔离引擎）

1. **静态扫描**：全仓 `grep .group_by` / `func.count` / `func.sum` → 98 处，归纳 13 候选 `(模型类, 聚合列, 是否 date() 包裹)`。
2. **索引双处提取**：AST 解析 `models/*.py`（内联 `index=True` + `__table_args__` 的 `db.Index`）与 `scripts/create_indexes.py::get_all_indexes`（清单），分别建立「表 → 索引列集合」。
3. **实证**：隔离 `Flask(__name__)` + `sqlite:///:memory:` + `db.init_app` + `db.create_all()`（`FLASK_LIGHTWEIGHT=true` 跳过 MQTT/调度器远程阻塞），对每候选构造 `SELECT <col>, COUNT(*) FROM <table> GROUP BY <col>` 跑 `EXPLAIN QUERY PLAN`，捕捉 `USE TEMP B-TREE FOR GROUP BY` / `SCAN`。
4. **修复 + 反证**：模型层补索引 → 复跑 `EXPLAIN` 确认 TEMP B-TREE 消失 → 同步双处定义 → 现有库自举 `--create` / `reconcile` 核验。

### 3.2 发现

- **异构漂移（同索引名、不同列）：0 处** —— 双处定义完全对齐，无不一致。
- **真冗余（同列多索引名）：0 处** —— 此前疑似的「同名重复」为解析器把 `__table_args__` 内的 `db.Index` 计两遍的伪影（已核实：R10 目标列均无 `index=True`，显式 `db.Index` 为唯一定义）。
- **结论**：索引双处定义健康，本轮**不做任何裁剪**（避免破坏双轨补索引机制）。

## 6. 结论与遗留

- **R11 收口**：GROUP BY / 聚合族索引完备性闭环——2 处实测 TEMP B-TREE 排序溢出已消除，双处索引定义零漂移；全仓聚合查询不再因分组列缺索引而内存排序溢出。
- **低优先遗留（超出本轮）**：`func.date(created_at)` 两类日期聚合仍走 TEMP B-TREE，但已用 `created_at` 覆盖索引做扫描、且实际查询带时间范围 `WHERE`，排序规模受范围约束，性能可接受；若要彻底消除需为 `score_record` / `operation_log` 新增 `created_date` 生成列 + 索引，属 schema 变更且给最热写入表增写惩罚，**建议专项评估后再定**，本轮不强制。
- **方法论沉淀**：R7–R11 已对「列级扫描 / 过滤+排序复合 / 单列排序 / 分组聚合」四类查询族完成索引完备性审计，SQLite 查询规划器自动选新索引 → 运行后端免重启受益。
