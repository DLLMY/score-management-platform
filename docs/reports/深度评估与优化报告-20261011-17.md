# 深度评估与优化报告 - R17：course-schedules / activity 残留 N+1 根因定位与修复（2026-10-11）

## 一、评估方法

R16 端点级画像暴露 `/api/course-schedules`（24 SQL）与 `/api/activity`（18 SQL）疑似残留 N+1（扣除每端点 ~4–6 条 RBAC 鉴权开销后仍显著偏高）。本次按"评估阶段不改主代码"纪律，复用 conftest 的测试 app 构建（`:memory:` + `StaticPool` + 全量命名空间注册）+ 自建中等业务数据集，**挂 SQLAlchemy 事件监听器按归一化 SQL 计数并捕获调用栈**，定位 N+1 源头（硬证据），修复留待回归闸门收口后再做。

## 二、诊断证据（实测，修复前冷请求）

| 端点 | HTTP | TOTAL_SQL | 主导重复查询 | 调用栈定位 | 命中次数 |
|---|---|---|---|---|---|
| `/api/course-schedules` | 200 | **29** | `SELECT class_periods … WHERE period_number=?` | `course_schedule_service.py:get_period_info` | **20**（=20 条排班） |
| `/api/activity` | 200 | **11** | `SELECT class_info … WHERE id=?` | `entity_names.py:_lookup`（即 `names.klass`） | **5**（=5 个 distinct 班级） |

> 口径说明：R16 报告记的 24/18 是含鉴权的粗略计数；R17 用调用栈精确归一化后实测修复前为 **29/11**，两者一致（鉴权基数随数据集略变），本报告以 R17 实测为准。

## 三、根因分析

两个端点 N+1 同源但机制不同：

1. **course-schedules —— `get_period_info` 逐排班查节次**：序列化循环 `_schedule_dict(schedule)` 对每条排班调 `get_period_info(period_number)`，该方法 `ClassPeriod.query.filter_by(period_number=...).first()` 逐条查库。列表 20 条排班 → 20 次 `class_periods` 查询。class_info / subject 已 `joinedload` 预载不重复查，唯独节次信息走逐行查询。

2. **activity —— `names.klass` 逐班查**：`_build_activity_response` 对每个活动调 `names.klass(a.class_id)`。`entity_names` 的请求级 `flask.g` 缓存按 id 去重（同 id 只查 1 次），但 **distinct 班级数 = 查询数**；15 活动跨 5 班 → 5 次 `class_info` 查询。R14 已建 `prefetch_classes` 批量设施，但 `list_activities` 未调用。

两者均**零契约变更、低风险**，复用已有 `entity_names` 的 flask.g 缓存 / 预取范式即可消除。

## 四、修复方案

| 端点 | 改动 | 机制 |
|---|---|---|
| course-schedules | `course_schedule_service.py::get_period_info` 加**请求级（flask.g）缓存**：首次调用一次性 `ClassPeriod.query.all()` 预载全部节次（1 查询），后续按 `period_number` 命中缓存 | 20 → 1 |
| activity | `activity_service.py::list_activities` 序列化前调 `names.prefetch_classes([a.class_id …])`（R14 已建设施） | 5 → 1 |

覆盖 `get_period_info` 的全部调用点（列表 / 按班级 / 导出 / 详情），无逻辑变更。

## 七、延伸发现（R18 评估预备）

R17 静态扫描发现 `entity_names` 的 `names.xxx(id)` 解析器存在系统性 N+1 隐患：请求内按 id 去重缓存，但 **distinct id 数 = 查询数**，且**仅 `prefetch_students` / `prefetch_classes`，缺 `prefetch_subjects`**。约 15 个服务模块 ~30 处在序列化循环逐条调 `names.student / klass / subject`，均为同源 N+1（逐学生类最危险：seating / attendance / study_group / committee / duty / homework / parent 等）。R18 拟按"先 A（逐学生）后 B/C（逐班级 / subject 缺 prefetch）"分批实施，每批自带全量回归闸门。详见 R18 评估结论（待整理成正式报告）。
