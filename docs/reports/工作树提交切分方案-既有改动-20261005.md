# 工作树提交切分方案（既有累积改动）

> 生成日期：2026-10-05
> 背景：用户选择「先梳理既有再提」。经核验，工作树实际改动规模远超此前摘要记录的 7 个文件，
> 实为 **38 个文件**（26 已修改 + 12 未跟踪），其中 25 个为会话之前累积的未提交工作，13 个为本会话产生。
> 本方案只梳理「既有 25 个文件」的提交切分；本会话 13 个文件保持未提交，按此前约定另议。

## 一、结论：批次级切分不可行 → 采用「按路径前缀的领域/分层切分」

- **leave（请假）功能横跨「既有组」与「本会话组」两组文件**（见下表），无法按逻辑功能边界还原为独立批次。
- 单个文件内也常聚合多主题（如 `app/service_init.py` 同时含 celery worker 隔离 + MQTT 缺失兜底 + 请假调度接线；`services/phonebox_policy.py` 仅扩展 `set_policy` 但整文件被 EOL 翻转为 CRLF）。
- 因此放弃 hunk 级 `git add -p`（数百 hunk 成本高、易错），改用**文件级领域分桶**：文件互斥、`git add <路径>` 精确落地、每个 commit 语义自洽。

## 四、执行顺序与「为何不可颠倒」

1. **C1 → C3 → C2 → C4 → C5 → C6**
   - C1（celery 修复）独立低风险，最先落地，尽早解锁 worker 任务执行。
   - C3（service_init）依赖 celery 概念但文件独立，紧接 C1 之后。
   - **C2（leave 后端）必须在 C4（leave 前端）之前**：后端先注册 `ns_leave` 路由 + 模型字段，前端 `LeaveManagement` 路由与 `api.leave` 调用才有对应端点（否则前端空闲引用未注册路由）。
   - C5（测试格式化）任意位置可插入，建议放 C4 之后。
   - C6（脚本/文档）最后，无依赖。
2. **请假功能完整闭环依赖说明**：本方案 C2+C4 仅覆盖既有侧的 leave 支撑；**完整功能还需本会话侧的 `leave_routes.py`/`leave_service.py`/`test_leave_service.py`/`LeaveManagement.tsx`**。若希望请假功能作为一个原子特性提交，应把本会话这 4 个文件并入 C2/C4 对应的提交（见第五节决策点 2）。

## 六、回滚方案
- 每次提交后 `git status --porcelain -uall | wc -l` 应递减，与方案计数一致。
- 未 push 前发现错提：`git reset --soft HEAD~1` 撤销最近提交（保留改动于暂存区），重新分桶。
- 已 push 后：`git revert <commit>` 生成反提交，禁止 `git push --force`。
- 收尾期望：`git status --porcelain -uall` 仅剩本会话 13 文件 + NON-COMMIT 产物（后者应已被 .gitignore 屏蔽）。
