# 深度评估与优化报告（2026-10-07 第四轮）

> 本轮为"隐蔽性能债"挖掘序列的第四轮。前三轮已收口：① 5 个缺失索引 + `warning_service.evaluate_risk` N+1（commit `35847b2`）；② 关系懒加载 N+1（4 处 `lazy="selectin"`，commit `cb39e31`，同批修复 MQTT 自循环）；③ 循环体内显式 DB 查询 N+1（3 处 `IN` 批量，commit `fc5d214`）。
> 前三轮聚焦"N+1"（逐元素查库）。本轮转向一个**相邻却被忽略的维度：同一函数内对同一张表反复发起独立聚合查询（尤其是 `COUNT` + `ALL` 配对、或多字段各自 `COUNT`）**——这些查询彼此结果可复用，却每次都打到 DB，属于"冗余查询"。

---

## 1. 评估方法

- 复用静态扫描思路，编写 `scan_round4.py` 遍历 `services/ api/ models/ utils/ app/` 共 **285 个 `.py`**（排除 `tests/ .venv/ venv/ migrations/`），检测两类信号：
  - **DUP_EXEC**：同一查询变量被 ≥2 次执行方法调用（`.all()/.first()/.count()/.paginate()` 等）；
  - **PY_GROUP**：`.all()` 结果在循环内按属性键聚合（`Counter/defaultdict/groupby/分组 sum`）。
- 对 `DUP_EXEC` 候选人工甄别：绝大多数为 `query -> all,paginate` 的**条件分支互斥**（分页走 paginate、非分页走 all，二者不会同执行）——判为误报排除。
- 真实信号落在 `query -> count,all`（同一张表先 `COUNT` 再 `ALL`，或多次不同过滤的 `COUNT`）——这是可合并的冗余查询。
- 辅以定向 `grep` 枚举全仓 `.count()`（79 处），逐处确认是否配对 `ALL` 或同表多 `COUNT`；并单独用 `scan_rel_nplus1.py` 扫描循环体内懒关系属性访问（结果 0 处：关系 N+1 已被第二轮 `selectin` + 列表端点 `@cached_api` 兜底，无新增）。

## 3. 根因分析

这些统计/概览端点为每个指标单独发一条聚合 SQL（`COUNT(*)`、`func.avg`、`filter().count()`、`filter().all()`）。它们查询的是**同一张表、同一份数据集**，差异仅在过滤条件。每次聚合都是一次独立的 DB 往返 + 一次独立的全表（或索引）扫描。

以 `get_device_advanced_stats_view` 为例：设备相关 5 条查询 + 告警 2 条查询 = **7 次 DB 往返**。但设备表是**有界表**（教室手机箱/门锁等，通常数百至数千行），一次性 `Device.query.all()` 载入内存后，total/error/online/signal 全部可由内存归类得到——**7 次往返 → 2 次**（`Device.all()` + `Alert.all()`，`Heartbeat` 仍走 COUNT 因需时间窗过滤）。

> 注：本优化成立的前提是**被查询表有界**。设备/分组/告警均为有界实体，载入内存成本可忽略，且这些端点多数已 `@cached_api` 缓存，优化主要降低缓存未命中/首算时的 DB 压力。

## 4. 修复方案（5 处，均零 API 契约变更）

### 4.1 `get_device_stats_view`（3 次 → 1 次）
```python
# 一次性加载全部设备，避免 total/error/online 各自 COUNT（3 次查询 -> 1 次）
_devices = Device.query.all()
total = len(_devices)
error = sum(1 for d in _devices if d.status == "error")
online_cutoff = datetime.now() - timedelta(seconds=60)
online = sum(1 for d in _devices if d.last_heartbeat is not None and d.last_heartbeat >= online_cutoff)
offline = max(0, total - online - error)
```
- 关键安全点：SQL 中 `last_heartbeat >= cutoff` 对 NULL 不自匹配；Python 端补 `is not None` 守卫，精确保留 NULL 语义（否则 `None >= cutoff` 抛 `TypeError`）。

### 4.2 `get_device_advanced_stats_view`（7 次 → 2~3 次）
```python
# 一次性加载全部设备：total/error/online/signal 全部由内存归类（5 次查询 -> 1 次）
_devices = Device.query.all()
total = len(_devices)
error = sum(1 for d in _devices if d.status == "error")
online_cutoff = datetime.now() - timedelta(seconds=60)
online = sum(1 for d in _devices if d.last_heartbeat is not None and d.last_heartbeat >= online_cutoff)
offline = total - online - error
_signal_devices = [d for d in _devices if d.wifi_signal is not None]
avg_signal = (
    round(sum(d.wifi_signal for d in _signal_devices) / len(_signal_devices), 1)
    if _signal_devices else None
)
# 设备相关告警一次性加载（2 次 COUNT -> 1 次）
_device_alerts = Alert.query.filter_by(source="device", is_resolved=False).all()
alert_count = len(_device_alerts)
critical_alerts = sum(1 for a in _device_alerts if a.severity == "critical")
```
- `avg_signal` 由原 `func.avg(wifi_signal) WHERE wifi_signal IS NOT NULL` 改为对同集合（非 NULL）的 Python 均值，结果集与数值一致（返回均 round 到 1 位）。
- `today_heartbeats` 保留 `COUNT`（需 `received_at >= 今日0点` 时间窗，内存归类无收益且需全表载入心跳表，反而更差）。

### 4.3 `get_dashboard_data`（2 次 → 1 次）
```python
# 一次性加载设备，total/online 由内存归类（COUNT + ALL -> 1 次查询）
_devices = Device.query.all()
total_devices = len(_devices) or 0
online_devices = sum(1 for d in _devices if d.is_online) or 0
```

### 4.4 `device_group_routes.get`（3 次 → 2 次）
```python
# 一次性加载分组：total/active 由内存归类（2 次 COUNT + ALL -> 1 次查询）
groups = DeviceGroup.query.all()
total_groups = len(groups)
active_groups = sum(1 for g in groups if g.is_active)
total_mappings = DeviceGroupMapping.query.count()   # 另一张表，保留
```

### 4.5 `get_device_status_summary`（2 次 → 1 次）
```python
# 一次性加载设备，total/online 由内存归类（COUNT + ALL -> 1 次查询）
devices = Device.query.all()
total = len(devices)
online = sum(1 for d in devices if d.is_online)
```

- 全部改动**仅替换查询组织方式**，响应 JSON 的 key 与数值与原实现逐字节等价（已通过定向测试 44 passed 验证）。
- `device_query_service.py` 移除已不再使用的 `from sqlalchemy import func` 导入（ruff F401 核查通过）。
