# 深度评估与优化报告 - 2026-10-10（R15：/api/dashboard success_rate=0% 排查与修复）

## 1. 背景与目标

R13/R14 性能基线刷新与 N+1 修复期间，压测脚本 `scripts/run_performance_test.py` 报告 `/api/dashboard` **success_rate=0%**。R14 报告 §6 遗留③ 初步将其归类为「鉴权/数据依赖问题（非性能）」，结论**不准确**——本轮（R15）目标：

1. **确凿定位** 0% 根因（鉴权失效？数据依赖异常？还是端点本身问题？）；
2. **低风险修复** 真实缺陷（仅改压测脚本 + 后端一处字段缺失，不动 API 契约）；
3. **重跑压测验证** dashboard 成功率恢复，并**零回归**（全量 2318/0/0/7）。

## 2. 排查过程

1. 定位路由：`api/analytics/dashboard_routes.py` 仅注册两个 GET 资源 `/data`（DashboardData）与 `/stats`（DashboardStats），命名空间 `ns_dashboard` 在 `app/api_versioning.py:235` 以 namespace 名 `dashboard` 为前缀 → 实际路径前缀 `/api/dashboard`。
2. 核对压测脚本：`scripts/run_performance_test.py` 的 endpoints 列表写的是 `{"endpoint": "/api/dashboard", ...}`（**无子路径**）——与已注册资源不匹配。
3. 核对前端真实调用：`frontend` 中 `api.ts:3961`、`cacheWarmupService.ts:22` 均正确请求 `/api/dashboard/data`，无根路由依赖。
4. 核对缓存降级：`services/redis_cache_service.py` 的 `get()/set()` 在 Redis 不可用时优雅降级（返回 None/False），不会抛异常 —— 排除「缓存未就绪导致 500」假设。
5. 实测判定：编写自删诊断脚本（合法 admin token vs 无 token），实测三种请求：

| 请求路径 | 带合法 admin token | 无 token |
|----------|-------------------|----------|
| `/api/dashboard`（压测实际请求）| **404**（资源未注册）| 404 |
| `/api/dashboard/data`（前端真实调用）| **200**，返回完整 JSON（total_users / total_admins / top_users …）| 401（鉴权正常生效）|
| `/api/dashboard/stats` | **200** | 401 |

## 3. 诊断发现

### 3.1 主因：压测脚本端点路径写错（非后端鉴权/数据依赖）

`run_performance_test.py:135` 写 `/api/dashboard`（无子路径），而该路径下**没有注册任何 GET 资源**（仅 `/data`、`/stats`）→ 50 次请求全部命中 **404** → `success_rate=0%`。后端 `/api/dashboard/data` 在合法 token 下**正常返回 200 且数据结构完整**，鉴权也正确（缺 token 返回 401）。**R14 报告 §6 遗留③ 的「鉴权/数据依赖」归类须纠正为「压测脚本端点路径 bug」。**

### 3.2 附带发现（指标失真，非 0% 主因）：`positive_ratio` 字段缺失

- `services/dashboard_service.py::get_dashboard_data()`（L62-81）返回的 dict **不含 `positive_ratio` 字段**；
- `dashboard_routes.py:38` 用 `data.get("positive_ratio", 0)` 兜底 → `/api/dashboard/stats` 的 `positive_ratio` 永远为 **0**（不报错，但指标失真）。

## 4. 修复落地（零 API 契约变更、向后兼容）

两个目标文件经字节级检测均为**纯 CRLF**，`Edit` 直改有混合行尾风险，改用字节级替换脚本严格守恒 CRLF（Python bytes 注释用 ASCII 规避编码限制）。

### 4.1 `services/dashboard_service.py`（补 `positive_ratio`）

在 `get_dashboard_data()` 计算 `weekly_records`（近7天 `ScoreRecord` 总数）后，新增：

```python
# positive ratio over last 7 days (score_change>0 / total)
positive_records = (
    ScoreRecord.query.filter(
        ScoreRecord.created_at >= last_7_days, ScoreRecord.score_change > 0
    ).count()
    or 0
)
positive_ratio = (
    round(positive_records / weekly_records * 100, 1) if weekly_records > 0 else 0
)
```

并在返回 dict 中加入 `"positive_ratio": positive_ratio`（`weekly_records` 之后）。口径：**近7天正向评分（score_change>0）记录数 / 近7天总记录数 × 100**，保留 1 位小数；分母为零时取 0。`ScoreRecord.score_change` 为可正可负 Float，`ScoreRule` 无正/负标记 → 取该口径合理且不引入新依赖。

### 4.2 `scripts/run_performance_test.py`（修正压测端点）

将 `{"endpoint": "/api/dashboard", "method": "GET", "iterations": 50}` 替换为：

```python
{"endpoint": "/api/dashboard/data", "method": "GET", "iterations": 50},
{"endpoint": "/api/dashboard/stats", "method": "GET", "iterations": 50},
```

与前端真实调用对齐，并补测 `/stats`（覆盖 positive_ratio 修复）。

### 4.3 行尾守恒验证

字节级替换后检测：`dashboard_service.py` 与 `run_performance_test.py` 均 `lf_only=0, crlf>0` → **CRLF 严格守恒，无 MIX**。`py_compile` 两文件全过。
