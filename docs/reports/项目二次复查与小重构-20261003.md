## 一、首轮修复的二次核验（缓存键用户维度）

上一轮把 `cached_api` 的缓存键并入 `user_id:role`（消除跨用户缓存越权），本轮复核其完整性与兼容性：

| 核查项 | 结论 |
|---|---|
| `_cache_user_dimension()` 三档降级 | ✅ `g.current_user`（requires_permission/role 已挂载）→ 直接解码 `Authorization: Bearer` JWT（`utils.security.decode_token`，与装饰器顺序无关）→ `anon` |
| 键格式兼容性 | ✅ 新键仍为 `api:{path}:{hash}`（hash 内部并入 `uid:role`）；`invalidate_cache` 按 `api:{path}:*` 前缀失效 → **前缀不变，失效逻辑完全兼容** |
| JWT 字段约定 | ✅ `decode_token` 返回裸 payload，`sub` 为用户 id（项目令牌生成一致）；即使 `role` 缺失，`user_id` 单列已杜绝跨用户共享（关键修复点） |
| 回归佐证 | ✅ 首轮全量回归 junitxml 权威计数 `2228 = 2221 passed / 0 failed / 0 errored / 7 skipped` |

**结论：首轮高危安全修复经二次核验，逻辑闭环、零破坏。**

## 二、本轮落地的小范围重构：删除缓存中间件死代码

`apps/backend/utils/api_cache_middleware.py` 中存在**全仓零引用**的死代码（grep 证实：所有外部导入仅用 `cached_api` / `invalidate_cache` / `setup_cache_middleware`；`_system_part1.py:316` 的 `cache_stats` 是局部变量，非本模块符号）：

- `class CacheStatistics` 及其 `record_hit/miss/bypass/get_stats/reset` 方法 —— 从未被调用；
- 模块级 `cache_stats = CacheStatistics()` 实例 —— 从未被引用；
- `setup_cache_middleware` 内空的 `@app.before_request def before_request_cache()` —— 函数体仅注释占位，无功能。

**改动**：删除上述三类死代码，保留功能性 `@app.after_request def after_request_cache()`（为未命中缓存的响应补 `X-Cache: BYPASS` 头，被测试与监控依赖）。

**性质**：纯删除无引用代码，**零行为变化**，符合项目「技术债清零」一贯纪律，降低维护认知负荷。
