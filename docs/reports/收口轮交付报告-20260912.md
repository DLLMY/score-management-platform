## #167 补齐差异 #4 前端 UI

### 计划外的重要补齐

原计划只补**阶段 3（密钥 UI）**。实施中发现 **阶段 1（白名单开关）前端也完全没有入口** —— 后端 `system_routes.py:212` 已暴露 `device_whitelist_enabled`，但前端零引用。

只补阶段 3 会导致：「能签发密钥，但开不了白名单」的半残状态。故**一并补齐阶段 1**。

### 设计决策

**密钥入口位置**：放在**设备设置弹窗内**，而非表格操作列。

理由：操作列已 260px 宽、6 个按钮（开A箱/开B箱/详情/绑定/设置/删除），再加会溢出；且密钥本质是**设备级配置**，与「设备名称/告警/心跳超时」同属一类，放设置弹窗语义更贴。

**安全语义显式告知**（UI 文案已体现）：
- 密钥明文**仅签发那一次**可见，后端/前端此后均不回显
- **吊销 ≠ 封禁**：吊销后设备回到「未发放密钥 = 免验签」状态，仍可上报
- 要真正拒绝未登记设备，须开**白名单开关**（阶段 1）

## 本轮沉淀的可复用教训

1. **grep 被 SIGTERM 截断 = 假「0 引用」**。删除/归档前必须用 `Grep` 工具（ripgrep）二次确认 —— 本轮若信了上轮结论直接删，根 `README.md` 会留永久断链。
2. **同名类型/同名对象多处定义是本仓常态**。改前先 grep 全仓定位「真实类型源」；`TS2353`/`TS2339` 基本就是这个原因。
3. **行尾守恒断言须按「多数风格」写**：先同时看 `crlf` 与 `bare` 计数判风格，再断言该风格计数不变。
