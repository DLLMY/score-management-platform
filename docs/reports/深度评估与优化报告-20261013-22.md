# 深度评估与优化报告 — R22（关系懒加载维度 + api 层 helper-delegated N+1）

- **日期**：2026-10-13
- **战役**：零回归性能修复（R7–R22 持续），铁律：不自动 commit、复用成熟设施、全量回归=重构完成、字节级 EOL 守恒、双处索引定义。
- **目标维度（双维）**：
  1. **关系懒加载 N+1**：全模型无显式 `lazy=` 定义的假设被证伪——实测 12 关系 + 5 backref 中仅 1 个走默认 `lazy="select"`，该维度经评估**基本闭合**；
  2. **R20 扫描盲区补扫**：R20/R21 的直接/委托型扫描只覆盖 `services/`，`api/` 路由层从未扫过——本轮补扫并收口 **3 处真实 N+1 + 1 处存量崩溃 bug**。

## 1. 维度一：关系懒加载评估（R22-0a）

AST 收集模型层全部 `db.relationship`（12 属性 + 5 backref），扫描 services/api 循环内关系访问（28 候选）。

**结论：关系维度基本闭合，绝大多数候选为误报**——

- 模型层已普遍声明 `lazy="selectin"`（加载父对象后 1 次 `IN` 批量拉取，非逐条）：`Device.class_info/admin`、`Score.student/admin/subject_rel`、`ScoreRecord.user/rule`、`ScoreRule.category`、`CourseSchedule.subject/class_info`、`SubjectClass.*`、`AdminClass.admin/class_info`、`Exam.class_info/admin`、`Notification/Approval.user`、`SubAccount.parent_admin`、`AdminRole.admin`、`PhoneBoxPolicy.class_info`、`ScoreArchiveRecord.*`；
- 2 处 `student` 候选为 `names.student(...)`（entity_names 助手方法）误匹配；
- 唯一默认 `lazy="select"` 的关系是 `SeatingChart.seats`（一对多），但其唯一访问点 `seating_service._build_chart_response` 走的是"直接 `filter_by(chart_id=...)` 查询 + `prefetch_students`"，本就不是 N+1；
- `_devices_part1` 3 处显式 `joinedload` 是 selectin 之前的历史写法，对过滤候选集反而更优（单 JOIN vs 3 查询），保留。

## 2. 维度二：api 层补扫（R20 盲区，R22-0b）

R20 的直接模式 + R21 的委托模式都只扫了 `services/`。本轮对 `api/**/*.py` 补扫两类模式：

**2a. 循环内裸查询（直接模式）**：12 候选 → 鉴别：
- 写路径 5 处（`_course_schedule_part2.post`、`_system_part1.post`×2、`_users_part1/2.post`）：事务内逐条处理，不动；
- 误报 3 处（`str.join` / `os.path.join` 命中链式方法名启发式）；
- RBAC 每请求开销 3 处（`check_admin_permission` / `get_inherited_permissions` / `AdminRoleList.get`）：循环体是**单个管理员的 role_codes**（通常 1–3 个）与小型配置表，不随数据量缩放，且权限缓存属安全敏感区，按低风险铁律不动（观察项，见 §5）；
- **真实 N+1 1 处**：`DeviceGroupOptions.get` 逐组 `count()`。

**2b. 循环内 `get_by_id` 委托型**（R21 模式应用到 api 层，`get_by_id = Model.query.get` 无缓存）：4 候选 → 2 真实（`DeviceGroups.get` 逐映射、`AdminClasses.get` 逐链接），2 误报（非循环的单对象查询）。

## 3. 修复方案（R22-1）

三处均复用同文件/同域已验证的批量模式（R13/R21 同款），零契约变更：

| # | 位置 | 旧逻辑（N+1） | 新逻辑 |
|---|---|---|---|
| 1 | `api/devices/device_group_routes.py::DeviceGroupOptions.get` | 每组 1 次 `DeviceGroupMapping.count()` → **1+G** | 循环前 `with_entities(group_id, count).group_by` 一次聚合 → **2**（列表+计数） |
| 2 | `api/devices/device_group_routes.py::DeviceGroups.get` | 每映射 1 次 `get_by_id(DeviceGroup, ...)` → **2+M** | 循环前 `DeviceGroup.id.in_(group_ids)` 一次 IN + 字典查找 → **2**（mappings+IN） |
| 3 | `api/academics/admin_classes_routes.py::AdminClasses.get` | 每链接 1 次 `get_by_id(ClassInfo, ...)` → **2+L** | 改用模型层 selectin 关系 `link.class_info`（1 次 IN 自动批量）→ **2**（links+IN）；同步清理失效 import |

**drive-by 存量崩溃 bug 修复**：`DeviceGroups.get` 的 `mapping.created_at` → `mapping.added_at`。`DeviceGroupMapping` 模型只有 `added_at` 列（无 `created_at`），该行在 HEAD 即存在——**任何有分组映射的设备调 `GET /api/device-group/device/<id>/groups` 必 500**（存量未测，本次实证 harness 首次触达）。与 R20 顺带修复 3 处 `dict()` 崩溃 bug 同性质。

EOL 守恒：`device_group_routes.py` 保持纯 CRLF（388 行）、`admin_classes_routes.py` 保持纯 CRLF（147 行）。

## 6. 观察项（不修，记录在案）

- **RBAC 每请求查询开销**：`requires_permission → check_admin_permission` 单次请求约 5–6 次 SELECT（admin ×2 + admin_roles + role_permission_mappings ×2 + role_hierarchies，超级管理员角色可短路）。属**恒定开销不随数据量缩放**，且权限结果缓存属安全敏感区（缓存键错误=权限 bypass），按低风险铁律本轮不动；如后续要做，须走"请求级 flask.g 缓存 + 权限变更主动失效"方案并过安全评审。
