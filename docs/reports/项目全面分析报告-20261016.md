## 二、技术栈与架构

### 后端（apps/backend）
- **框架**：Flask-RESTful（flask_restx）+ SQLAlchemy + SQLite（WAL 模式）+ Redis + Celery + MQTT/EMQX
- **架构铁律（已固化）**：
  - 路由唯一源 `app/api_versioning.py::register_v1_routes`；API 信封 `{success, code, data}`
  - 双 JWT 隔离（管理端/设备端）；RBAC 68 条权限一致性闸门（`verify_rbac_consistency.py`）
  - 写路径 `db_session_scope(detach=False)` 事务管控；错误处理统一 `@safe_handle` 装饰器
  - 索引双处定义（模型层 + `scripts/create_indexes.py` 启动自举）
- **端点域分布**：algorithm 62 / system 61 / devices 53 / scores 53 / academics 51 / nlp 48 / class_management 44 / data 29 / users 28 / monitoring 27 / 其他 36

### 前端（apps/frontend）
- **栈**：React 18 + Vite 6 + TS 5.9 严格档 + Zustand + antd5 + tailwind
- **25 个业务域**：dashboard / classManagement / scoreEntry 类 / deviceManagement / firmwareManagement / algorithm-analysis / nlp-management / attendanceManage / homeworkCheck / mentalHealth / approvals / examManagement / courseSchedule / activityManage / cultureBoard / committeeList / dutyRoster / classCompare / diagnostics / phonebox 相关等
- **规范**：全 LF、prettier 100 列、导入走 barrel、禁 any、四闸门（tsc/eslint/prettier/vitest）

### IoT（ESP32）
- **链路**：设备 register/heartbeat → EMQX → Flask 协商 → `phonebox/ota/{id}` 固件推送
- phonebox 无缝 OTA 已全链路闭环（HMAC 验签 / 断点续传 / MD5 / Boot 回滚）
- `device_type` 维度已闭合（phonebox / doorlock 同构）

### 🟡 真实风险项（按严重度排序）

| # | 风险 | 现状 | 影响 | 建议 |
|---|---|---|---|---|
| 1 | **MQTT broker 连公共 hivemq** | R9 遗留：切回 EMQX Cloud 缺主机+账号密码，后端 `mqtt_config` 仍指向 broker.hivemq.com | **生产可用性/安全风险**（公共 broker 无 SLA、设备凭证裸露风险） | 补齐凭据即切（管理端改配置重启+设备端同步），改动小 |
| 2 | **SQLite 单库天花板** | WAL 已开、读密集 1.88x；写并发受文件锁限制 | 当前 40 学生量级无感；规模化（多学校/高并发写）受限 | 维持；触发条件=并发写瓶颈出现，届时迁移 PostgreSQL（模型层已 SQLAlchemy 抽象，迁移成本可控） |
| 3 | **doorlock C2 OTA 硬件阻塞** | 后端维度就绪，卡 ESP32 固件（缺 `Update.h`、不订阅 ota 主题） | 门锁设备无法 OTA | 与硬件团队对齐固件路线；后端零改动待命 |
| 4 | **前端体量腐化风险** | 436 页面文件 / 25 域，单页最大域待监控 | 长期维护成本上升 | 已有 barrel/死代码 SOP 防腐化；建议加"单文件行数 ratchet"监控 |

| 6 | **依赖更新停滞** | Flask/React 生态依赖静态维护 | 安全漏洞累积 | 引入 Dependabot/周期 `npm audit` + `pip audit` |

## 五、后续开发方向与优先级建议

### P0 — 风险处置（本周可启动，低改动高价值）
1. **MQTT broker 切换 EMQX Cloud**：向用户/运维索取凭据 → 管理端配置重启 + 设备端同步 → 联调验证。消除公共 broker 依赖。
2. **依赖安全基线**：`npm audit` / `pip-audit` 全量扫一遍，出补丁清单（预计小版本升级为主）。

### P1 — 业务就绪项（等外部条件或排期）
3. **doorlock C2 联调**：硬件固件到位即启动，后端零改动。
4. **可观测性看板**：`/metrics` 已暴露，加 Grafana 看板 + 告警规则（错误率/OTA 成功率/设备在线率）——`grafana/`、`prometheus/` 目录已有骨架。
5. **生产运维 Runbook 补全**：故障定位 SOP + 备份恢复演练（`docs/生产运维Runbook-20261003.md` 已有初版，需演练验证）。

### P2 — 工程增强（按批推进，每批过闸门）
6. **死代码暂缓清单分批清理**：约 6–8 批（download/imageOptimization/optimisticUpdate/auth/cacheDB/requestCoalescing/performanceMonitor/useWorkbenchClass），每批「单文件删除+同步测试+四闸门」。
7. **API 文档站**：G5 OpenAPI 461 路径已具备，生成可交互文档站（对外/协作价值）。
8. **单文件行数 ratchet**：前端 436 页加行数监控，防超大页回归。

### P3 — 维持性（常态化）
9. 监控线上指标、定期安全补丁、DB 备份策略验证。
10. 任何源码改动必过四闸门，守住 2389/3038 零回归基线。

## 六、总结

项目处于**「成熟稳定 + 业务驱动」**阶段：功能完整、生产就绪、测试基线高（后端 2389 / 前端 3038 全绿）、性能实测 −35%、技术债基本清零。**继续挖掘技术债的边际收益已很低**；下一阶段的实质驱动力按优先级为：① 消除 hivemq 公共 broker 依赖（P0 风险）→ ② 硬件联调与可观测性（P1）→ ③ 渐进工程增强（P2）。建议按本报告 P0 启动，其余按业务节奏排期。
