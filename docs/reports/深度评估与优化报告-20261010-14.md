# 深度评估与优化报告 - 2026-10-10（R14：服务层 N+1 系统审计与批量修复）

## 1. 背景与目标

R13 收口了 `/api/classes` 的 N+1（缓存 Miss 冷路径尖刺），并在报告 §6 遗留项③ 点明：**服务层「列表分页后对每项的关联补全」型 N+1 模式（如 `class_service._build_class_response`）此前未被 R12 路由层扫描覆盖**。R12 的 N+1 启发式只扫路由层 `for` 循环体内的 DB 调用，漏掉了「服务层补全方法被列表循环调用」这一类。

本轮（R14）目标：
1. **系统性审计**全部列表型服务方法，用 AST 两阶段扫描 + 人工读源码 + `entity_names` 设施核实，区分「确凿 N+1」「已优化项」「误报」；
2. **全批量消除确凿 N+1**（含次要模块，用户已确认「全批量修」），全部走「批量预取 + 向后兼容回退」低风险范式；
3. **零 API 契约变更、零新依赖、零回归**（全量 2318/0/0/7）。

核心问题：**除 `/api/classes` 外，其他列表端点（活动 / 考试排名 / 学习小组 / 班委 / 值日 / 座次 / 课表等）是否仍存在同类服务层 N+1？若有，逐一消除。**

## 2. 诊断方法论

1. **AST 两阶段扫描**（在 `apps/backend/services/` 上）：
   - 阶段一：找出所有列表函数（`list_*` / `get_*_view` 分页返回）循环体内调用的「补全方法」（`_build_*_response` 等），以及这些方法内部是否含 DB 查询（关键字 `query` / `get_by_id` / `names.`）。
   - 阶段二：对阶段一命中的「列表函数 → 补全方法 → 含 DB」链路，逐一读源码 + 核对 `entity_names.py` 的请求级缓存（`_lookup` 经 `flask.g`，相同 id 二次访问命中缓存）与 `prefetch_*` 批量预热设施，判断是否真 N+1（逐行首访各异 id）还是高缓存命中（同 id 重复访问）。
2. **去伪**：对扫描命中项逐一人工读源码，纠正 AST 误报（已 `joinedload` 预加载、列表方法本身不含 DB、仅 dict 展平、或详情方法被误标）。
3. **修复范式**：批量 `Model.id.in_(ids)` + `GROUP BY` 一次预取；`_build_*_response(obj, xxx_map=None)` 新增可选参数，传 `None` 回退原逐行查询（详情页 / 单对象调用方行为完全不变）；跨 `names.klass/student` 的调用用 `prefetch_classes/prefetch_students` 在列表入口一次性预热。
4. **行尾守恒**：7 个目标文件经字节级检测均为纯 LF，`Edit` 不破坏行尾（无 CRLF/MIX 特例）。

## 3. 诊断发现

### 3.1 审计结果总览（确凿 N+1 vs 已优化 vs 误报）

| 模块 | 列表方法 | 补全调用 | 判定 | 根因 |
|------|----------|----------|------|------|
| activity | `list_activities` | `_build_activity_response` → `ActivityRegistration.query.filter_by(...).count()` | **确凿 N+1** | 逐活动 COUNT（无 `func` 导入、未批量） |
| exam | `get_exam_rankings_view` | 循环 `get_by_id(User, score.student_id)` | **确凿 N+1** | 逐成绩查学生名 |
| study_group | `list_groups` | `_build_group_response` → `StudyGroupMember.query.filter_by(group_id=...).all()` | **确凿 N+1** | 逐组查成员 + 逐成员 `names.student` |
| committee | `list_members` | `_build_member_response` → `names.student(member.student_id)` | **确凿 N+1** | 逐成员查学生名（各异 id） |
| duty | `list_groups` | `_build_group_response` → `names.klass(group.class_id)` | **确凿 N+1（跨班）** | 逐组查班级名，跨班首访各异 |
| seating | `list_charts` | `_build_chart_list_response`（无 DB / 无 names） | 误报（非 N+1） | 早期 AST 误标，列表方法纯字段返回 |
| committee | `list_terms` | `_build_term_response`（无 names） | 误报（非 N+1） | 列表方法纯字段返回 |
| course_schedule | `get_schedule_list_view` | 已 `joinedload(CourseSchedule.class_info, CourseSchedule.subject)` | 已优化（非 N+1） | R6/R7 已预加载 |
| scores | `get_score_list_view` | 已 `joinedload(Score.subject_rel)` | 已优化（非 N+1） | R6 已预加载 |
| class | `get_class_list` | 已批量预取 | 已优化（非 N+1） | R13 已修 |
| users/rules/score-categories | 主列表 | `cached_api` 命中缓存 | 已优化（非 N+1） | R12 已收口 |
| rule_recommendation | `get_all_recommendations` | 仅 dict 展平无 DB | 误报（非 N+1） | 无 DB 访问 |

**关键洞察**：
- R12 路由层扫描只覆盖「路由层 `for` 直接调 DB」，漏掉「列表 → 服务层补全方法 → DB」这一类。R14 用「列表函数 → 补全方法 → DB」链路扫描补齐了盲区。
- `names.klass/student` 经 `flask.g` 请求级缓存，**同 id 重复访问高命中**；真正构成 N+1 的是「各异 id 的首访」（如 committee 逐成员 student_id、duty 跨班 class_id），用 `prefetch_*` 一次性预热即可消除。
- `seating.list_charts` / `committee.list_terms` / `rule_recommendation` 经核实无 DB，纠正了 AST 的早期误报——**不盲目改写**。

### 3.2 缓存设施缺口

`services/entity_names.py` 已有 `prefetch_students`（批量预热学生名缓存），但**缺 `prefetch_classes`**（班级名预热）。duty 跨班 N+1、study_group 的 `names.klass` 防御均需此设施 → R14 补 `prefetch_classes`（同构 `prefetch_students`）。

## 4. 修复落地（零 API 契约变更、向后兼容）

所有文件经检测为纯 LF，字节级守恒；6 文件 `py_compile` 全过。

### 4.1 `services/entity_names.py`（设施补全）
- 新增 `prefetch_classes(ids)`：同构 `prefetch_students`，一次性 `ClassInfo.id.in_(want)` 预热班级名缓存，供列表入口防御性消除 `names.klass` 跨班 N+1。

### 4.2 `services/activity_service.py`（导入 + 批量预取）
- 补 `from sqlalchemy import func`（原文件缺 `func` 导入）。
- 新增 `_batch_reg_counts(activity_ids)`：`ActivityRegistration.activity_id.in_(ids)` + `status=="registered"` + `GROUP BY activity_id` 一次取报名计数（构造 `{activity_id: count}`）。
- `list_activities` 分页 / 非分页两路径均先批量预取，再 `_build_activity_response(a, reg_counts=reg_counts)`。
- `_build_activity_response(a, reg_counts=None)`：传字典时 `reg_counts.get(a.id, 0)`，传 `None` 回退原逐活动 COUNT（**详情页 / 单对象调用方行为完全不变**）。

### 4.3 `services/exam_service.py`（批量预取学生名）
- `get_exam_rankings_view`：循环前一次性 `User.id.in_(student_ids)` 取 `{student_id: name}` 字典，循环内直接 `students.get(score.student_id)`；查不到时与原逻辑一致不写 `student_name` 字段。`get_by_id` 仍服务于其它视图，导入保留。

### 4.4 `services/study_group_service.py`（批量预取成员 + 学生名）
- `list_groups`：一次性 `StudyGroupMember.group_id.in_(group_ids)` 取全部成员（构造 `members_map`），并收集 leader_id + 成员 student_id 调 `names.prefetch_students(...)` 预热。
- `_build_group_response(g, members_map=None)`：传 `members_map` 时直接取 `members_map.get(g.id, [])`，传 `None` 回退原逐组查成员（**详情 / 单对象调用方兼容**）。

### 4.5 `services/committee_service.py`（学生名预热）
- `list_members`：循环前 `names.prefetch_students([m.student_id ...])` 一次性预热，消除逐成员 `names.student` N+1；`names.klass(member.class_id)` 同班高命中保持。

### 4.6 `services/duty_service.py`（班级名预热）
- `list_groups` 分页 / 非分页两路径均在循环前 `names.prefetch_classes([g.class_id ...])`，消除跨班 `names.klass` N+1（单班时退化为无操作）。

预期效果：上述列表端点每页 N+1 查询（活动 ~N 次 COUNT、排名 ~N 次 get_by_id、小组 ~N 次成员查询 + 成员名、班委 ~N 次学生名、值日跨班 ~N 次班级名）全部降为 **1 次批量查询**（或缓存预热），命中路径（已 `cached_api` 的端点）不变。
