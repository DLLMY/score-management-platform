# 深度静态评估与优化报告（2026-10-07 · 其二：关系懒加载 N+1）

> 范围：`apps/backend/models/score_models.py`（Flask + SQLAlchemy + flask-restx）
> 方法：纯 AST 静态分析（不执行、不污染仓库）定向扫描 `to_dict` 读关系属性 + 抽样读码甄别真伪 + 全量回归零破坏验证
> 本轮目标：在上轮 R14–R38、OPT-1/OPT-2 与"5 索引 + `warning_service` N+1 重构"（commit `35847b2`）基础上，**继续挖掘更隐蔽的真实性能债**——即 AST 显式查询扫描抓不到的**关系懒加载 N+1**（list 端点序列化逐行访问 `lazy` 默认=select 的 `relationship`，触发隐式逐行查询）。

---

## 1. 评估方法

上一轮 `#467`/`#468–#471` 的 AST N+1 检测只覆盖"循环体内出现引用循环变量的 DB 查询"，漏掉一类同样致命但形态不同的 N+1：**`to_dict` 序列化时访问 `lazy=select`（默认）的 `relationship` 属性**。此时 ORM 在每行序列化时隐式发 1 次 SELECT，列表端点规模 N 即放大为 N 次查询，且**不出现在任何手写 `for` 循环里**，纯查询扫描无法命中。

本轮用定向 AST 脚本（临时不入库）补这一盲区：

1. **关系清单**：扫描 `models/*.py`，提取每个类的关系定义，记录其 `lazy` 关键字（缺省=默认 `select`）。
2. **to_dict 读关系**：对每个类的 `to_dict` 方法体做 AST 遍历，提取 `self.<attr>` 访问，若 `<attr>` 属关系且 `lazy` 为默认 `select`，列为候选。
3. **抽样甄别**：逐条读源码判定是"条件式访问（仅当 `fields` 含派生字段）"还是"无条件访问"，并结合默认序列化字段确认普通列表端点是否真的触发。

## 3. 已确认的真实缺陷（定位 + 量化）

### 3.1 `Score.to_dict` — 无条件关系懒加载 N+1（确定性热点）
- **位置**：`models/score_models.py` `Score.subject_rel`（L325），`to_dict`（L327–341）。
- **问题**：`to_dict` 内 `"subject": self.subject_rel.name if self.subject_rel else None` 为**无条件**访问。任意 `Score` 列表（成绩查询/导出/统计）每序列化 1 行即触发 1 次隐式 `SELECT ... WHERE subject.id = ?`。
- **量化**：返回 N 条成绩的端点 ≈ **N 次额外查询**（与成绩条数线性）。这是最确定的 N+1，因为访问不依赖 `fields`。

### 3.2 `ScoreRecord.to_dict` — 默认序列化即触发的双关系 N+1
- **位置**：`ScoreRecord.user`（L150）/ `ScoreRecord.rule`（L151），`to_dict`（L153–200）。
- **问题**：`need_user = "user_name" in fields or "card_id" in fields`、`need_rule = "rule_name" in fields or "category_name" in fields` 为条件式，但 `serialize_score_record` 默认输出即含 `user_name`+`rule_name`（见 `services/score_record_service.py` docstring），故**普通列表端点每 1 行触发 2 次隐式查询**。
- **量化**：返回 N 条积分记录的端点 ≈ **2N 次额外查询**。
- **已有缓解（仅局部）**：`utils/query_optimizer.py::optimize_user_records_query` 与 `export_routes.py:203` 对**导入/导出路径**已用 `joinedload(ScoreRecord.user, ScoreRecord.rule)` eager-load；**普通列表端点未加**，即普通列表即 N+1。

### 3.3 `ScoreRule.category` — 条件式但详情端点触发
- **位置**：`ScoreRule.category`（L88）。`to_dict` 仅在 `"category_name" in fields` 时访问，默认详情端点含该字段，故详情/列表含 `category_name` 时每条 1 次隐式查询。风险低于 3.1/3.2，但同属一类，一并修复成本低、收益确定。

## 4. 已执行的优化（惯用、零契约变更）

### 4.1 惯用修复：4 个 many-to-one 关系改 `lazy="selectin"`
将 N 个逐行 `lazy=select` 隐式查询合并为 **1 个 `WHERE fk IN (...)` 批量查询**，是 many-to-one 关系消除 N+1 的标准零契约手法（查询次数与列表规模解耦，HTTP 响应体字段与值完全不变）。

| 模型.关系 | 行 | 改动前 | 改动后 |
|---|---|---|---|
| `ScoreRule.category` | L88 | `backref="rules"` | `backref="rules", lazy="selectin"` |
| `ScoreRecord.user` | L150 | `backref="records"` | `backref="records", lazy="selectin"` |
| `ScoreRecord.rule` | L151 | `backref="records"` | `backref="records", lazy="selectin"` |
| `Score.subject_rel` | L325 | `backref=db.backref("score_records", lazy=True)` | `backref=db.backref("score_records", lazy=True), lazy="selectin"` |

> - 反向 one-to-many `backref`（如 `User.records`、`ScoreRule.rules`、`Subject.score_records`）**未改动**，保持默认 `lazy=select`（集合不该被 selectin eager-load），符合 many-to-one 用 selectin、collection 不 eager 的惯用边界。
> - 与既有 `query_optimizer.py` 的 `joinedload(ScoreRecord.user, ScoreRecord.rule)` **不冲突**：显式 `joinedload` option 覆盖单次查询策略，`lazy="selectin"` 仅作默认回退。

### 4.2 未改动项
- `Score.exam` / `Score.student` / `Score.admin` / `ScoreRule` 以外关系：`to_dict` 不访问或为测试桩路径，无证据 N+1，不纳入（避免引入回归风险）。
- 其他 22 模型文件中 `lazy=select` 关系：经 AST 确认 `to_dict` 不读取，无序列化 N+1，保持现状。

## 6. 结论与后续建议

本轮在"有证据、低风险、零契约变更、全量零回归"原则下，收口一类**上一轮 AST 查询扫描漏掉的隐蔽 N+1**——`to_dict` 序列化时访问 `lazy=select` 关系：

1. **消除 `Score.subject_rel` 确定性 N+1**（每列表行 1 次隐式查询 → 1 个 IN 批量查询）；
2. **消除 `ScoreRecord.user`/`ScoreRecord.rule` 默认序列化双 N+1**（每列表行 2 次 → 1 个 IN 批量查询，普通列表端点亦受益，不再仅限导入/导出路径）；
3. **顺带修复 `ScoreRule.category`** 详情端点触发的关系访问。

改动仅触及模型关系 `lazy` 策略，**零 API 契约变更**（响应字段与值完全不变），且与既有 `joinedload` 优化路径共存无冲突。

**后续可选（非必修）**：其余模型 `lazy=select` 关系经 AST 确认 `to_dict` 不读取，无序列化 N+1；若后续出现新的列表端点跨关系聚合需求，可复用"selectin 默认 + 热点路径 joinedload 覆盖"的同一范式。
