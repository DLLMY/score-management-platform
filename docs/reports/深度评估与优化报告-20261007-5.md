## 1. 评估方法

- 用 AST 静态分析遍历 `models/`（关系定义）与 `api/ services/ utils/ tasks/`（访问点）：
  - **关系清单**：解析全部 `relationship(...)` 声明，记录每个 `(类, 属性)` 的 `lazy` 值。共 **29 个关系**。
  - **非 eager 关系**：`lazy != selectin/joined/subquery/dynamic` 的有 **25 个**（全部为默认 `lazy="select"`，即访问时才逐条查库）。
  - **序列化访问点**：扫描所有 `to_dict/serialize/to_json/as_dict` 方法，以及所有 `for x in ...:` 循环体、`[... for x in ...]` 列表推导内对 `x.<rel>` 的访问，匹配非 eager 关系名。
- **关键陷阱（命名冲突）**：全局按关系名聚合会把 `user`/`rule`/`subject_rel`/`category` 等同名关系误判——例如 `ScoreRecord.user` 第二轮已改 `selectin`，但 `Approval.user`/`Notification.user` 仍是 `select`；必须**逐类（类,属性）精确归属**才能区分。第一轮扫描因此误报 0 处（且误排除了 models 目录），修正后定位到真实债。
- **O:M 排除**：`SeatingChart.seats` 为 one-to-many 集合关系，不在循环访问列表内，若改 `selectin` 会退化成 N 条子查询，故**保持不动**。

## 3. 根因分析

Flask-SQLAlchemy 关系默认 `lazy="select"`：访问 `obj.some_relation` 时若关系对象尚未加载，会在**当前会话内立即发起一条针对性查询**。当 `for item in items: serialize(item)` 在循环内访问 `item.class_info` / `item.user` 等，每个 `item` 都触发一次独立查询——这就是经典的**序列化 N+1**。

前几轮修复的 N+1 是"路由层显式 `Model.query.get(x)`"，而本轮的是"模型关系在序列化时被隐式惰性加载"。两者表现相同（列表越长，额外查询越多），但修复位置不同：本轮在**模型关系定义层**用 `lazy="selectin"` 一次性解决——加载父集合时，SQLAlchemy 自动用一条 `WHERE id IN (...)` 把全部相关子对象批量预加载，将 N+1 降为 1 次额外 IN 查询（与关系数量成正比，而非与行数成正比）。

---

## 4. 修复方案（24 个关系，均零 API 契约变更）

在 6 个模型文件中，为 24 个 many-to-one 关系追加 `lazy="selectin"`：

```python
# 修复前
class_info = db.relationship("ClassInfo", backref=db.backref("devices", lazy=True))
# 修复后
class_info = db.relationship("ClassInfo", backref=db.backref("devices", lazy=True), lazy="selectin")
```

- 涉及文件：`models/device_models.py`（3）、`models/notify_models.py`（2）、`models/archive_models.py`（4）、`models/user_models.py`（3）、`models/system_models.py`（2）、`models/score_models.py`（10），总计 **24 处**。
- `backref(..., lazy=True)` 保持不变（反向多端仍惰性加载，符合常理）。
- **零 API 契约变更**：响应 JSON 结构与字段完全不变，仅加载时机从"逐条访问时查"变为"随父集合批量预加载"。
- 行尾守恒：后端 `.py` 多为 CRLF，用字节级精确替换（断言每处原文唯一），未改动任何逻辑与行尾。
- 修复后全局 `lazy="select"` 关系仅剩 `SeatingChart.seats`（O:M，按设计保留）。
