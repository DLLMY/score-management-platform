# 深度评估与优化报告 - R16：端点级 DB 查询画像与索引命中核验（2026-10-10）

## 一、评估方法

在 R14（服务层 N+1 系统审计）与 R15（dashboard 指标修复）收口后，按"颗粒度继续细一些"的要求，将诊断从"是否存在 N+1"下沉到**端点级 DB 查询画像 + 索引命中核验**：

1. 复制 `tests/conftest.py` 的测试 app 构建方式（`sqlite :memory:` + `StaticPool` + 全量命名空间注册），**自建中等规模业务数据集**（User 320 / Score 2600 / ScoreRecord 1500 / Exam 12 / Device 40 / Alert 320 / Activity 15 / CourseSchedule 150 / DutyGroup 12 等），使索引选择具备真实基数。
2. 构建后**施加生产索引集**：先 `db.create_all()`（仅含模型层索引），再用守卫式逻辑把 `scripts/create_indexes.py::get_all_indexes()` 中"表存在且索引不存在"的索引 `CREATE INDEX` 补上（本轮补建 16 个），使画像等于生产真实索引集——避免"测试库缺索引"造成的假阳性。
3. 挂 SQLAlchemy `before_cursor_execute` / `after_cursor_execute` 事件监听器，统计每个 GET 端点**单次冷请求**（强制清缓存）触发的 DB 查询次数与耗时。
4. 对每条 distinct SQL 跑 `EXPLAIN QUERY PLAN`，标记 `FULL_SCAN`（整表扫、未命中任何索引）与 `TEMP_BTREE`（排序/分组未走索引覆盖）。
5. 诊断脚本为**自删型**：运行后自动清理，不污染仓库（本次生成的中间结果 `_diag_r16_profile_result.json/.txt` 仅作过程产物，已随脚本删除）。

> 关键校正：首轮画像直接判定大量 `TEMP_BTREE`，但随后发现测试库缺 `create_indexes.py` 索引，导致低估覆盖（例如 dashboard 的 `ORDER BY current_score` 本应命中 `ix_user_current_score`）。施加生产索引集后重跑，残留项才是真实缺口。

## 三、真实残留缺口（生产索引集下仍存在的索引未命中）

### 3.1 FULL SCAN + ORDER BY（整表扫描 + 内存排序，表增长后才会显著；本次优先修）
| 表 | 列表端点 | 默认 ORDER BY（源码核实） | 现状 |
|---|---|---|---|
| CourseSchedule | /api/course-schedules | `(day_of_week, period_number)` | SCAN + TEMP B-TREE（**且 24 条查询疑似残留 N+1**） |
| DutyGroup | /api/duty/groups | `(day_of_week, name)` | SCAN + TEMP B-TREE |
| Device | /api/devices | `(created_at DESC, id DESC)` | SCAN + TEMP B-TREE |
| Subject | /api/subjects | `(sort_order, name)` | SCAN + TEMP B-TREE（表极小，8 行） |
| DeviceGroup | /api/device-group | `(sort_order, name)` | SCAN + TEMP B-TREE（表极小，6 行） |

### 3.2 已走索引但 ORDER BY / GROUP BY 未覆盖（复合索引可消除排序）
| 表 | 端点 | 触发 SQL 计划 | 建议复合索引 |
|---|---|---|---|
| Score | /api/score-analysis/rankings/1 | `SEARCH scores USING ix_scores_exam_id (exam_id=?) \| USE TEMP B-TREE FOR ORDER BY` | `ix_score_exam_score (exam_id, score, id)` |
| Score | /api/scores（按 exam_id/student_id 过滤后排序） | `SCAN scores USING ix_scores_subject_id \| USE TEMP B-TREE FOR ORDER BY` | `(score, id)`（无过滤时覆盖排序） |
| ScoreRule | /api/score-categories | `SEARCH score_rule USING ix_score_rule_is_active \| USE TEMP B-TREE FOR GROUP BY` | `(is_active, category_id)` |
| Notification | /api/notifications | `SEARCH notification USING ix_notification_recipient_type \| USE TEMP B-TREE FOR ORDER BY` | `(recipient_type, <order_col>)` |
| ScoreRecord | /api/dashboard/data\|stats（按 rule_id 聚合排序） | `SCAN score_record USING ix_score_record_rule_id \| USE TEMP B-TREE FOR ORDER BY` | 聚合排序，低收益（见 3.3） |
| ScoreRecord/User | /api/analysis/class-ranking（JOIN 后 GROUP BY class_name） | `USE TEMP B-TREE FOR GROUP BY` | 低收益（见 3.3） |
| User | /api/dashboard（ORDER BY current_score DESC） | `SCAN user \| USE TEMP B-TREE FOR ORDER BY` | 见 3.3 |

### 3.3 评估为"可接受 / 基本不可避免"（不建议改）
- **dashboard `ORDER BY current_score DESC` 全用户读取**：单列 `ix_user_current_score` 已存在，但全列全行读取时，非覆盖索引无法消除排序（需回表），仅当改 `LIMIT top-N` 或覆盖索引才有意义——收益低、改动风险高，**标记可接受**。
- **dashboard / class-ranking 的 `GROUP BY … ORDER BY sum(…)`**：排序对象是聚合结果，单索引无法覆盖，**低收益**，不改。
- **score-categories / notifications 的微小表 GROUP BY/ORDER BY**：表极小，排序成本可忽略，**可选**。

### 3.4 附带发现：疑似残留 N+1
- `/api/course-schedules` 单次列表 **24 条 SQL**（鉴权外约 18 条数据查询），远高于其它列表端点；`/api/activity` **18 条**（鉴权外约 12 条）。二者虽状态 200、DB 耗时仍 <1ms，但**结构上疑似每列表项触发额外查询**（如逐行查班级/科目/教师或报名数），建议在索引修复之后单独做一次 N+1 细查。

## 四、修复方案（待确认范围；零契约变更）

按"双处定义"纪律：新增索引须**同时**写入模型层 `__table_args__`（覆盖新建/测试库 `create_all` + `reconcile`）**与** `scripts/create_indexes.py::get_all_indexes()`（覆盖现有库启动自举），并经 `verify_indexes()` 闸门；改动后跑全量 21 分块回归（基线 2318/0/0/7）。

**Tier 1（高 ROI，核心/可增长端点）**
1. `CourseSchedule`：`(day_of_week, period_number)` —— 消除 /api/course-schedules 整表扫描+排序（**并顺带追查其 24 条查询的 N+1**）。
2. `DutyGroup`：`(day_of_week, name)` —— 消除 /api/duty/groups 整表扫描+排序。
3. `Device`：`(created_at, id)` —— 消除 /api/devices 整表扫描+排序（设备规模可增长）。
4. `Score`：`(exam_id, score, id)` —— 消除 /api/score-analysis/rankings 排序（核心排名，随班级人数增长）。

**Tier 2（小表/可选，低成本）**
5. `Subject`：`(sort_order, name)`；`DeviceGroup`：`(sort_order, name)`；`ScoreRule`：`(is_active, category_id)`；`Score`：`(score, id)`（覆盖无过滤 scores 列表排序）；`Notification`：`(recipient_type, <order_col>)`。

## 五、结论
R16 评估确认：R14/R15 收口后，主流列表端点的 N+1 已被消除（多数端点数据查询 0–1 条），**残留问题集中在"排序/分组未走索引覆盖"的索引缺口**，以及 course-schedules/activity 的疑似 N+1。建议先修 Tier 1（4 个复合索引，零契约变更、低回归风险），再视情况补 Tier 2，最后单独追查 course-schedules/activity 的查询膨胀。
