- **日期**：2026-10-08
- **范围**：管理平台后端（Flask + SQLAlchemy + SQLite）
- **目标**：在第七轮「列级 FULL-SCAN 审计」收口（`eba8056`）基础上，继续做更细粒度诊断——聚焦**静态分析抓不到、列级索引审计也漏判**的查询族：**`filter + order_by + limit` 触发的排序溢出（`USE TEMP B-TREE FOR ORDER BY`）** 与 **`COUNT(*)` 分页总成本**。沿用第七轮验证过的「隔离内存引擎 + EXPLAIN QUERY PLAN」实证法，零破坏修复并经全量回归收口。

R7 收口后结论：单列过滤列层面已无大型 FULL-SCAN 债。本轮下沉到**「过滤+排序」复合查询族**——这类查询即便过滤列有单列索引（`SEARCH ... USING INDEX`），排序列若无匹配索引，SQLite 仍会在内存中做**全量排序溢出（USE TEMP B-TREE FOR ORDER BY）**，随结果集增大而显著拖慢，且无法被第七轮的单列审计发现。

---

## 1. 方法论（四步闭环，复用 R7 隔离引擎）

1. **静态扫描查询族**：全仓提取所有 `.order_by(...)` 与配对 `.filter/.filter_by` 的 (模型, 过滤列, 排序列, 有无 limit/paginate, 有无 count)，产出候选清单；同时提取所有 `.count()` 分页统计查询。
2. **比对真实索引**：复用 R7 提取的 `db.metadata` 真实索引（含 `UNIQUE` 隐式索引），标记「过滤有索引但排序无匹配」的候选。
3. **隔离内存引擎实证**：最小 `Flask + sqlite:///:memory:` + `db.create_all()`（**完全不碰开发库**，规避 `create_app('testing')` 触发 `create_indexes` 建索引 / `db.drop_all()` 风险）。对每族构造 `SELECT * FROM <tbl> WHERE <fcol>=? ORDER BY <ocol> DESC LIMIT N`，跑 `EXPLAIN QUERY PLAN`，捕捉 `USE TEMP B-TREE FOR ORDER BY`（排序溢出）与 `SCAN table`（COUNT 全扫）。
4. **修复 + 实证反证**：对确凿债务在模型层补复合索引 `db.Index(...)`，**再次在隔离引擎手动 `CREATE INDEX` 复跑 EXPLAIN 反证 TEMP B-TREE 消失**，再落地到源码。

## 2. 候选清单与实测结论

### 2.1 确凿排序溢出债（已修复）

| 表 | 过滤列 | 排序列 | 修复前 EXPLAIN | 高频路径 |
|----|--------|--------|----------------|----------|
| `scores` | `student_id` | `entered_at` | `SEARCH scores USING INDEX ix_scores_student_id` → **`USE TEMP B-TREE FOR ORDER BY`** | 单学生成绩录入历史倒序分页 |
| `scores` | `exam_id` | `entered_at` | `SEARCH scores USING INDEX ix_scores_exam_id` → **`USE TEMP B-TREE FOR ORDER BY`** | 单考试各科成绩列表 |
| `exams` | `class_id` | `start_time` | `SEARCH exams USING INDEX ix_exams_class_id` → **`USE TEMP B-TREE FOR ORDER BY`** | 班级考试列表按开始时间倒序 |
| `composite_scores` | `student_id` | `composite_score` | `SEARCH composite_scores USING INDEX ix_composite_scores_student_id` → **`USE TEMP B-TREE FOR ORDER BY`** | 学生综合分排行/排序分页 |

**反证（隔离引擎手动建复合索引后复跑）**：

```
### scores filter=student_id order=entered_at
  BEFORE: spill=True  | SEARCH scores USING INDEX ix_scores_student_id (student_id=?) | USE TEMP B-TREE FOR ORDER BY
  AFTER (composite [student_id, entered_at]): spill=False uses_index=True
     | SEARCH scores USING INDEX ix_scores_student_id_entered_at (student_id=?)
### scores filter=exam_id order=entered_at
  AFTER (composite [exam_id, entered_at]): spill=False uses_index=True
     | SEARCH scores USING INDEX ix_scores_exam_id_entered_at (exam_id=?)
### exams filter=class_id order=start_time
  AFTER (composite [class_id, start_time]): spill=False uses_index=True
     | SEARCH exams USING INDEX ix_exams_class_id_start_time (class_id=?)
### composite_scores filter=student_id order=composite_score
  AFTER (composite [student_id, composite_score]): spill=False uses_index=True
     | SEARCH composite_scores USING INDEX ix_composite_scores_student_id_composite_score (student_id=?)
```

四族排序溢出**全部消除**，且复合索引前导列与既有单列索引一致，过滤-only 查询仍可用该复合索引，无功能回退。

### 2.2 排除的非债（实测已走索引 / 误报）

| 候选 | 实测结论 | 原因 |
|------|----------|------|
| `exams` filter=None order=`start_time` | `SCAN exams USING INDEX ix_exams_start_time` | 全局按开始时间排序已走单列索引，无溢出 |
| `notify_histories` filter=None/global order=`created_at` | `SCAN notify_histories USING INDEX ix_notify_histories_created_at` | 全局按时间排序已走单列索引 |
| `frontend_perf_metrics` / `frontend_error_logs` / `system_metrics` / `security_audits` global order=`created_at` | 均 `SCAN ... USING INDEX ix_*_created_at` | 同上，时间列已有单列索引 |
| `operation_log` / `score_record` / `mqtt_log` filter+order | 已有复合索引 `(user_id, created_at)` / `(student_id, created_at)` 覆盖 | R1 已建复合索引 |
| `rate_limit_records` order=`window_start` | 该表为短时存活小表、无 `identifier` 列（候选列名误写），无高价值热路径 | 排除，不制造假优化 |
| `notify_histories` filter=`user_id` | 该表无 `user_id` 列（候选列名误写）；真实过滤列为 `notification_id`/`device_id` 且表体积极小 | 排除 |

> 教训：第八轮初版脚本因列名误写（`identifier`/`user_id` 不存在于目标表）一度漏判两族；经核对 `RateLimitRecord` / `NotifyHistory` 真实模型字段后排除，避免无效索引。

## 4. 评估范围说明（未被判定为债的维度）

- **`COUNT(*)` 分页统计**：扫描所有 `.count()` 调用，定位的高成本统计均落在已索引过滤列（如 `Score.query.filter_by(student_id=...).count()` 走 `ix_scores_student_id`），未出现「无索引列 + COUNT + 大表」组合，故本轮 COUNT 维度**无新债**。
- **布尔/低基数列排序**：`is_active` / `is_read` 等布尔排序即便建索引优化器亦跳过，非债（与 R7 结论一致）。
- **tiny-table 排序**：通知历史、限流记录等体积极小且短时存活，排序溢出成本可忽略，排除。

## 6. 结论
