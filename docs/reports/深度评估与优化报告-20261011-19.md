## 3. 唯一清晰冗余（R19-1 修复）

### 3.1 根因

`composite_score_service.recalculate_user_score`（增量重算）对同一批活跃用户做了**两次整表全对象加载**：

```python
# 第一次：仅取 id 列表
active_user_ids = [u.id for u in User.query.filter(User.is_active).all()]
...
# 第二次：按 id 重载同一批对象，仅取 current_score
behavior_map = {
    u.id: u.current_score or 0
    for u in User.query.filter(User.id.in_(active_user_ids)).all()
}
```

- 两次查询返回的是**同一批 User 全对象**（ORM 物化 60 个完整 `User` 行 ×2）。
- 实际只需 `id` 与 `current_score` 两个字段 → 属冗余 I/O 与内存占用。

### 3.2 修复

合并为单条 `with_entities` 投影查询，`active_user_ids` 与 `behavior_map` 一次取齐：

```python
rows = (
    db.session.query(User.id, User.current_score)
    .filter(User.is_active)
    .all()
)
active_user_ids = [r.id for r in rows]
behavior_map = {r.id: r.current_score or 0 for r in rows}
```

- **零契约变更**：返回的数据结构（`active_user_ids` 列表、`behavior_map` 字典）与字段语义完全不变，下游代码零改动。
- **纯 LF 守恒**：仅改 1 文件 `composite_score_service.py`，无行尾漂移。

## 4. 定向验证（R19-3）

构建 seeded harness（`create_app(lightweight=True)` + `app.app_context()` + `db.create_all()` + 60 活跃用户种子），用 SQLAlchemy `after_cursor_execute` 事件统计 `recalculate_user_score` 的 SELECT 计数：

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| `recalculate_user_score` 总 SELECT | 9 | 8 | **−1** |
| 整表全对象加载次数 | 2（×60 完整 User 物化） | 0 | **−2** |
| 用户投影查询 | 0 | 1（`with_entities(id, current_score)` ×60 元组） | +1（轻量） |

> 关键收益不在 SELECT 条数（−1），而在**消除一次整表全对象物化**：从"两次加载 60 个完整 `User` 行"降为"一次投影 60 个 `(id, current_score)` 元组"——I/O 与内存占用显著下降，且不影响任何返回值。

`py_compile` 通过；Temp 诊断脚本已清理。
