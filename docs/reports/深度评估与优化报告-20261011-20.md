## 1. 评估目标与范围

R17/R18 收口了序列化层 N+1（entity_names 请求级缓存 + prefetch 批量预热），R19 收口了整表双加载。本轮进入**第三维度扫描**：**循环体内部直接出现的裸 DB 查询**——这些查询绕过了 entity_names 的 `flask.g` 去重缓存，是序列化层修复后残留的真实 N+1。

扫描对象：`apps/backend/services/` 全量，用 `ast` 模块静态定位 `for` / `async for` / 推导式循环体内直接出现的 `Model.query.xxx` / `db.session.query` / `session.get` 调用。

扫描策略与误报排除：
- 仅保留「遍历对象本身不是查询、但循环体内又发起了新查询」的显式 `for`；
- 排除「遍历查询结果」（`for x in query.all()`）这类正常的逐行处理结果，避免误报；
- 排除批处理 / 种子 / 导入 / NLP 作业与写入事务路径（非读路径 N+1）。

## 3. 修复（R20-1）

### 3.1 `analysis_service.get_class_compare`（多班对比，循环内逐班点查）

**根因**：原函数在循环体（逐 `class_name`）内直接发起两类查询：
- 每日记录：`db.session.query(...).filter_by(class_name=cn).all()`（每班 1 次）
- 班级 Top 学生：`User.query.filter_by(class_name=cn).order_by(...).all()`（每班 1 次）

N 个班 → 2N 条裸查询，且**完全绕过 entity_names 缓存**（class_name 维度未纳入 prefetch）。

**修复**：循环前批量预取，循环内字典查找替代点查：
```python
# 循环前：按 (date, class_name) 批量取出全部 daily 行
daily_rows = (
    db.session.query(ClassDailyRecord.date, ClassDailyRecord.class_name, ...)
    .filter(ClassDailyRecord.class_name.in_(class_names))
    .all()
)
daily_by_class = {}
for d in daily_rows:
    daily_by_class.setdefault(d.class_name, []).append(d)  # 存 Row 对象

# 循环前：按班级批量取 Top 学生（current_score 倒序）
top_rows = (
    User.query.filter(User.class_name.in_(class_names))
    .order_by(User.current_score.desc())
    .all()
)
top_by_class = {}
for u in top_rows:
    top_by_class.setdefault(u.class_name, []).append(u)

# 循环内：字典查找，零额外查询
daily = daily_by_class.get(class_name, [])
top_students = top_by_class.get(class_name, [])[:5]
```

- **顺带修复 3 处原有 `dict(query.all())` 生产崩溃 bug**（函数在多列聚合场景下必崩）：
  - `class_stats_map` / `period_records_map` / `unlock_stats_map` 原用 `dict(query.all())`（6 列 / 多列 `Row` → `ValueError: dictionary update sequence element #0 has length N; 2 is required`）。
  - 改为 dict-comprehension：`{r.class_name: r for r in query.all()}`（值仍为 `Row`，下游属性访问 `r.xxx` 不变）。
  - 这是函数**原有生产隐患**（测试不播种多班数据未暴露），本次一并消除。

### 3.2 `class_service.validate_associations`（班级关联校验，循环内逐班点查）

**根因**：原函数在循环体（逐 `AdminClass` 班级）内对每班发起 2 次点查：
- `AdminClass.query.filter_by(class_info_id=cls.id, ...).first()`（关联计数）
- 同上另一条件 `.first()`（主班判定）

N 个班 → 2N 条裸查询。

**修复**：循环前批量预取全部关联，按 `class_info_id` 分组，循环内 `next(...)` 过滤替代点查：
```python
# 循环前：一次性取出所有班级的关联
links = AdminClass.query.filter(
    AdminClass.class_info_id.in_([c.id for c in classes])
).all()
links_by_class = {}
for _l in links:
    links_by_class.setdefault(_l.class_info_id, []).append(_l)

# 循环内：内存过滤，零额外查询
cls_links = links_by_class.get(cls.id, [])
link = next((_l for _l in cls_links if _l.some_cond), None)
primary = next((_l for _l in cls_links if _l.is_primary), None)
```

### 3.4 单元测试 mock 桩配套修正（R20 必要配套）

`validate_associations` 由"逐班 2 次 `filter_by().first()`"改为"单次 `IN` 批量查询 + 内存按 `class_info_id` 分组"后，原单元测试 `test_validate_associations_missing_link` / `test_validate_associations_not_primary` 仍以旧桩 `AdminClass.query.filter_by(...).first()` 模拟查询——新代码根本不调用 `filter_by`，桩失效致 `links` 为空，把本应检出的 `not_primary` 误判成 `missing_link`（首次全量回归 chunk-003 `rc=1` 即此一处失败）。

修正：两测试改为模拟新批量路径——

- `missing_link`：`mock_admin_query.filter.return_value.all.return_value = []`（无关联记录 → 期望 `missing_link`）
- `not_primary`：`mock_admin_link` 补 `class_info_id = 1`（与 `cls.id` 对齐分组键），`mock_admin_query.filter.return_value.all.return_value = [mock_admin_link]`（存在关联但 `is_primary=False` → 期望 `not_primary`）

**生产逻辑零改动**，仅让测试桩匹配新查询结构，测试意图（`not_primary` / `missing_link` 分支判定）完全保留。其余 `fix_associations` 测试（582/614/644 行）走 `filter_by` 且未被 R20 改动，不受影响。
