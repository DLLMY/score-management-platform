## 1. 扫描方法（R21-0）

对 `services/*.py` 做 AST 增强扫描：
1. 构建"本模块函数 → 是否含 DB 查询"映射；
2. 遍历所有 `for/async for/推导式`，收集其体内调用的本地函数名；
3. 命中"调用的本地函数自身含查询" → 委托型 N+1 嫌疑（区别于 R20 直接 `.query`/`session.get`）。

命中 **50 候选**，按铁律排除：
- **批处理/导入/ML 训练/写事务**（`academics`/`device`/`import_export`/`nlp_*`/`risk_predict`/`score_predict`/`warning`/`ota`/`rule_engine` 等）：非请求热路径或行为敏感，不动；
- **已批量优化**的热列表路径（`get_class_list` R13、`list_activities`、`list_groups`、`user_list_service`、`get_period_info` R17）：确认已用 `prefetch_*`/IN 批量/请求级缓存，排除。

最终锁定唯一清晰、低风险、高价值的读/导出路径 N+1：**`class_service.export_classes`**。

## 2. 根因（R21-1）

`export_classes` 循环内逐班调用两个辅助函数：
- `_get_head_teacher_name(head_teacher_id)` → `get_by_id(Admin, ...)`（每班 1 次 SELECT）；
- `_get_student_count(class_info)` → `User.query.filter(class_name==, is_active).count()`（每班 1 次 SELECT）。

N 个班级 → **2N 次额外查询**。而同文件 `get_class_list`（R13）早已用"批量 IN 预取 teachers + group_by 计数 counts"模式消除同类 N+1，`_build_class_response` 也已支持 `teachers`/`counts` 字典入参（带逐班回退）。`export_classes` 是**一致性缺口**——复用已验证模式即可零契约变更修复。

## 3. 修复方案

`export_classes` 循环前批量预取（与 R13 同款 IN 模式）：
- `head_teacher_ids` → `Admin.query.filter(Admin.id.in_(...))` 一次取全部班主任名 → `teachers` 字典；
- `class_names` → `User.query.filter(class_name.in_(...), is_active).with_entities(class_name, func.count()).group_by(...)` 一次分组计数 → `counts` 字典；
- 循环内改为 `teachers.get(...)` / `counts.get(...)` 字典查找。

`_build_class_response` 的逐班回退路径（`teachers=None`/`counts=None` 时调原 helper）保留，详情页行为不变。EOL 守恒：class_service.py 保持纯 LF（794 行）。

## 4. 实证验证（R21-1，seeded harness + SQLAlchemy `after_cursor_execute` SELECT 计数）

播种 N 班 × 4 生 + 每班 1 班主任，调用 `ClassService().export_classes()` 统计 SELECT 数：

| 班级数 N | export_classes SELECT 数 | 旧逻辑预期（1+2N） |
|---|---|---|
| 5  | **3** | 11 |
| 20 | **3** | 41 |
| 50 | **3** | 101 |

- **SELECT 数恒定 = 3**（1 列表 + 1 班主任 IN + 1 分组计数），与班级数无关 → N+1 消除；
- **值正确性**：导出行 `student_count == 4`、`head_teacher_name` 正确填充（如 `teacher_0`）；
- 生产代码与测试桩零破坏性变更（现有 `test_export_classes_*` 用 MagicMock + patch helper，响应结构断言仍全过）。
