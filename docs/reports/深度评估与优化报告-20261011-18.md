## 1. 背景与根因

序列化层在构造响应时大量调用 `entity_names` 的 `names.student(id)` / `names.klass(id)` / `names.subject(id)` 逐条查库补全名称。

`entity_names` 的缓存机制（`flask.g` 请求级按 id 去重）：
- 同一 `id` 在同一请求内重复访问只查 1 次（去重生效）；
- **但 distinct id 数 = 查询数** —— 列表接口返回 N 条记录、涉及 N 个 distinct 学生/班级/科目时，仍是 N 次单 id 点查。

此前仅 `prefetch_students` / `prefetch_classes` 两个批量预热设施，**缺 `prefetch_subjects`**，且各服务列表函数序列化前普遍未调用预取，导致：
- A 高危（逐学生）：每页 40 学生 → 40+ 次点查；
- B 中危（逐班级）：每页 ≤12 班级点查；
- C（缺 prefetch_subjects）：homework / study_guide 的 subject 逐条点查。

静态扫描 **~15 模块 ~30 处** 序列化循环同源 N+1。

## 4. 定向验证（R18-3）

**方法论**（复刻 R17 可信验证，消除交叉污染）：
- 用 `monkeypatch` 关闭/恢复 `prefetch_*`（`_NOP = lambda ids: None` 模拟"修复前"，恢复原方法模拟"修复后"）；
- **每端点独立 `app_context()`**：`flask.g` 请求级缓存在同一 context 内跨多次 measure 会交叉污染（OLD 写缓存→NEW 命中缓存 0 查询），故每端点用独立 `g`（共享 StaticPool 内存库）；
- ORM 对象跨 context 会 `DetachedInstanceError`，measure 内用整型 id 重取（`SeatingChart.query.get(chart_id)`）；
- SQLAlchemy `event.listen(db.engine, "after_cursor_execute", _count)` 统计 SQL 条数（事件监听必须在 `app_context()` 内注册）。

**结果（修复前 → 修复后，7 行全证 N+1 消除）**：

| 端点 | distinct id 维度 | 修复前 | 修复后 | 降幅 |
|---|---|---|---|---|
| mental_health.list_records(page) | 40 student_id | 82 | 4 | 95% |
| attendance.list_attendance(page) | 5 class_id + 40 student_id | 87 | 5 | 94% |
| seating._build_chart_response | 20 student_id | 42 | 4 | 90% |
| homework.list_assignments(page) | 5 class_id + 8 subject_id | 15 | 4 | 73% |
| study_guide.list_plans(page) | 40 student_id + 8 subject_id | 90 | 5 | 94% |
| entity_names.student ×30 (prefetch+loop) | 30 student_id | 60 | 2 | 96% |
| entity_names.subject ×8 (prefetch+loop) | 8 subject_id | 8 | 1 | 87% |

> 注：修复后计数含分页/权限/自身元数据查询，非纯粹 name 查询；"修复后"仍保留极少量（每端点 1–4 条）基础查询属正常。
