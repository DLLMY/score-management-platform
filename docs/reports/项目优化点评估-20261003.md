## 二、功能 / 正确性优化点（已有功能）

### 🔴 高优先级：API 读缓存键缺失「用户维度」→ 跨用户缓存越权读取风险
- **证据**：`utils/api_cache_middleware.py::generate_cache_key` 仅以 `method + path + 查询参数` 生成键，**不含当前登录用户 / 角色 / 班级**：
  ```python
  data = f"{method}:{path}:{json.dumps(args, sort_keys=True)}"
  hash_key = hashlib.sha256(data.encode()).hexdigest()
  ```
- **风险**：被 `@cached_api` 装饰的 GET 端点若返回**与当前用户相关**、且**查询参数不足以区分用户**的数据，则缓存命中会跨用户返回他人数据。典型场景：班级排行（`rank_routes.py:35` 注释「班级排行高频读缓存」）、按 RBAC 服务端决定返回范围的列表端点——教师 A 的班级数据可能被键相同的请求返回给教师 B。
- **影响面**：Redis 模式下为全局共享，必然越权；内存模式（无 Redis）在单 gunicorn worker 内也会跨请求共享。与项目一贯强调的「RBAC / 班级隔离」铁律直接冲突。
- **修复建议（低风险、明确正确）**：在 `generate_cache_key` 中并入身份维度，例如 `user_id = get_current_user_id()` / `role`，或让缓存键包含 `g.user.id`；对**明确无用户态的纯全局只读端点**才允许不加。亦可对返回用户私有数据的端点用 `unless=` 显式跳过缓存。

### 🟡 低优先级：read-after-write 失效依赖手工调用
- 新增「GET 列表 + 写操作」端点时，需作者记得调用 `invalidate_*`；遗漏则短期读到陈旧数据。建议：把失效收口为装饰器/信号钩子，或加 lint/测试断言（写端点后相关缓存被清）。

### 🟡 低优先级：少量写路径 N+1（非热路径）
- `services/academics_service.py:219`：`Subject.query.get(item.get("id"))` 在循环内（批量导入/更新写路径）。
- `services/alert_service.py:315`：循环内 `Alert.query.filter(...).count()`。
- 二者均在非高频写路径，影响小；可改为 `in_()` 批量查询。

## 三、性能优化点

### 🟡 中优先级：前端传输压缩（构建卫生误报已更正）
- **更正（2026-10-03 复扫）**：此前「dist 路由 chunk 叠加 3 个仅 hash 不同变体」的判定**不成立**——重新用脚本枚举 dist/assets 全部 221 个 .js 文件并按 名称.哈希.js 归组，**重复变体数 = 0**。6.79MB / 229 文件属正常 Vite 分块体量，且 dist 已被 .gitignore 忽略（0 跟踪文件），Dockerfile 部署 RUN npm run build 每次清空重建，**不影响生产**。该「构建卫生」子项撤销，不再改动。
- **保留项：传输压缩**。前端产物首屏与 vendor 体积可观（vendor ~425KB、recharts ~349KB、首屏 index ~393KB）。**修复采用 nginx 边缘 gzip**（apps/frontend/nginx.conf 已启用 gzip on + 覆盖 gzip_types），而非 vite-plugin-compression：
  - 零新增前端依赖、零构建改动（部署链路用 npm install 非 npm ci，但无需动 package.json）；
  - 压缩在反向代理层完成，对所有静态资源与 /api 代理响应统一生效，比构建期压缩更省心；
  - 量化：vendor 425KB -> gzip ~110KB，整体传输显著下降。
  - 注：recharts 已独立分包（仅图表页加载）、antd 已做页面级共享分包（首屏不拖入），这两点**已做得对**，保留。

### 🟡 中优先级：分析类时间范围聚合查询的索引核实
- **证据**：`services/analysis_service.py` 是查询密度最高的服务（36 处 `.query/.filter`），统计/趋势按 `created_at` 做时间范围扫描。
- **建议**：核实 `ScoreRecord`、`OperationLog` 等高频分析表是否具备 `(student_id, created_at)` / `(created_at)` 覆盖索引；若数据量增长后时间范围聚合变慢，补齐复合索引避免全表扫描。（模型已有 184 处 `index=True`，此处仅「核实补齐缺口」，非从零建索引。）

### 🟢 低优先级：SQLite 连接池规模
- `pool_size=20 + max_overflow=40 = 60` 连接对 SQLite（单写者）略过度，写路径会序列化。非缺陷，`busy_timeout=5000` 已兜底；如追求更省资源可下调至 `~10 + overflow`。

### 🟢 低优先级：NLP 首请求解析器预热竞态
- `nlp_service` 快速解析器由守护线程异步加载，加载完成前回退到 DB 增强解析器（测试中有确定性钉固）。生产建议确认 `warmup_cache_task` 在启动即触发，避免冷启动首请求走较慢路径。
