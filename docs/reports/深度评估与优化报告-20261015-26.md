## 2. 修复方案（DB 条件聚合，复用 R24/R25 模板）

### R26-1 get_device_stats_view
```python
dev_row = db.session.query(
    func.count(Device.id),                                   # total
    func.count(case((Device.status == "error", Device.id))), # error
    func.count(case((and_(Device.last_heartbeat.isnot(None),
                          Device.last_heartbeat >= online_cutoff), Device.id))),  # online
).one()
```
1 条查询回传 3 个计数（原回传整表行）。offline = max(0, total-online-error) 保持不变。

### R26-2 get_device_advanced_stats_view
```python
dev_row = db.session.query(
    func.count(Device.id),                                   # total
    func.count(case((Device.status == "error", Device.id))), # error
    func.count(case((and_(last_heartbeat.isnot(None),
                          last_heartbeat >= online_cutoff), Device.id))),  # online
    func.avg(Device.wifi_signal),                            # avg_signal
    func.count(case((Device.wifi_signal >= -50, Device.id))),                    # excellent
    func.count(case((and_(wifi_signal >= -70, wifi_signal < -50), Device.id))),  # good
    func.count(case((and_(wifi_signal >= -80, wifi_signal < -70), Device.id))),  # fair
    func.count(case((Device.wifi_signal < -80, Device.id))),                     # poor
).one()
alert_row = db.session.query(
    func.count(Alert.id),
    func.count(case((Alert.severity == "critical", Alert.id))),
).filter_by(source="device", is_resolved=False).one()
```
- signal_distribution 用 `case` **互斥区间**复刻原 `if/elif/else` 分档（NULL 天然排除）。
- avg_signal 用 `func.avg`（SQL AVG 跳过 NULL，等价原 `sum/len`），外层 `float()` 包裹保持原 float 契约。
- 告警 2 计数合并为 1 条条件聚合。

### 明确排除（甄别记录）
- **dashboard 的 online 计数**：`Device.is_online` 是 `@property` → `is_device_online`（含 per-device `heartbeat_timeout` + OTA 保护窗 + status 三要素），语义复杂，保正确性优先、不冒险下推 SQL。
- exam/analysis（有界且混合序列化）、homework（行确需序列化）、security（写去重）、engagement（另一层 N+1）——均非干净的"取全表只数几个值"。

## 3. 实证验证

**关键方法调整**：R26 优化前后**都是 1 条目标表 SELECT**（旧的 `.all()` 与新的聚合各 1 条），SQL 语句计数 harness 无法区分"回传整表行"vs"回传聚合行"。故 `tests/test_r26_aggregation.py`（新增，4 用例）改用**双证据**：

1. **SQL 形状**：捕获目标表 SELECT 语句，断言含 `count(` / `avg(` 聚合函数（证明是聚合查询、非回传整表行）。
2. **数值正确性**：种子 5 台设备（3 在线/1 心跳过期/1 无心跳/1 error/信号覆盖四档）+ 设备告警，逐字段断言 total/error/online/offline/avg_signal/signal_distribution/alert_count/critical/online_rate。

| 测试 | 证明点 |
|---|---|
| `TestR26DeviceStats::test_aggregate_shape` | device SELECT == 1 且含 `count(` |
| `TestR26DeviceStats::test_numeric` | total=5/error=1/online=3/offline=1 |
| `TestR26DeviceAdvancedStats::test_aggregate_shape` | device SELECT==1（含 avg+count）、alert SELECT==1（含 count） |
| `TestR26DeviceAdvancedStats::test_numeric` | avg=-65.0、分布 {excellent:1,good:2,fair:1,poor:1}、告警基线 delta、online_rate=60.0 |

4 用例全绿。

## 6. 观察项（记录在案）

- **「假经济优化」识别**：把多 COUNT 改为 `.all()` + Python 计数并非总是更优——设备/用户等潜在大表上，回传整表行的成本高于 DB 聚合。DB 条件聚合（只回传计数/均值）通常是更优解。
- **语句计数 harness 的边界**：当优化不改变"SELECT 条数"而只改变"回传载荷"时，需改用 SQL 形状 + 数值正确性证明。
- **@property 派生字段不宜下推**：`is_online` 这类含多要素（超时窗/保护窗/status）的派生属性，强行下推 SQL 易产生语义漂移，保正确性优先。
