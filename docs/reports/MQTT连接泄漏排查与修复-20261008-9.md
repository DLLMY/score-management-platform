# 深度评估与优化报告（第九轮：MQTT 云平台连接数 954/1000 异常排查与连接泄漏修复）

- **日期**：2026-10-08
- **触发**：用户发现 EMQX Cloud 控制台连接数达 **954 / 1,000**（即将触顶），要求排查原因。
- **范围**：`apps/backend/services/mqtt_manager.py`（后端 MQTT 连接生命周期）

---

## 1. 结论（TL;DR）

**根因 = 后端 MQTT 重连路径的连接泄漏**：每次网络抖动/意外断线后，重连逻辑创建**全新 client_id** 的 paho 客户端，而**旧客户端从不被显式断开**——旧客户端既保持与 broker 的既有连接（其 paho auto-reconnect 还会自行重连），又因 client_id 唯一（带秒级时间戳）broker 侧无法做会话替换，旧连接**永久堆积**。

- **增长模型**：每次网络抖动 → 所有已泄漏客户端触发 `on_disconnect` → 调度器只建 1 个新客户端/类型，但旧 N 个客户端各自 auto-reconnect 成功 → 总数 **N+1/类型**，线性累积。
- **量级核验**：现存最早 dev 服务进程自 **10/4 23:53** 持续运行（实测 4 个 python 进程存活：10/4 一对 + 10/7 一对，dev 模式 `debug=True` 触发 Werkzeug reloader 父+子双进程，每进程各建 control+telemetry 两条连接）。约 4 天内数百次 TLS/网络抖动 ≈ 数百条泄漏连接，与 954 观测值吻合。
- **修复后上界**：同进程同类型只有 1 条连接（client_id 稳定 + 重连前回收旧客户端），broker 侧会话可自愈替换。

## 2. 泄漏链路（代码级证据）

### 2.1 唯一化 client_id（`_create_and_connect_client`，修复前 L941）
```python
cid = f"{client_id}_{suffix}_{int(time.time())}"
```
每次重连生成**不同** client_id → EMQX 视为全新客户端，永不替换旧会话（`clean_session=True` 的会话替换只对**同 id** 生效）。

### 2.2 重连不回收旧客户端（`_connect_control` / `_connect_telemetry`）
```python
# 修复前：直接覆盖引用，旧客户端对象既不 disconnect 也不 loop_stop
self._client = self._create_and_connect_client("control", ...)
```
- 旧客户端 paho `loop_start()` + `reconnect_delay_set(1, 30)` **自带自动重连**，断线后自行重连成功；
- `_on_connect_control` 回调对旧客户端同样生效（设 CONNECTED、重新订阅）→ 旧客户端"复活"后与新旧连接**并存且都订阅工作**（还造成重复消息派发风险）；
- 下一次抖动：所有存活客户端同时 `on_disconnect` → 又建 1 个新客户端 → **堆积 +1**。

### 2.3 重连调度（`_schedule_reconnect`）
按类型去重（同类仅 1 个重连线程），但**每次抖动仍净增 1**，无收敛机制。

### 2.4 放大因素
- dev 模式 `run.py`：`debug = args.debug or args.env == "development"` → **开发环境恒为 debug=True** → Werkzeug reloader 父+子双进程，各建 control+telemetry 连接（每服务 4 条起步）；
- `service_init.py` L229-236：遥测未连上时**重试一次** `_connect_telemetry()`，修复前每次重试又是一條新连接；
- 实测存在 **10/4 23:53 启动的僵尸 dev 服务对**（4 天未关）。

## 3. 修复内容（唯一源码改动：`apps/backend/services/mqtt_manager.py`，零 API 契约变更）

### 3.1 新增 `_dispose_client`：回收旧客户端，阻断 auto-reconnect
```python
@staticmethod
def _dispose_client(client):
    if not client:
        return
    try:
        client.disconnect()
    except Exception:
        pass
    try:
        client.loop_stop()
    except Exception:
        pass
```

### 3.2 重连前先回收（`_connect_control` / `_connect_telemetry`）
```python
self._dispose_client(self._client)
self._client = None
self._client = self._create_and_connect_client("control", ...)
```
> 显式 `disconnect()` 触发的 on_disconnect rc=0，不会误触发 `_schedule_reconnect`（其守卫为 `rc != 0`），无重连风暴风险。

### 3.3 client_id 改为「进程内稳定」
```python
cid = f"{client_id}_{suffix}_{os.getpid()}"   # 原: f"{client_id}_{suffix}_{int(time.time())}"
```
- 同进程重连复用同一 id + `clean_session=True` → broker 自动踢掉同 id 旧会话（**broker 侧自愈兜底**，即使出现其它泄漏路径，连接数上界 = 1 条/类型/进程）；
- 跨进程（Werkzeug reloader 父子进程、多实例部署）因 pid 不同互不干扰，不会互踢；
- 修复了原实现**同秒内两次创建 id 碰撞**的隐患（`int(time.time())` 秒级精度）。

### 3.4 保持不变
- 双连接分流架构（control QoS1 + telemetry QoS0）、no_local 订阅、M10 快速确认、R2 last_known_good 回退等既有机制全部不动；
- 无新依赖、无迁移、无配置变更。

## 4. 排除项与取证记录

| 排查点 | 结论 |
|--------|------|
| 每消息新建客户端 | 无——`publish` 复用单例 `self._client`（`mqtt_manager.py` L1062） |
| API 反复触发重连 | `/mqtt/connect` 管理端点存在但走同一 `mqtt_manager.connect()` 单例；`connect()` 对已连接状态短路 |
| Celery worker 侧连接 | Celery 只做 DB 写入与通知，不建 MQTT 连接 |
| 设备侧（ESP32）泄漏 | 无法从本仓证实；后端修复后若连接数仍高，需查固件 client_id 策略（建议：每台设备固定 id，重连由 broker 会话替换收敛） |
| 实时 TCP 取证 | `Get-NetTCPConnection` 本机未见 8883 活连接（泄漏连接在 broker 侧等待 keepalive 过期/或属其它网络出口） |

## 6. 运维处置建议（需用户决策）

1. **立即止血**：重启/关闭现存 dev 服务进程（尤其 **10/4 23:53** 那对僵尸进程，PID 6644/16680），让 broker 侧泄漏会话随 keepalive（60s）过期回收；观察 EMQX 控制台连接数应回落到 ~个位数（设备数 × 1）+ 后端 4 条。

## 7. 后续可评估方向（不属本轮）

- ESP32 固件侧 client_id 策略复核（确认设备重连是否复用固定 id）。
- dev 模式 debug=True 强制开启 reloader 的双进程成本（父进程也会初始化 app 并建 MQTT 连接），可评估 `debug=False` + 显式 `use_reloader` 开关。
- 给 `_on_connect_*` 加「连接代际」校验：旧代客户端连接成功时自动自我回收（纵深防御，当前修复已够用）。
