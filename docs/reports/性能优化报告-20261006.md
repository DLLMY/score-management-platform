## 二、发现的两个真实瓶颈

### 瓶颈 1（影响面最大）：`SQLITE_CONFIG` 是"死配置"

全仓精确核实结果：`SQLITE_CONFIG` / `journal_mode` / `mmap_size` / `WAL` **各仅出现 1 次**（即 `config.py:84` 的定义本身），且**无任何 `connect` 事件监听器**。

→ 整段 SQLite 性能调优从未应用到真实 DBAPI 连接，SQLite 一直以库默认参数运行：

| 项 | 配置意图 | 修复前实际值 | 后果 |
|---|---|---|---|
| `journal_mode` | WAL | **`delete`** | 读写互相阻塞，并发能力骤降 |
| `cache_size` | 100MB | **-2000（约 2MB）** | 磁盘读放大 |
| `mmap_size` | 256MB | **0** | 无内存映射加速 |
| `synchronous` | 1（NORMAL） | **2（FULL）** | 每次写都 fsync |
| `temp_store` | memory | **0** | 临时表落盘 |

> 佐证：`services/mqtt_message_service.py:1058` 注释曾记录 "busy_timeout=0 ... 撞写锁"，与配置未接线互相印证。
> 更正：`busy_timeout` 实测修复**前已为 5000**（Python `sqlite3.connect()` 默认 5s，且 `connect_args.timeout=30` 亦会设置），故**不计入本次收益**。真正收益是 WAL + 缓存 + mmap + synchronous。

### 瓶颈 2：健康端点每次请求同步阻塞 100ms

`utils/diagnostics.py:116`（修复前）：

```python
cpu_percent = psutil.cpu_percent(interval=0.1)  # 缩短检查时间
```

`interval=0.1` 为**阻塞调用**，每次健康探测占用工作线程 100ms。而 `/api/system/health` 被监控系统 / K8s 探针 / 前端仪表盘高频轮询，代价被显著放大——这正是历史基线里该端点 56.76ms、仅 17.6 req/s 的主因。

## 三、已实施的优化

### OPT-1：`app/db_init.py` 新增 `connect` 事件监听器，真正应用性能 PRAGMA

```python
_SQLITE_PERF_PRAGMAS = (
    "journal_mode", "cache_size", "temp_store",
    "mmap_size", "synchronous", "busy_timeout", "locking_mode",
)

@event.listens_for(Engine, "connect")
def _apply_sqlite_perf_pragmas(dbapi_connection, connection_record):
    """为每个新建的 SQLite 连接应用性能 PRAGMA（WAL/缓存/mmap/busy_timeout）。"""
    if not isinstance(dbapi_connection, sqlite3.Connection):
        return
    cursor = dbapi_connection.cursor()
    try:
        for key in _SQLITE_PERF_PRAGMAS:
            value = getattr(config, "SQLITE_CONFIG", {}).get(key)
            if value is None:
                continue
            cursor.execute(f"PRAGMA {key}={value}")
    except Exception as e:
        log_warning(f"应用 SQLite 性能 PRAGMA 失败（忽略，不影响启动）: {e}")
    finally:
        cursor.close()
```

实测前后对比（临时库验证）：

| PRAGMA | 修复前 | 修复后 |
|---|---|---|
| `journal_mode` | `delete` | **`wal`** |
| `cache_size` | `-2000` | **`-100000`（约 100MB）** |
| `mmap_size` | `0` | **`268435456`（256MB）** |
| `synchronous` | `2`（FULL） | **`1`（NORMAL）** |
| `temp_store` | `0` | **`2`（memory）** |

**有意排除 `foreign_keys`**：它是正确性开关而非性能项，且历史迁移脚本依赖其 `OFF`；全局开启会改变现有行为，留作独立决策项。

### OPT-2：CPU 采样改为非阻塞

```python
# interval=0.1 会让每次健康探测同步阻塞 100ms；
# 该端点被监控/探针高频轮询，代价被显著放大。
# interval=None 立即返回「距上次调用期间」的 CPU 均值（标准非阻塞用法）。
cpu_percent = psutil.cpu_percent(interval=None)
```

实测：**109.0 ms → 0.56 ms**，单次健康探测节省约 **108 ms**。

## 六、续：实测收益与三处预存在失败修复（2026-10-07）

### 6.1 OPT-1 读密集负载实测收益

OPT-1 的全部效果 = 把性能类 PRAGMA 应用到每个 SQLite 连接。为给出可复现的量化结论，
用「修复前库默认」与「修复后 OPT-1 配置」两套 PRAGMA 跑贴近 `/api/users`、`/api/classes`
的读密集工作负载：10 万行 `users`（含 3 个二级索引，贴近真实 schema）+ 100 个 `classes`，
每轮 500 次迭代（分页有序列表 `ORDER BY current_score DESC LIMIT 50 OFFSET ?` + 随机点查
`WHERE id=?` + 过滤计数 `WHERE class_name=? AND is_active=1`），3 批取最优。

| 配置 | 单轮最优耗时 | 3 批(ms) |
|---|---|---|
| 修复前（SQLite 库默认：DELETE / -2000 / 0 / 2） | **2020.4 ms** | 2258 / 2020 / 2239 |
| 修复后（OPT-1：WAL / -100000 / memory / 1 + mmap 256MB） | **1074.4 ms** | 1215 / 1074 / 1079 |

**结论**：单线程读负载 **1.88× 加速**，单轮节省约 **946 ms**。该基准主要体现 `cache_size`
（2MB→100MB）与 `mmap_size`（0→256MB）的页缓存收益；`journal_mode=WAL` 带来的**读写并发互不阻塞**
收益无法在单线程基准中体现，但已随监听器在每个连接上生效，是生产环境更高价值的收益点。
