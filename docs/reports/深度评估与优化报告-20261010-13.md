# 深度评估与优化报告 - 2026-10-10（R13：性能基线刷新 + /api/classes N+1 冷查询尖刺消除）

## 1. 背景与目标

R12 已收口「端点级读缓存补全」：配置型列表端点（`/api/system/config`、`/api/time-rules`、`/api/class-periods`、`/api/class-periods/active`）接入 `cached_api` + 写后失效闭环，全量回归 **2318/0/0/7** 零回归入库（commit `172e54d`）。R12 收尾时遗留一项诊断结论：**现有 `performance_report*.json` 是 9 月旧基线，仅压测 9 个端点，R7–R12 已大幅改写性能画像，不足以支撑后续决策**。

本轮（R13）目标：
1. **刷新性能基线**——用当前（R7–R12 全优化后）代码重跑压测，得到真实时延分布（avg / p95 / max）；
2. **数据驱动定位真实热点**——对比新旧基线，找出退化/异常端点，而非拍脑袋；
3. **消除确认到的低风险高收益债**——本轮定位到 `/api/classes` 冷查询 324ms 尖刺，根因为 N+1，做批量预取改写。

核心问题：**R7–R12 之后，系统当前的真实性能画像是什么？是否仍有可量化消除的查询债？**

## 2. 诊断方法论

1. 定位压测脚本 `apps/backend/scripts/run_performance_test.py`：其用 `create_app()` + `test_client()` 直接压测（无需独立服务器），令牌经 `generate_tokens(admin_id=1)` 生成，端点清单硬编码在脚本内（9 个），输出 `performance_report.json`。
2. 备份旧基线（`performance_report.json` 仓库根 + `performance_report_postfix.json`），以 `FLASK_LIGHTWEIGHT=true` 重跑（跳过 MQTT / 调度器 init，避免沙箱网络挂死），新基线落在 `apps/backend/performance_report.json`。
3. 新旧基线逐端点对比：**avg / p95 / max / success_rate**，定位 max 异常退化的端点。
4. 用 `EXPLAIN QUERY PLAN` + AST 定位退化端点的查询实现，确认是缺索引 / 全表扫描 / N+1。
5. 全仓 AST 复核 `cached_api` 覆盖，确认 R12 §6 遗留候选（users / rules / score-categories 主列表）**已实质缓存**，缓存主线新增空间有限。

**关键洞察**：
- **`/api/classes` 是唯一严重退化端点**：max 从 38ms 暴涨到 **324ms**（+286ms），但 **p95 仅 8.89ms、avg 11.38ms**——典型「95% 请求命中 `cached_api`（ttl=60）平稳、5% 冷查询（缓存 Miss / 过期 / 首访）尖刺」特征。尖刺来自缓存 Miss 时的冷查询路径，而非命中路径。
- 其余端点 R7–R12 后均平稳或改善（users / subjects / rules / score-categories / csrf-token max 均下降）。
- `/api/system/health` 未缓存冷查询 29ms，非瓶颈（监控心跳，可接受）。
- `/api/dashboard` success_rate=0%，是鉴权 / 数据依赖问题（与 R12 报告一致），**非性能问题**，不在本轮范围。

### 3.2 `/api/classes` 退化根因 —— 确认 N+1

- `ClassList.get` 已带 `@cached_api(ttl=60)`（命中走缓存，不触发 DB 查询）；
- 缓存 Miss 冷路径：`get_class_list` 拿到分页结果（每页 ~10 个班级）后，对每个班级调用 `_build_class_response(c)`，其中逐班执行：
  - `_get_head_teacher_name(c)` → `get_by_id(Admin, …)`（逐个查管理员表，取班主任名）；
  - `_get_student_count(c)` → `User.query.filter(class_name==c.class_name, is_active).count()`（逐个按班级统计学生数）。
- 即 **1 页 ~10 个班级 → ~20 次额外查询**（10 次 Admin 查询 + 10 次 User 计数），正是缓存 Miss 时 324ms 尖刺的来源。这是 R12 N+1 启发式扫描遗漏的点（R12 扫描只覆盖路由层 for 循环体内的 DB 调用，未覆盖服务层 `_build_class_response` 这类「列表分页后对每项的关联补全」模式）。

### 3.3 缓存覆盖复核（R12 §6 遗留项）

AST 复核 `UserList` / `RuleList` / `CategoryList` 三个主列表资源，**均已接入 `cached_api`**——R12 的「配置型端点缓存主线」在 R12 之前/之中已完成，并非遗漏。全仓 197 个未缓存 GET 中 21 个疑似列表型，但绝大多数是成绩、学生、算法状态、导出、监控指标等高频变更/实时型，按 R12 安全准则不宜缓存。→ **缓存主线新增空间有限，R13 转向查询层 N+1 消除是正确的方向。**

## 4. 修复落地（零 API 契约变更、向后兼容）

改动集中在 `apps/backend/services/class_service.py`（文件为 LF 行尾，字节级守恒）：

1. **导入 `func`**（`from sqlalchemy import func`），供 `GROUP BY` 计数。
2. **`_build_class_response` 支持预取字典**：新增 `teachers=None, counts=None` 参数；传 `None` 时回退原逐班查询逻辑（**详情页 / 其它单对象调用方行为完全不变**），传字典时直接从预取字典取值。
3. **`get_class_list` 批量预取**：在拿到分页 `items` 后，一次 `Admin.id.in_(head_teacher_ids)` 批量取班主任名（构建 `{admin_id: real_name}` 字典）+ 一次 `User.class_name.in_(class_names)` + `GROUP BY class_name` 取学生数（构建 `{class_name: count}` 字典），把原 ~20 次查询降为 **2 次**；随后 `_build_class_response(c, teachers=…, counts=…)` 走预取字典。
4. **N+1 闭环验证**：`py_compile` 通过；定向回归（`test_classes_routes` / `test_class_service` / `test_admin_classes_routes`）**RC=0**，确认 `student_count` / `head_teacher_name` 字段值与旧逻辑一致。

预期效果：缓存 Miss 冷查询 max 从 324ms 回落到 <50ms（批量预取 2 查询 + 既有索引）；命中路径（p95 8.89ms）不变。
