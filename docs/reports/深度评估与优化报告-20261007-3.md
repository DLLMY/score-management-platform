## 3. 根因分析

N+1 的本质：循环体对集合中的每一个元素发起一次**独立 DB 查询**，查询次数随输入规模线性增长（O(n) 次往返）。在批量审批（最多 100 条）、每请求多处的预警配置读取等场景下，这会放大成数十次查询，且难以被"关系懒加载"类修复覆盖——因为它发生在服务/路由层的**显式循环**，而非 ORM 关系访问。

---

## 4. 修复方案（3 处，均零 API 契约变更）

### 4.1 批量审批 / 批量拒绝端点（高优先级）
**文件**：`apps/backend/api/scores/approvals_routes.py`  
**原代码**（两处结构相同）：
```python
results = []
for aid in ids:
    approval = Approval.query.get(aid)          # 逐条查询 → N+1
    if not approval:
        results.append({"id": aid, "success": False, "message": "申请不存在"})
        continue
    try:
        ok, message, _detail = _execute_approve(approval, {"comment": comment})
        ...
```
**修复**：一次性批量加载，构建 `{id: obj}` 字典，循环内改为字典查找（O(n) → O(1) 查询，实际 1 次 `IN` 查询）：
```python
# 批量加载，消除逐条 Approval.query.get 的 N+1（单次最多 100 条）
_approvals = Approval.query.filter(Approval.id.in_(ids)).all()
_approval_map = {a.id: a for a in _approvals}
results = []
for aid in ids:
    approval = _approval_map.get(aid)           # 字典查找，无额外查询
    ...
```
- 行为一致性：原 `query.get(aid)` 对非法/字符串 id 返回 `None` → 走"申请不存在"分支；修复后 `approval_map.get(aid)` 对不匹配主键同样返回 `None`，分支结果一致。
- 证据：`batch-approve`（L291-301）、`batch-reject`（L329-339）。

### 4.2 预警配置读取（热点，高优先级）
**文件**：`apps/backend/services/warning_service.py` `_get_config()`  
**原代码**：
```python
config = {}
for key, default in WarningService.DEFAULT_CONFIG.items():
    cfg = WarningConfig.query.filter_by(config_key=key).first()   # 每 key 独立查询
    config[key] = cfg.config_value if cfg else default
return config
```
**问题**：`_get_config()` 被 `evaluate_risk`（L68）、`get_warnings`（L243）、另一方法（L361）等多处调用，且预警计算/列表为**每请求高频路径**。若 `DEFAULT_CONFIG` 含 N 个键，单次调用即触发 N 次单 key 查询，跨请求叠加成显著热点。
**修复**：一次性 `IN` 批量加载：
```python
# 批量加载预警配置，消除逐 key 单查的 N+1（_get_config 被每请求多次调用）
_keys = list(WarningService.DEFAULT_CONFIG.keys())
_rows = (WarningConfig.query.filter(WarningConfig.config_key.in_(_keys)).all() if _keys else [])
_cfg_map = {r.config_key: r.config_value for r in _rows}
config = {}
for key, default in WarningService.DEFAULT_CONFIG.items():
    config[key] = _cfg_map.get(key, default)
return config
```
- 空列表特判（`if _keys else []`）避免 SQLAlchemy `IN ()` 语法错误。
- 证据：L312-316。

### 4.3 权限角色映射预加载（中优先级，缓存内 N+1）
**文件**：`apps/backend/utils/permission.py` `_get_admin_permission_codes()`  
**原代码**：
```python
for role_code in role_codes:
    mappings = RolePermissionMapping.query.filter_by(role_code=role_code).all()   # 逐 role 查询
    for m in mappings:
        permissions.add(m.permission_code)
    permissions.update(_get_inherited_permissions(role_code))
```
**说明**：该函数已被 `_PERM_CACHE`（30s TTL）兜底，单次无缓存时才触发 N+1；本修复消除该单次无缓存路径的逐 role 查询，且**不动递归的 `_get_inherited_permissions`**（继承链跨 role，无法简单 `IN`）。
**修复**：
```python
# 批量预加载所有角色的直接权限映射，消除逐 role 单查的 N+1
_mappings = (
    RolePermissionMapping.query.filter(RolePermissionMapping.role_code.in_(role_codes)).all()
    if role_codes
    else []
)
for m in _mappings:
    permissions.add(m.permission_code)
for role_code in role_codes:
    permissions.update(_get_inherited_permissions(role_code))
```
- 空列表特判避免 `IN ()` 错误。
- 证据：L339-345。

## 5. 索引复核（#477 结论）

- 现有索引 **22 个**，覆盖 `user / device / score_record / alert / exams / scores / notification / approval / operation_log / device_heartbeat` 等核心表（pytest 启动日志 `Existing indexes: 22` 实证）。
- 本轮 3 处 `in_()` 查询的索引命中：
  - **#4.1** `Approval.id.in_(ids)` → 走主键索引；
  - **#4.2** `WarningConfig.config_key.in_(keys)` → `warning_config` 为配置表（仅十余行），全表扫描成本可忽略；
  - **#4.3** `RolePermissionMapping.role_code.in_(role_codes)` → 权限表仅数十行，且上层 30s 缓存兜底。
- **结论**：本轮 N+1 修复无需新增索引。
