# 深度评估与优化报告 - 2026-10-09（R12：端点级读缓存补全与失效闭环）

## 1. 背景与目标

R7–R11 已完成索引层优化闭环（列级 FULL-SCAN → filter+order+limit 复合 → order_by 单列 → group_by 聚合），SQLite 排序/聚合溢出债清零。本轮（R12）转向查询层 / 缓存层：用数据定位真正可量化的收益点，而非盲目改写。

核心问题：**查询层是否存在显著的 N+1 / 冗余查询债？若无，是否还有其他低风险、可复用、可度量的优化面？**

## 2. 诊断方法论

1. 读取现有性能基线报告（`performance_report.json` / `performance_report_postfix.json` / `performance_report_baseline_20260919.json`），提取端点级响应时延与波动。
2. AST 扫描路由层 N+1 模式（for 循环体内含 DB 查询调用）。
3. 全仓扫描 `cached_api` 装饰器使用面，并用 AST 枚举所有 **未接入缓存的 `Resource.get` 端点**。
4. 逐候选评估缓存安全性：用户维度隔离、数据变更频率、实时性要求、写后失效可行性。

## 3. 诊断发现

### 3.1 性能画像（来自 `performance_report*.json`）
- `/api/system/health` 曾是最早期瓶颈（基线 avg **56.76ms** / max 144ms，被压测 100 次，是监控心跳）；`postfix` 已降至 **6.95ms**（间接受 R7–R11 索引优化 + 端点轻量化影响）。现已非瓶颈。
- 读密集列表端点（users / classes / subjects / rules / score-categories / config）avg 2–7ms，但 **max 远超 avg**（偶发冷查询波动，如 users max 59ms vs avg 5ms）——典型可通过缓存平滑。
- `/api/dashboard` 在两次报告里 `success_rate=0%`（鉴权 / 数据依赖，非性能问题）。

### 3.2 N+1 扫描
启发式仅定位 **6 处**「for 循环内含 DB 查询」，均为合理的小结构（health 探活、rbac 权限树遍历、批量导入），**无明显 N+1 债**。结论：盲目做 N+1 批量改写收益极低、风险高，不值得。

### 3.3 缓存基础设施（关键）
项目已有**生产级 `cached_api` 装饰器**（`utils/api_cache_middleware.py`）：
- 仅缓存 GET；key 强制含 `user_id + role`（从 `g.current_user` 或 JWT 解码，与装饰器顺序无关），**杜绝跨用户越权读取**，符合 RBAC / 班级隔离铁律；
- `skip_cache=true` 前端可强制刷新；缓存不可用自动穿透降级；仅缓存 200 非空响应；
- 已在 **46 文件 / 97 处**使用。

### 3.4 未覆盖端点分析
全仓 AST 扫描：**201 个 `Resource.get` 端点未接入 `cached_api`**，但绝大多数为详情（Detail）/ 导出（Export，返回流）/ 算法（计算密集 + 参数多变）/ 实时（health / metrics / csrf-token）端点——**不宜缓存**。适合缓存的是**低频配置型列表端点**（变更极低频、DB 查询重、前端反复拉取命中率高）。

### 3.5 精选候选
性能报告实测未缓存、且安全可缓存的低频配置型端点：
- `/api/system/config`（`SystemConfigResource`）—— 系统配置，极低频变更
- `/api/time-rules`（`TimeRuleList`）—— 评分时间规则，低频
- `/api/class-periods`（`ClassPeriodList` + `ClassPeriodActiveList`）—— 课程节次，极低频
- `/api/rank-rules`（`RankRuleList`）—— **已自带手动缓存**（`get_cache_service().get/set` + `invalidate_by_tag`），排除
- `/api/rules` 主列表 / `/api/score-categories` —— 已在 academics / score 体系内部分接入 `cached_api`，留作后续确认

## 4. 修复落地（零 API 契约变更、零新依赖）

复用现有 `cached_api`，给 4 个端点补缓存 + 写后失效闭环：

| 端点 | 文件 | 改动 |
|------|------|------|
| GET `/api/system/config` | `api/system/_system_part1.py` | +`@cached_api(ttl=120)`；PUT 后 +`invalidate_cache("/api/system/config*")` |
| GET `/api/time-rules` | `api/scores/time_rules_routes.py` | +`@cached_api(ttl=60)`；POST 后 +`invalidate_cache("/api/time-rules*")` |
| GET `/api/class-periods` | `api/scores/class_periods_routes.py` | +`@cached_api(ttl=120)`；POST 后 +`invalidate_cache("/api/class-periods*")` |
| GET `/api/class-periods/active` | `api/scores/class_periods_routes.py` | +`@cached_api(ttl=120)`（只读，无写端点） |

附带修复：`class_periods_routes.py` 的 `ClassPeriodActiveList` 查询存在**重复 `.order_by(...)`**（同一表达式写两次，`.order_by(A).order_by(A)`），已去重（行为不变）。

### 4.1 安全性与一致性论证
- **越权防护**：`cached_api` 缓存键含 `user_id+role`，A 用户无法读到 B 用户的缓存响应，符合 RBAC / 班级隔离铁律（与既有 97 处缓存一致）。
- **一致性**：写端点（PUT / POST）在变更成功后显式 `invalidate_cache(path*)`；即便失效路径因前缀偏差未命中，TTL 短（60–120s）+ 配置变更极低频，数据陈旧窗口可接受。
- **降级安全**：缓存服务不可用时 `cached_api` 自动穿透到原函数，不影响业务；写路径的 `invalidate_cache` 失败仅告警不阻断（T9 基础设施层日志化）。

## 6. 结论与遗留

- R12 未做 N+1 批量改写（诊断证实债不显著），而是**补全端点级读缓存**这一低风险、高复用、可度量的优化，平滑读密集端点的 P95 / max 波动、减轻 SQLite 读负载。改动仅 3 文件 / 10 处（加装饰器 + 写后失效 + 1 处去重），零契约变更、零新依赖。
- 排除：`RankRuleList`（已自带缓存）、详情 / 导出 / 算法 / 实时端点（不宜缓存）。
- **遗留（待确认）**：性能报告里的 `/api/users` 列表、`/api/rules` 主列表、`/api/score-categories` 列表若经核查确实未缓存，可作为 R12 扩展或后续轮次接入；R9 切回 EMQX Cloud 仍待用户提供主机 + 用户名 + 密码。
