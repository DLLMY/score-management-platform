## 2. P0 — 必须修的硬伤（部署前卡点）

> 这 4 项是**阻断性**缺陷：要么安全风险公开化，要么核心功能在生产直接失效。必须在任何对外服务前清零。

### P0-a 占位密钥入库（安全风险，可伪造 admin token）
- **证据**：`.gitignore` 仅忽略真实的 `apps/backend/.env`（`.gitignore:39`），但 **`.env.production` / `.env.development` 未被忽略**，且文件内含字面占位值：
  - `FLASK_SECRET_KEY=CHANGE_ME_IN_PRODUCTION_...`
  - JWT 密钥同样为固定占位串
- **fail-closed 的盲区**：`validate_secret_keys` 只校验「非空」，占位串能过检（非真正的随机密钥）。
- **后果**：若任一环境误用这些文件，签名密钥即公开于仓库历史，**可离线伪造任意用户（含 admin）JWT**。
- **修复方向**：① 将两个 `.env.*` 纳入 gitignore；② 在 fail-closed 中增加「禁止占位前缀（`CHANGE_ME_` / `change-me` / 长度阈值）」断言；③ 通过部署平台注入真实密钥，绝不入仓。

### P0-b WebSocket 生产入口断裂（功能致命）
- **证据**：
  - 后端生产镜像 CMD：`gunicorn --workers=4 --threads=2`（默认 sync worker，`ops/infra/Dockerfile`）。
  - `init_websocket`（`service_init.py:340`）配置 `async_mode="threading"`；WebSocket 处理器仅在 `run.py` 的 `socketio.run`（Werkzeug 开发服务器）下真正接好。
  - `wsgi.py` 仅 `from app import create_app; application = create_app()`，**未初始化/挂载 SocketIO**。
- **后果**：容器化 prod 下 gunicorn sync worker 不处理长连接 → **设备状态推送、WS 实时通知静默失效**（无报错，难排查）。
- **修复方向**：prod 用 `eventlet`/`gevent` worker + `socketio.run` 的 gunicorn 入口（`gunicorn -k eventlet app.wsgi:application`），或在 `wsgi.py` 挂载 `socketio`，compose 同步调整 worker 类型。

### P0-c 无 TLS 与安全 cookie 互斥（登录在生产直接坏）
- **证据**：`apps/frontend/nginx.conf` 仅 `listen 80`，**无 443 / 无 SSL 证书 / 无 80→443 跳转 / 无 HSTS**；但 prod 配置 `SESSION_COOKIE_SECURE=True`（`config.py`）。
- **后果**：纯 HTTP 下浏览器拒绝写入 Secure cookie → **登录会话无法建立，prod 登录直接失败**。
- **修复方向**：nginx 配 TLS（证书管理 + 80 跳转 + HSTS），或前置真实 TLS 终止层；并补充 `X-Forwarded-Proto`/代理头信任配置（否则 `SECURE` 判定仍可能错位）。

### P0-d 无版本化数据库迁移（运维致命）— 已修复（reconcile 方案，非 Alembic）
- **证据**：`apps/backend/migrations/` 是约 **16 个一次性 `fix_*.py` 脚本**（无 `alembic.ini`、无 `versions/`、无回滚机制）；新装库靠 `db.create_all()`（`db_init.py:33`），存量结构变更靠手工脚本；且**真实可运行 schema 一直由 `create_all` 维护**——集成测试暴露 6 个脚本 `from app import app, db`（`db` 不在 `app`）根本无法执行、`score_change_float.py` 对全新库盲目 `ALTER COLUMN`（SQLite 不支持）后整表重建引用不存在列，**多数 legacy 脚本长期是坏的**。
- **后果**：多环境（dev/staging/prod）schema 极易漂移；无回滚保障；团队协作无法追平结构版本。**尤为严重**：`User.risk_score`/`User.last_risk_updated`/`ScoreRecord.operation_log_id` 三列仅由 legacy 脚本 `ALTER TABLE` 追加、**未进模型** → 全新库缺列、`warning_service` 写 `user.risk_score` 必崩。
- **修复方案（已落地，未提交）**：**不引入 Alembic**（无法访问真实生产库，autogenerate 对既有库风险高）。改用「**reconcile.py（元数据驱动对账器，按 `db.metadata` 自动补缺失表/列/索引，幂等、零新依赖）+ seed_defaults.py（幂等种子：12 默认节次 + 5 预警配置）**」双保险，接入 `app/db_init.py::init_database`（受 `TESTING` 守卫，测试库不污染）。三列漂移已**收口进模型**由 `create_all`/`reconcile` 统一维护。legacy 脚本保留为已弃用历史参考（不接入启动）。新增 `tests/test_migration_runner.py`（tempfile 库 + 轻量 app，校验 schema 完整/种子/幂等/列补齐）全过。
- **部署衔接（剩余）**：迁移步骤已嵌入启动期（`init_database`），部署无需独立 `alembic upgrade`；后续可把迁移执行日志纳入 `P1-a` 部署流水线审计。
