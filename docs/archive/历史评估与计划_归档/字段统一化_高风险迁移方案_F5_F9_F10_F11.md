## 1. F10 —— `WOLDevice` 并入 `Device`（P3，结构合并，前置依赖 F5）

### 1.1 现状
- `Device`（L385，`devices`）：业务主键 `device_id` String(100) unique；外加整数 `id` PK；列含话机/盒子状态、OTA、class_info_id、admin_id 等；`device_type` String(50) 已存在（当前多为空/未用）。
- `WOLDevice`（L832，`wol_devices`）：整数 `id` PK + `device_id` String(100) index（**非** unique、非 FK）；WOL 专属列：`mac_address`、`subnet_mask`、`broadcast_ip`、`wake_on_lan_enabled`、`last_wake_time`、`wake_count`、`is_active`。
- 代码引用：`api/devices/wol_routes.py` 全量 CRUD（约 20 处 `WOLDevice.query`）；`DeviceGroupMapping.device_id` FK→`wol_devices.id`（L890）。

### 1.2 目标
- 以 `Device` 为唯一设备实体；WOL 设备作为 `Device` 行（`device_type='wol'`）。
- `WOLDevice` 专属列提升为 `Device` 的可空列（合并后 `wol_devices` 表删除）。

### 1.3 数据迁移映射（核心）
对每条 `wol_devices` 行 `w`：
1. 取 `w.device_id`（字符串业务键）。若为空 → 生成 `f"wol-{w.id}"` 占位（保证非空唯一）。
2. 在 `devices` 中按 `device_id` 查找：
   - 不存在 → `INSERT` 新 `Device` 行，拷贝 `device_id` + WOL 专属列（`mac_address`/`subnet_mask`/`broadcast_ip`/`wake_on_lan_enabled`/`last_wake_time`/`wake_count`/`is_active`），`device_type='wol'`，其余 Device 列取默认值。
   - 已存在（device_id 撞 `devices`）→ 仅回写 WOL 专属列（不新建重复行）。
3. 建立映射 `map_wol_int_id[w.id] = devices_row.id`（用于 F5 重映射 `DeviceGroupMapping`/`NotifyHistory`）。

### 1.4 执行步骤（幂等迁移脚本 `migrate_merge_wol_device.py`）
1. `WOLDevice`/`Device` 模型临时保留（脚本内用 `from models import ...`，不依赖模型改名即可跑数据）。
2. 单事务：
   - 遍历 `wol_devices`，按 1.3 写入/更新 `devices`，构建 `map_wol_int_id`。
   - 将 `map_wol_int_id` 写入临时表/JSON 落盘（`migration_wol_id_map.json`），供 F5 复用（**关键：F5 必须在本步之后**）。
   - 确认 `devices` 全部写入成功后再 `DROP TABLE wol_devices`（先不删，留待 F5 完成并验证后再删，见 1.5）。
3. 模型层（代码改动，不在脚本内）：`models/__init__.py` 给 `Device` 增加 WOL 专属列；删除 `WOLDevice` 类；`wol_routes.py` 改为读写 `Device`（`device_type='wol'` 过滤）。
4. 前端 `DeviceManagement`/`WOL` 相关页若独立调用 WOL 接口，需改为 Device 接口（带 `device_type` 过滤）。

### 1.5 回滚预案
- `wol_devices` 表在 F5 验证通过前**不删除**，仅标记废弃；回滚 = 还原 `wol_routes.py` 引用 `WOLDevice`（模型类恢复）。
- `map_wol_int_id` 持久化于 JSON，回滚时 `DeviceGroupMapping` 仍可还原为原整数键。
- 全程单事务 + 执行前 `sqlite3 .backup` 物理备份 `instance/score_management.db`。

### 1.6 风险与缓解
- **device_id 空/重复**：WOLDevice.device_id 非 unique，可能为空或与 devices 撞。缓解：空值生成占位键；撞键回写不新建。
- **关联外键**：`DeviceGroupMapping.device_id` FK→wol_devices.id 在建新表阶段（F5）重建为 →devices.device_id（String）。F10 阶段仅搬数据，FK 重建留 F5。
- **wol_routes 行为回归**：合并后 WOL CRUD 走 Device 表，需回归测试 `wol_routes` 用例。

## 2. F5 —— `device_id` 全项目统一 `String(100)`（P1，语义数据迁移）

### 2.1 现状（类型分裂，实测）
| 表.字段 | 类型 | 引用目标 |
|---|---|---|
| `Device.device_id` (L387) | String(100) unique | 业务主键 |
| `DeviceAlert.device_id` (L428) | String(100) | devices.device_id |
| `DeviceHeartbeat.device_id` (L439) | String(100) | devices.device_id |
| `Alert.device_id` (L544) | String(100) | devices.device_id |
| `DeviceFirmwareUpdate.device_id` (L572) | String(100) | devices.device_id |
| `ScheduledNotify.device_id` (L908) | String(100) | devices.device_id |
| **`DeviceGroupMapping.device_id` (L890)** | **Integer FK→wol_devices.id** | WOLDevice 整数主键 |
| **`NotifyHistory.device_id` (L1225)** | **Integer（无 FK）** | 推断指向 wol_devices.id |

→ 6 处 String 直接引用 `devices.device_id`；2 处 Integer 引用 `wol_devices.id`。跨表 JOIN 因键空间不同（字符串 vs 整数）必然出错。

### 2.2 目标
- `DeviceGroupMapping.device_id`、`NotifyHistory.device_id` 改为 `String(100)`，FK→`devices.device_id`。
- 既有整数值（wol_devices.id）经 F10 的 `map_wol_int_id` → `wol_device.device_id` 字符串重映射。

### 2.3 数据迁移映射（核心，依赖 F10 的 `map_wol_int_id`）
- `DeviceGroupMapping`：每行 `device_id`（整数 wol id）→ 经 `map_wol_int_id[int] `得 `devices.id` → 再查该 Device 的 `device_id` 字符串 → 写入新 String 列。
- `NotifyHistory`：确认 `device_id` 整数语义（grep 显示 `scheduled_notify_routes.py:268` / `notify_template_routes.py:264` 写入时传入的值；**执行前需二次确认是 wol_devices.id 还是 devices.id**）。若是 wol id → 同 DeviceGroupMapping 重映射；若是 devices.id → 直接转字符串。
- 重映射后两表 `device_id` 统一为 `devices.device_id` 字符串，FK 约束重建。

### 2.4 执行步骤（幂等迁移脚本 `migrate_device_id_unify.py`）
1. 前置：F10 已执行且 `migration_wol_id_map.json` 存在。
2. 重建 `device_group_mappings`（SQLite 不支持改列类型/换 FK）：
   - `CREATE TABLE device_group_mappings_new (id, device_id VARCHAR(100) REFERENCES devices(device_id), group_id ..., added_at ...)`；
   - `INSERT ... SELECT dgm.id, COALESCE(d.device_id, 'ORPHAN-'+dgm.device_id), dgm.group_id, dgm.added_at FROM device_group_mappings dgm LEFT JOIN devices d ON d.id = (SELECT devices_id FROM map WHERE wol_id=dgm.device_id)`；
   - `DROP device_group_mappings; ALTER TABLE device_group_mappings_new RENAME TO device_group_mappings`。
3. 同法重建 `notify_histories` 的 `device_id`。
4. 模型层：`DeviceGroupMapping.device_id` / `NotifyHistory.device_id` 改为 `String(100)` + `ForeignKey("devices.device_id")`；`device_group_routes.py` 入参 `device_id` 改为字符串（前端传 device_id 字符串）。
5. 执行后删除 `wol_devices` 表（F10 遗留，至此 WOL 完全并入）。

### 2.5 回滚预案
- 重建前 `CREATE TABLE ..._old AS SELECT *` 备份原表；回滚 = 改名还原 + 还原模型列类型。
- 物理备份 `score_management.db` 先于一切。
- `map_wol_int_id` JSON 保留至 F5 验证通过。

### 2.6 风险与缓解
- **孤儿键**：wol id 在 `map_wol_int_id` 找不到（wol_devices 已脏数据）→ 写 `'ORPHAN-<int>'` 并记日志，不丢行；回滚后人工处理。
- **前端契约变更**：`device_group_routes` 入参从整数变字符串，前端 `DeviceGroup` 页需同步改传 `device_id` 字符串（执行时一并改）。
- **NotifyHistory 语义未明**：2.3 标注的二次确认点，执行前必须 grep 确认写入来源。

## 3. F9 —— 8 张通知表合并为 `Notification` + `Alert`（P3，结构合并，最大风险）

### 3.1 现状（8 张表，实测 file:line）
| 表 | 行 | 关键列 | 角色 |
|---|---|---|---|
| `Notification` | L271 | user_id, type, title, content, status, phone, sent_at | 用户通知 |
| `AdminNotification` | L1168 | admin_id, title, message, type, priority, is_read, extra_data(JSON) | 管理员通知 |
| `NotifyHistory` | L1212 | text, volume, speak, popup, timeout_sec, urgent, send_mode, device_id(Int), topic, template_id, status, sent_by | 发送历史 |
| `ScheduledNotify` | L895 | text, device_id(Str), scheduled_at, repeat_*, status, last/next_send_at | 定时通知 |
| `NotifyTemplate` | L1184 | name, template, text, category, tags, usage_count, is_active | 模板 |
| `NotifyAudit` | L523 | type, target_class_id, admin_id, payload, reason_code, force_send | 审计 |
| `Alert` | L539 | alert_type, severity, message, device_id(Str), device_name, extra_data, is_read | 系统/设备告警 |
| `DeviceAlert` | L426 | device_id(Str), alert_type, severity, message, is_resolved, resolved_at | 设备告警（Alert 子类） |

### 3.2 目标（报告方案）
- 收敛为 **`Notification`**（统一通知）+ **`Alert`**（统一告警）两张核心表：
  - `Notification` 增加 `recipient_type`('user'|'admin')、`scope`、`channel`、`priority`、`template_id`、`scheduled_task_id`；`NotifyHistory` 并入 `Notification` 的 `status`/`sent_at`/`delivery_*` 列或独立 `notification_deliveries` 窄表；`ScheduledNotify`/`NotifyTemplate` 保留，经外键关联；`NotifyAudit` 合并进统一审计（或 `PermissionLog` 扩展 `target_type='notify'`）。
  - `Alert` 增加 `source`('device'|'system')，`DeviceAlert` 并入（`source='device'`）。

### 3.3 数据迁移映射（核心，需先定 Target Schema）
- 建议**保守路径**（避免一次大合并炸裂）：先合并 `DeviceAlert→Alert`（`source='device'`，字段 1:1 拷贝，`is_resolved`→保留为 Alert 新增列或并入 `extra_data`），其余 7 张表**暂不物理合并**，仅做「逻辑统一」（增加 `recipient_type`/`source` 等区分列 + 文档约定），将 `NotifyHistory`/`ScheduledNotify`/`NotifyTemplate` 通过外键挂到 `Notification`。
- 若坚持物理合并 `Notification`+`AdminNotification`→单表：
  - `AdminNotification` 行 → `Notification` 行，`recipient_type='admin'`、`user_id` 置 NULL、`title`/`message`→`title`/`content`、`priority`→`priority`、`extra_data` 保留、加 `admin_id` 列。
  - 反向 `Notification`(user) → `recipient_type='user'`、`admin_id` 置 NULL。

> **强烈建议分阶段**：阶段 A 仅 `DeviceAlert→Alert`（最小）；阶段 B `AdminNotification→Notification`（加 recipient_type）；阶段 C 通知历史/模板/定时经外键关联（不删表）。每阶段独立脚本+回滚。

### 3.4 执行步骤（分阶段脚本，物理表名以实测为准：无 `__tablename__` 的模型用单数物理名）
- `migrate_f09a_alert_merge.py`：给 `alert`(单数物理名，非 `alerts`) 增加 `source`/`is_resolved`/`resolved_at` 列，拷 `device_alert`(10 行，单数物理名)→`alert`(source='device')，**DROP device_alert**，重指 `devices_routes.py`/`heartbeat_service.py`。
- `migrate_f09b_notification_merge.py`：`notification`(单数物理名，非 `notifications`) 增加 `recipient_type`/`admin_id`/`priority`/`is_read`/`read_at`/`extra_data` 列，`INSERT...SELECT` 自 `admin_notifications`(有 `__tablename__`)，**DROP admin_notifications**，重指 `admin_notifications_routes.py` + 用户通知中心加 `recipient_type='user'` 过滤。
- 外键关联阶段（F9-C）：`scheduled_notifies` 加 `template_id` FK→`notify_templates(id)`；`notify_histories` 加 `notification_id` FK→`notification(id)`（两表为空，FK 安全）。

### 3.5 回滚预案
- 每阶段单事务 + 物理备份；旧表在下一阶段验证通过前不删。
- `Alert`/`Notification` 合并后保留 `source`/`recipient_type`，回滚只需还原路由层读旧表。

### 3.6 风险与缓解
- **最大风险**：8 表相互依赖（NotifyHistory.template_id、ScheduledNotify.device_id、NotifyAudit 引用 class/admin），一次性合并易破坏通知链路。**缓解：分阶段，阶段间可独立回滚**。
- **前端契约**：通知/告警列表页（`Notification*`/`Alert*`/`AdminNotification*`）读取字段变化，需同步改前端类型与组件。
- **审计职责重叠**：`NotifyAudit` 与 `PermissionLog`，合并需确认是否共用审计表。
