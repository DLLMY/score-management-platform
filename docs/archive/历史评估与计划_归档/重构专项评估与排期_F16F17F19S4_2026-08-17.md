## 1. F16 — 模型层拆包（models 模块化）
| 项 | 内容 |
|------|------|
| 当前状态 | 全部 ORM 模型集中在 `backend/models/__init__.py`（约 56 KB，含 Score/User/Alert/ScoreArchive 等数十个类）。本次升级新增的 `ScoreArchive`/`AttendanceArchive` 也已落入此单文件。 |
| 风险 | 中。纯结构重构，不改表结构/语义；但 `from models import X` 的 import 面极广，拆包后需全量替换 import 并防循环依赖。 |
| 影响面 | 后端几乎所有模块（api/、services/、scripts/）的 `from models import ...`；pytest 全量收集。 |
| 建议方法 | ① 新建 `backend/models/` 子模块（`user.py`/`score.py`/`alert.py`/`archive.py` 等），逐个迁移类；② `__init__.py` 改为仅做再导出（`from .score import Score, ScoreArchive`…）以保持 `from models import X` 兼容，**降低爆炸半径**；③ 循环依赖用 `TYPE_CHECKING` + 字符串外键规避。 |
| 验证 | py_compile 全量 + `create_app()` 冒烟 + pytest 定向（models/import） + OpenAPI 0 漂移。 |
| 排期 | **第一批**。预计 0.5–1 天，可随小改逐步拆，不必一次性。 |

## 2. F17 — 路由直连 db 迁移到服务层
| 项 | 内容 |
|------|------|
| 当前状态 | 路由层大量直接操作 `db.session`（实测 `backend/api/` 下约 40 个文件含 `db.session`；全后端口径约 **883 处**直接引用，集中于 api/ 与 services/）。 |
| 风险 | **高**。涉及数据写入路径（成绩录入/扣分/审批/导出），改错即数据不一致或 500。 |
| 影响面 | 成绩、考勤、手机箱开锁、通知、RBAC、运维等全业务写入链路。 |
| 建议方法 | **不主张全量重写**。采用"防腐层"渐进式：① 抽取 `services/*_service.py` 薄封装（已部分存在）；② 路由内 `db.session.add/commit` 改为调用 service 方法；③ 事务边界统一收口到 service；④ 每改一个域（scores→devices→notifications…）即跑对应 pytest + 定向回归。优先改**写入/事务**路径，只读 `db.session.query` 可暂缓。 |
| 验证 | 每域：pytest 定向 + 后端冒烟 + 前端 e2e（成绩录入/开锁/审批）；全量：G1–G8。 |
| 排期 | **第二批**，按域分期（scores → notifications → devices → academics → users）。每域 0.5–1 天，整体 3–5 天。禁止一次性 883 处全改。 |

## 3. F19 — URL kebab-case 统一
| 项 | 内容 |
|------|------|
| 当前状态 | 路由命名风格混用（snake_case 与 kebab-case 并存）。 |
| 风险 | 中–高（**契约变更**）。改 URL 即改前端调用 + OpenAPI 契约 + e2e 脚本，易引发 404 连锁。 |
| 影响面 | 前端 `api.ts` 全部调用点、OpenAPI 快照、e2e spec、第三方集成方。 |
| 建议方法 | **默认不选 / 最低优先级**。收益仅为命名一致，破坏契约成本高。若执行：① 仅新增端点用 kebab，旧端点保留并加 301 兼容重定向；② 前端调用点批量替换 + OpenAPI 重基线；③ 设过渡期双路由共存。 |
| 验证 | OpenAPI strict 0 漂移 + 前端全量 e2e + vitest。 |
| 排期 | **可选，延后**。与 F17 同窗口顺带做只读路径的命名，不单独排期。 |

## 4. S4 — JWT Bearer → Cookie 会话
| 项 | 内容 |
|------|------|
| 当前状态 | 双 JWT 隔离体系已落地（`access` 管理员 + `student` 学生，见 MEMORY）；鉴权在 `utils/permission.py`（21 处 jwt 引用）、`utils/security.py`（27 处）及 `requires_permission`/`requires_student` 装饰器。前端 `api.ts` 在 `Authorization: Bearer` 注入 token。 |
| 风险 | **最高**。认证架构级变更，影响**每一个**受保护端点与前后端握手；CSRF、HttpOnly、SameSite、刷新令牌、移动端/ESP32 调用方全部受影响。 |
| 影响面 | 后端全部守卫 + 前端 `api.ts` token 注入 + 学生端独立路由 + MQTT/工具侧 HTTP 调用（固件下载等无 Cookie 场景需例外）。 |
| 建议方法 | 必须**专项设计**后再动：① 保留 JWT 作为内部服务/设备调用凭证，仅浏览器会话改 Cookie（HttpOnly+SameSite=Lax+CSRF 双 token）；② 登录响应改发 `Set-Cookie` 并保留 `access_token` 字段兼容过渡；③ 新增 `requires_session`（Cookie）与保留 `requires_permission`（Bearer）并行；④ 前端 `api.ts` 改 `credentials: 'include'` 并移除手动 Bearer（保留设备/固件专用头）。 |
| 验证 | 专项集成测试：登录→Cookie 下发→受保护端点访问→刷新→登出失效；CSRF 防护；固件/工具无 Cookie 调用不被破。全量 G1–G8 + e2e 21/21。 |
| 排期 | **最后一批，需单独排期 + 真机/集成测试**。预计 2–3 天设计 + 2–3 天实现 + 1 周观察期。C 盘满且无独立测试环境，强烈建议先在 staging 验证。 |
