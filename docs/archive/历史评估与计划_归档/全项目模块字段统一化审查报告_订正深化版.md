## 1. 后端模型层硬伤（既有报告未覆盖 —— 本次新增重点）

证据均来自 `backend/models/__init__.py`（行号已实测定位）。

### 1.1 通知类冗余表集群（8 张，语义重叠）
| 表 | 行号 | 用途 | 问题 |
|---|---|---|---|
| `Notification` | L272 | 用户通知 | 与 AdminNotification 语义重叠 |
| `AdminNotification` | L1168 | 管理员通知 | 与 Notification 重复设计 |
| `NotifyHistory` | L1213 | 发送历史 | device_id 类型分裂（见 1.2） |
| `ScheduledNotify` | L896 | 定时通知 | 独立表，缺与模板/历史的关联 |
| `NotifyTemplate` | L1185 | 通知模板 | 独立表 |
| `NotifyAudit` | L524 | 通知审计 | 与 PermissionLog 职责重叠 |
| `Alert` | L540 | 告警 | 与 DeviceAlert 重叠 |
| `DeviceAlert` | L427 | 设备告警 | Alert 子类却独立建表 |

**统一方案**：收敛为两张核心表 `Notification`（统一通知，加 `recipient_type`/`scope` 区分用户与管理员、`channel` 字段）、`Alert`（统一告警，加 `source` 区分设备/系统），各自通过 `notify_template_id`、`scheduled_task_id` 关联模板与定时任务；`NotifyHistory` 并入 `Notification` 的 `status`/`sent_at` 列或独立 `notification_delivery` 窄表；`NotifyAudit` 合并进统一审计表。

### 1.2 设备双表 + `device_id` 类型分裂（已实测，跨表 JOIN 必然出错）
| 表.字段 | 行号 | 类型 | 备注 |
|---|---|---|---|
| `Device.device_id` | L388 | `String(100)` unique | 设备业务主键（MAC/序列号） |
| `DeviceAlert.device_id` | L429 | `String(100)` | — |
| `DeviceHeartbeat.device_id` | L440 | `String(100)` | — |
| `Alert.device_id` | L545 | `String(100)` | — |
| `DeviceFirmwareUpdate.device_id` | L573 | `String(100)` | — |
| `WOLDevice.device_id` | L839 | `String(100)` | — |
| **`DeviceGroupMapping.device_id`** | L891 | **`Integer` FK→`wol_devices.id`** | 类型与上面 6 处不一致 |
| **`NotifyHistory.device_id`** | L1226 | **`Integer`** | 类型与上面 6 处不一致 |

**问题**：`Device.device_id` 是字符串业务主键，但 `DeviceGroupMapping`/`NotifyHistory` 用 `Integer` 指向 `wol_devices.id`（另一张整数主键表）。三套"设备"语义（Device / WOLDevice / 字符串 device_id）并存，跨表关联无法一致 JOIN。
**统一方案**：全项目以 `Device` 为唯一设备实体，`device_id` 统一为 `String(100)`（业务主键）；`WOLDevice` 降为 `Device` 的一个 `device_type='wol'` 子类或独立属性表；`DeviceGroupMapping.device_id`、`NotifyHistory.device_id` 改为 `String(100)` 并 `ForeignKey('devices.device_id')`。

### 1.3 RBAC 碎片化（实测比既有报告更碎：含两个映射表）
| 表/字段 | 行号 | 角色表示 |
|---|---|---|
| `Role` | L216 | 角色主表 |
| `Permission` | L681 | 权限主表 |
| `RolePermission` | L490 | 角色-权限映射（1） |
| `RolePermissionMapping` | L696 | 角色-权限映射（2）——**与上面重复** |
| `RoleHierarchy` | L707 | 角色层级 |
| `AdminRole` | L668 | 管理员-角色映射 |
| `PermissionLog` | L512 | 权限操作日志 |
| `User.role` | L135 | 字符串角色（学生侧） |
| `Admin.role` | L306 | 字符串角色（管理员侧） |
| `User-Role` 三套并存 | — | `User.role`(字符串) + `Admin.role`(字符串) + `Role/AdminRole`(关系表) |

**问题**：（a）两套角色映射表 `RolePermission` 与 `RolePermissionMapping` 功能重叠；（b）学生 `User.role` 与管理员 `Admin.role` 各用字符串，与关系表体系割裂。
**统一方案**：保留 `Role`+`Permission`+`RolePermission`（删除 `RolePermissionMapping`，迁移数据）+`AdminRole`+`RoleHierarchy`+`PermissionLog`；`User.role`/`Admin.role` 字符串字段仅作缓存/显示，权威来源为关系表；学生与管理员共用同一套 RBAC 关系表（加 `actor_type` 区分）。

### 1.4 分数三表边界不清
| 表 | 行号 | 语义 |
|---|---|---|
| `Score` | L624 | 考试成绩 |
| `ScoreRecord` | L184 | 行为积分（含 `user_id` L186 与 `student_id` L192 双字段） |
| `CompositeScore` | L1248 | 综合成绩 |

**统一方案**：明确三表职责（考试/行为/综合），不强行合并；但 `ScoreRecord` 内 `student_id` 与 `user_id` 二选一（见对照表 F1），并补充文档说明三者聚合规则。

### 1.5 `admin ↔ class_info` 潜在外键环
- `ClassInfo.head_teacher_id` L457：`db.Column(db.Integer)` **无 ForeignKey**（当前为故意规避 admin↔class_info 循环依赖）。
- **统一方案**：保留无 FK 的现状（规避环），但在应用层通过统一查询接口解析班主任；或在 `Admin` 侧加 `managed_class_ids` 反向关系，避免双向硬 FK。

### 1.6 状态布尔命名不一致
- 主流：`is_active`（启用/禁用）
- 例外：`WarningConfig.enabled`（L1295）——与 `is_active` 同义不同名
- **统一方案**：全项目布尔"启用态"统一为 `is_active`，`enabled` 改名（需数据迁移脚本）。

### 2.1 响应信封风格四分天下

- `APIResponse.success(data=...)`（推荐，统一信封 `{success,code,data}`）

## 5. 结构优化方案（单一数据源原则）

**目标**：每个数据实体仅一处定义，所有模块通过统一接口/关联引用。

1. **模型层单一真相**
   - 所有 ORM 模型集中在 `backend/models/__init__.py`（已是事实），但需消除重复实体：合并 8 张通知表 → 2 张；WOLDevice 并入 Device；删除 RolePermissionMapping。
   - 引入 `models/registry.py` 导出「标准字段名清单」，禁止在模型里新增与清单同义不同名的列。

2. **外键与外键环治理**
   - `device_id` 全项目统一 `String(100)` 业务主键 + FK→devices.device_id，消除 DeviceGroupMapping/NotifyHistory 的 Integer 分裂。
   - `admin ↔ class_info` 维持无硬 FK（应用层解析 `head_teacher_id`），避免循环依赖；反向关系放 Admin 侧。

3. **API 契约统一**
   - 响应 100% 经 `APIResponse.success`；入参分页统一 `per_page`；班级引用统一 `class_info_id`。
   - 路由注册唯一源 `app/api_versioning.py::register_v1_routes`，禁止裸 Blueprint 绕过。

4. **前端单一类型与组件**
   - `frontend/src/types/index.ts` 定义权威类型（与后端字段字典 F1–F13 一一对应）。
   - 新增 `<StatusBadge>`（消费 `is_active`）、`<Pagination>`（消费 `per_page`）、统一 `useUser()` 取 `current_score`；删除 `user.score` 误用。

5. **枚举/选项集中管理**
   - 状态、角色、设备类型等枚举集中在 `src/constants/` 与后端 `models/enums.py`，禁止散落字符串字面量。
