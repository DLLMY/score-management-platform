# 系统整体评估报告（六维度）

> 评估对象：自我管理提升管理平台（Flask-RESTful + SQLAlchemy + SQLite + MQTT/EMQX + Redis 后端；React + Vite + TypeScript 前端）
> 评估日期：2026-08-16
> 评估方法：研读 4 份既有核心评估报告建立基线 → 对高价值残留项做当前代码核查（grep/read） → 以"当前代码真实状态"为结论依据
> 项目规模（实测）：后端 433 .py / 98k LOC；前端 179 .tsx/.ts / 63k LOC；生产库 `instance/score_management.db` ≈ 2.3G

## 1. 功能完整性评估

### 1.1 评估结论
核心业务闭环完整，后端功能实现度 ≈ 95%，前端核心页 ≈ 90%。评分、考试、班级、学生、考勤、请假、通知、OTA/固件、NLP 评分、报表、运维中心等模块均具备可用端点与前端页面。

### 1.2 发现的问题与风险

| 编号 | 问题 | 风险等级 | 状态 |
|---|---|---|---|
| F1 | 成绩/考试导出、导入、撤销闭环已补齐，但**批量导入异常回滚的边界用例仍需专项测试** | 低 | 已修复，待专项测试 |
| F2 | 短信通知为 stub 实现（无真实短信网关），不影响核心闭环但提醒类功能名不副实 | 低 | 已知残留 |
| F16 | `backend/models/__init__.py` 单文件 1348 行，承载全部 ORM 模型，新增模型/迁移成本高、易冲突 | 中 | 残留（待大型重构） |
| F17 | `api/` 下 82 个文件中仍有 34 个直接 `Model.query / db.session` 操作数据库，未走 Service 层 | 中 | 残留（待重构） |
| F19 | URL 命名未完全统一（部分 `/api/xxx`、`/api/v1/xxx` 混用），外部契约一致性依赖人工 | 低 | 残留 |

### 1.3 改进建议
- 将 `models/` 按业务域拆分为子模块（student / score / attendance / device / notification 等），消除 1348 行单文件。
- 逐步将 34 个直连 db 的路由迁移到 Service 层，统一事务与异常处理入口。
- 对短信 stub 明确标注"演示通道"，或接入真实网关后补全回调状态。

## 2. 性能评估

### 2.1 评估结论
常规管理后台负载下响应时间可接受；已引入 Redis 缓存（`RedisCache` + `cached_api` 中间件，统一单套）与权限 TTL 缓存，显著降低重复鉴权开销。主要瓶颈在**超大单库（2.3G）**与**部分未走缓存/索引的高频查询**。

### 2.2 发现的问题与风险

| 编号 | 问题 | 风险等级 |
|---|---|---|
| P1 | 生产库 `score_management.db` 达 2.3G，单库无分表/归档，全量备份与迁移极慢且 C 盘常年 100% 满 | 高 |
| P2 | `scores` 表为复数物理表名，部分历史查询仍走未优化的子查询，缺少复合索引（subject_id + student_id + 时间） | 中 |
| P3 | 全量 pytest 收集 1710 用例，内存峰值约 50h 量级，CI 必须走 `run_regression.sh` 闸门而非全量 | 中（CI 风险） |
| P4 | 通知/预警合并后 `alert` 表承载 4 类 source，未对高频 device 告警做写入削峰 | 低 |

### 2.3 改进建议
- 建立成绩/考勤历史数据**归档表 + 定时迁移**，将热数据维持在百 MB 级。
- 对 `scores(subject_id, student_id, exam_id)` 建复合索引；`alert(source, created_at)` 建分区/索引。
- 引入慢查询日志（PRAGMA + 应用层计时），对 >200ms 端点告警。

## 3. 安全性评估

### 3.1 评估结论
**本维度是修复最彻底的一层**：伪认证、鉴权绕过、班级越权、前端权限残留、OTA 未鉴权下载等历史高危项均已真实落地修复。残留集中在"密钥强度策略"与"固件侧真机验证"。

### 3.2 发现的问题与风险

| 编号 | 问题 | 风险等级 | 状态 |
|---|---|---|---|
| S1 | `validate_secret_keys` 校验 SECRET_KEY 默认值/长度<32/JWT 未设置，**仅打印警告不拒绝启动**（"缺失 env 拒绝启动"未完全落地，仍是弱密钥+警告模式） | 中 | 残留 |
| S2 | 固件侧（phonebox.ino）弱凭据 / TLS `setInsecure` / 断点续传完整性，需真机验证（本机无 ESP32 工具链，无法静态确认） | 中 | 待真机 |
| S3 | 账号枚举 DoS（S6 历史项）：登录失败未做账号级锁定，仅 IP 限流，仍可被分布式试探 | 低 | 残留 |
| S4 | token 存 localStorage（S4 历史项）：已加 401 跳转与权限清理，但未改 httpOnly Cookie，XSS 仍可窃取 | 中 | 部分残留 |
| S5 | CSRF 保护未启用（S5 历史项）：后端无 CSRF token 校验，依赖同源 + Bearer | 低 | 残留 |

### 3.3 已落地确认的安全修复（供审计）
- X-Admin-Id 伪认证移除（get_current_admin 仅 Bearer）✓
- OTA 固件匿名下载改为 realpath 校验 + HMAC 签名来源保证 ✓
- NLP 评分走 atomic + 流水，防越权改分 ✓
- 导出/导入/报表全套班级隔离 ✓
- 登录/密码/设备写/规则写限流启用 ✓
- Excel 公式注入清洗（未覆盖区域 S10）✓

### 3.4 改进建议
- **S1 升级为硬失败**：`validate_secret_keys` 在 production 环境下 SECRET_KEY 为默认值/过短/JWT 缺失时**拒绝启动**（而非仅警告）。
- S4：评估迁移至 httpOnly + SameSite Cookie（短期可加 CSP 收紧）。
- S5：对 state-changing 端点启用 CSRF double-submit token。
- S2：安排真机验证固件 TLS 与凭据强度，补充 OTA 断点续传校验测试。

## 4. 稳定性与可靠性评估

### 4.1 评估结论
异常处理与错误恢复能力较基线显著提升：MQTT 派发逐条 try/except 隔离、入口顶层兜底防收包循环被打死；score 查询加 `PRAGMA busy_timeout` + 重试；成绩插入幂等（flush 后读 id 生成 undo_code）。单点故障风险主要在 Redis 磁盘满告警与 MQTT Broker 依赖。

### 4.2 发现的问题与风险

| 编号 | 问题 | 风险等级 |
|---|---|---|
| R1 | Redis 因 C 盘满报 `MISCONF ... not able to persist on disk`（仅告警不阻断读路径），极端下缓存层不可用退化为直查 DB | 中 |
| R2 | MQTT Broker 为 EMQX 远程托管，断连重连策略依赖客户端，无本地兜底 broker | 中（单点） |
| R3 | Flask-SocketIO 不 reload，改后端须强杀全部 python 重启，部署流程易遗漏 | 低（运维） |
| R4 | `pending` 状态在三处语义不同（审批/成绩/设备），跨模块理解成本高、易误用 | 低（产品决策） |
| R5 | composite 开锁维度方向未统一（产品语义），代码中存在双向兼容分支 | 低（产品决策） |

### 4.3 改进建议
- R1：将 Redis 持久化目录指向非系统盘，或启用 `maxmemory-policy` 自动驱逐 + 磁盘水位监控告警。
- R2：关键控制指令在本端做"最近一次已知好配置"缓存，Broker 不可达时设备侧按本地策略降级。
- R3：引入进程管理（supervisor/systemd）统一重启，避免人工强杀遗漏。
