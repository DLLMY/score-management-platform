## 二、直接修项：成本 / 收益 / 风险

### M1 VirtualList 默认 keyExtractor 用 `Math.random()`

**现状**（`VirtualList.tsx:18-21`）：

```ts
keyExtractor = (item: T) => {
  const itemWithId = item as unknown as { id: string | number };
  return itemWithId.id !== undefined ? itemWithId.id : Math.random().toString(36).slice(2);
},
```

**缺陷**：当 item 无 `id` 字段时，每次渲染都生成全新随机 key → React 认定所有行都是新节点，整段列表卸载重建。后果：滚动位置抖动、行内输入焦点丢失、动画重放、虚拟滚动性能收益被抵消。

**修复**：`keyExtractor` 签名扩展为 `(item: T, index: number)`，无 `id` 时回退到稳定的绝对索引（`startIndex + localIndex`），不再用随机数。现有调用方传入的一元函数在 TS 与运行时均向后兼容（多余入参被忽略）。

- 成本：单文件约 10 行
- 收益：消除无 id 列表的整段重渲染
- 风险：低。key 语义从"随机"变"索引"，纯改善；有 id 的路径行为字节不变

### M2 / M3 事务提交无 rollback 守卫

**现状**：`composite_score_service.py` 与 `approval_service.py` 全文件 `rollback` 出现次数均为 **0**，但存在 6 处 `db.session.commit()`。commit 失败（约束冲突 / 锁超时）时 session 停留在脏状态，后续同请求的 ORM 操作会连锁 `PendingRollbackError`。

**修复**（遵循 F17 既有模式：守卫下沉 service 层，不得仅删除）：

```python
try:
    db.session.commit()
except Exception:
    db.session.rollback()
    raise
```

- 契约影响：**零**。异常继续向上抛，路由层 / 全局 errorhandler 的响应体与状态码逐字节不变
- 成本：6 处包裹
- 风险：低。仅新增失败路径清理，成功路径完全不变

### M4 algorithm_service N+1

**现状**（`algorithm_service.py:226-231`）：

```python
for user in users:
    scores = Score.query.filter_by(student_id=user.id).all()
    avg_score = np.mean([s.score for s in scores if s.score is not None]) if scores else None
```

N 个学生 → N+1 次 SQL。全校量级（千人）时该分析接口线性劣化。

**修复**：改为一次 `GROUP BY student_id` 聚合查询预取平均分字典，循环内查表。

**语义等价性论证**（关键）：
- SQL `AVG` 天然跳过 NULL，与 `[s.score for s in scores if s.score is not None]` 过滤一致
- 无成绩学生 → 聚合结果无该 key → `None`，与原 `if scores: else None` 一致
- 有成绩但全为 NULL → SQL 返回 NULL → `None`；原代码 `np.mean([])` 返回 `nan`。两者最终都被末行 `df.dropna(subset=[...])` 剔除，**输出 DataFrame 逐行等价**

- 成本：单函数约 15 行
- 收益：N+1 → 2 次查询
- 风险：低（等价性已论证，且有 dropna 双重保障）

### M5 api.ts AbortController 覆盖

**现状**（`api.ts:182-184`）：

```ts
export const registerAbortController = (key: string, controller: AbortController): void => {
  abortControllers.set(key, controller);
};
```

同 key 二次注册时旧 controller 被 Map 直接覆盖，**旧请求既不被 abort 也不再被任何引用持有** → 请求继续跑、响应可能回写已卸载组件、`abortAllRequests()` 也漏掉它。

**修复**：注册前若已存在同 key 且未 abort，先 `abort()` 旧实例再 set。

- 成本：3 行
- 收益：消除重复 key 场景的请求泄漏，与 F2（`useOptimizedFetch` 竞态）修复形成闭环
- 风险：低。语义从"静默覆盖"变为"取消旧的再注册新的"，符合调用方本意

## 三、判定关闭项（M6，重要结论）

**原判**：110 处 `request.get_json()` 裸调用缺 KeyError / None 防护，疑似 500 隐患。

**实测复核结论 —— 非缺陷，本轮关闭，不做这 110 处改动**：

1. `backend/app/api_versioning.py:20-33` 已注册全局 `HTTPException` errorhandler：body 缺失 / Content-Type 不匹配时 Flask 抛 `BadRequest(400)`，被统一转成项目信封
   `{"success": false, "message": "请求参数错误，请检查输入内容", "error_code": "BAD_REQUEST"}, 400` —— 符合契约，非 500
2. 裸 `get_json()`（不带 `silent=True`）**不会返回 None**，因此不存在 `None.get()` 的 AttributeError 路径
3. 全仓仅 2 处 `get_json(silent=True)` 未接 `or {}`，均已自带 None 守卫：
   - `phonebox_policy_routes.py:81` → `if isinstance(payload, dict)`
   - `admins_routes.py:372` → `if data and data.get(...)`
4. 另有 27 处已显式写 `or {}` / `silent=True` 组合

**价值**：避免了 110 处零收益改动及其回归风险。

### M7 today_count 统计未套班级隔离 —— 数据可见范围问题【已按方案 A 实施 ✅】

**位置**：`backend/services/score_record_service.py:316-322`

```python
today = datetime.now().date()
today_records = ScoreRecord.query.filter(          # ← 全新 query，未继承上方隔离
    ScoreRecord.created_at >= datetime.combine(today, datetime.min.time())
)
if user_id:
    today_records = today_records.filter(ScoreRecord.student_id == user_id)
today_count = today_records.count()
```

同函数上方的 `total_records / total_add / total_subtract` 都经过 `_apply_isolation_filter(query, allowed_classes)`，**唯独 `today_count` 另起 query 绕过了隔离**，也未套 `class_name` 过滤。

**后果**：班主任查看本班积分统计时，`today_count` 显示的是**全校今日记录数**，其余四个指标是本班数 → 口径不一致，且构成跨班数据量的间接泄露。

**为何需要你拍板**：修复会**改变返回值**（班主任看到的 `today_count` 会变小）。这属于数据可见范围 / 业务口径变更，按铁律③须你确认。

请择一：

- **方案 A（推荐）**：`today_count` 与其余四指标口径对齐 —— 套用相同的 `class_name` 过滤 + `_apply_isolation_filter`。语义统一，但班主任端数值会下降
- **方案 B**：保持现状不动，仅在前端把该指标文案改为"全校今日记录数"，明确口径差异
- **方案 C**：保留全校口径并**另加**一个"本班今日"指标，两者并列展示（需前端配合改动）

**✅ 实施结果（方案 A）**：`get_score_statistics` 中 `today_count` 改为镜像主查询口径——`user_id` 分支按 `student_id` 过滤，`class_name` 分支 `join(User).filter(User.class_name == class_name)`，两者均再经 `_apply_isolation_filter` 套隔离；同步更新函数 docstring 注明口径统一。注意 `_apply_isolation_filter` 用 `EXISTS` 子查询（非 JOIN），与 `join(User)` 不冲突，规避 SQLite 重复 JOIN 歧义。班主任端 `today_count` 现与其余四指标同口径（数值下降属预期）。

### M8 权限缓存 TTL 硬编码 30 秒

**位置**：`backend/utils/permission.py:286-287`

```python
_PERM_CACHE: dict = {}
_PERM_CACHE_TTL = 30
```

**问题**：TTL 硬编码在模块内，不可按环境调整。语义后果是**角色/权限变更后最长 30 秒才生效**（缓存未命中前旧权限仍可用）。

**为何需要你拍板**：TTL 属权限体系配置，改动直接影响"权限变更生效延迟"这一安全语义，按铁律②③须你确认。

请择一：

- **方案 A（推荐）**：TTL 提为环境变量 `PERMISSION_CACHE_TTL`，默认仍 30（**行为零变化**，仅获得可调能力）
- **方案 B**：方案 A + 在 RBAC 写操作（授权/撤权/改角色）后主动清除该用户缓存 → 权限变更即时生效，但需改动 `rbac_routes` 多个写路径（F17 敏感域，34 处已收口，改动面较大）
- **方案 C**：不动

**✅ 实施结果（方案 A）**：`backend/utils/permission.py` 顶部新增 `import os`；TTL 改为 `int(os.getenv("PERMISSION_CACHE_TTL", "30"))` 并带 `TypeError/ValueError` 兜底（非法值回退 30）。**默认行为零变化**（仍 30s），仅获得按环境可调能力，未触碰 RBAC 写路径（方案 B 未采用）。
