## 系统评估优化（第十八轮 / R18）：并发安全 / 竞态条件审计

### 审计方向
写入侧 lost update（读-改-写竞态）：重点是**用户积分/计数的原子性**——竞态不仅会算错分，更会**绕过业务上限规则**（属安全相关）。

### 全景结论
项目存在**两种积分写入范式并存**：
- ✅ 原子：`services/user_service.py::bulk_score_update` 用 SQL 表达式 `User.current_score + score_change`（`rowcount` 取受影响行数）。
- ❌ 读-改-写：`user.current_score -= / += / = max(0, ...)` 在 Python 内算完再 flush，共 4 处（`unlock_validator` / `device_service` / `reward_service` ×2 / `mqtt_message_service`）。

### 真实缺陷（已修：`services/unlock_validator.py::record_unlock`）
- **lost update**：分数 + `today_unlock_count` + `weekly_unlock_count` + `updated_at` 四个字段在 Python 内算完整体 flush。并发开箱（同一学生，**MQTT 重连/重复上报时常见**）会互相覆盖 → **漏扣分 + 计数丢失**。
- **计数丢失可绕过业务规则**（危害升级点）：`today_unlock_count`/`weekly_unlock_count` 直接决定每日/每周开锁上限（`_check_daily_limit`/`_check_weekly_limit`）。计数丢失 = 上限被绕过，属**安全相关缺陷**（非仅数据不准）。
- 修复：改为**单条 UPDATE 原子表达式**（与 `bulk_score_update` 同范式，不自造标准）：
  - `current_score = func.max(0, func.coalesce(current_score,0) - UNLOCK_COST)` —— 在 SQL 内保住「不为负」下限，语义与原 `max(0, ...)` 完全一致；
  - 日/周计数 `func.coalesce(cnt,0) + 1` 在 SQL 内自增；
  - 跨日/跨周重置改为**条件 UPDATE 清零**（`synchronize_session=False`），避免覆盖并发增量；
  - 补 `db.session.refresh(user)`：调用方 `mqtt_message_service._deduct_and_unlock` 紧随其后就要读 `user.current_score` 下发结果，**不刷新会下发陈旧分数**（原实现亦有此问题）。

## 系统评估优化（第二十三轮 / R23）：请求参数类型转换陷阱

### 审计方向
Python/Flask 中 request 参数的类型陷阱 —— 字符串被当布尔/当数值使用，导致筛选静默失效。

### 真实缺陷（已修 3 处）
- **① 字符串直传 Boolean 列 → 恒空集（功能失效）**：`services/culture_service.py::list_records:21` 与 `services/study_group_service.py::list_groups:13` 均 `filter_by(is_active=is_active)`，而 `is_active` 来自 `request.args.get("is_active")`（**原始字符串**）。
