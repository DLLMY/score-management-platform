## ✅ 修复 analyzer 单例测试污染（#929）

### 现象
`tests/test_nlp_analyzer_service.py::TestNLPAlgorithmAnalyzer::{test_record_intent_prediction, test_record_performance}`
跟在 `test_nlp_routes.py` **之后**运行必然失败（`assert 4 == 3`），单独跑该文件则 29 passed。
完整 NLP 套件的基线因此长期挂着 2 failed。

### 根因
`services/nlp_analyzer_service.py` 的 `NLPAlgorithmAnalyzer` 用 **`__new__` 实现进程级单例**（L105-111，`cls._instance` 缓存 + `_initialized` 守卫）：

```python
def __new__(cls):
    if cls._instance is None:
        with cls._lock:
            if cls._instance is None:
                cls._instance = super().__new__(cls)
                cls._instance._initialized = False
    return cls._instance
```

测试里 `NLPAlgorithmAnalyzer()` 拿到的**永远是同一个实例**。断言形如「新建 analyzer → 记录 3 条 → 计数 == 3」，
但 `test_nlp_routes.py` 的 train-all 异步流程已向该单例写入过 1 条 → 读到 4。

### 定性：测试隔离问题，**非生产缺陷**
单例指标收集器是**合理设计**（全局指标聚合）；`IntentMetrics` / `PerformanceMetrics` 也是正确的
dataclass（可变默认用 `field(default_factory=...)`，实例间不共享）。因此**不改生产代码**。

### 修法
在 `tests/test_nlp_analyzer_service.py` 加 autouse fixture，每个用例前后调用**既有**的
`reset_metrics()`（L391，覆盖 intent / performance / error / request_history / component_stats 全部指标）复位单例：

```python
@pytest.fixture(autouse=True)
def _reset_analyzer_singleton():
    from services.nlp_analyzer_service import NLPAlgorithmAnalyzer
    NLPAlgorithmAnalyzer().reset_metrics()
    yield
    NLPAlgorithmAnalyzer().reset_metrics()
```

顺带补上该文件此前缺失的模块级 `import pytest`（原文件顶部全是 try/except 局部导入）。
作用域刻意限定在**该文件**而非 conftest：全仓仅此一个测试文件引用该服务，
放 conftest 会让数千用例平白承担导入与复位开销。

### 验证

|---|---|---|
| `test_nlp_routes.py` + analyzer | 2 failed / 46 passed | **48 passed** |
| analyzer 单独 | 29 passed | 29 passed（无退化） |
| 完整 NLP 套件（13 文件） | 224 passed / 1 skipped / **2 failed** | **226 passed / 1 skipped / 0 failed** ✅ |

### 踩坑
- 一次验证跑出**空日志（0 字节）**：疑似沙箱 torch 段错误（记忆已有记载：「验证时主线程先

## ✅ FastNLPParser 复句拆分（#930，用户选定方案 3）

### 缺陷回顾
「张三迟到扣2分，李四积极回答加3分」在快路径被解析成 `add / 张三 / 2.0`：
姓名按**文本位置**取最靠前者，意图按 `_quick_intent_keywords` **字典序**取首个命中
（add 组先于 deduct），于是「前半句姓名 + 后半句意图」错配 —— **加减方向相反**、
李四被静默丢弃；而 confidence=1.0 满足 `nlp_service.py:174` 的 `>= 0.6` 门槛，
完整解析器根本不参与，全程无失败信号。

### 实现（`services/nlp_fast_parser.py`）
- 新增 `_CLAUSE_SPLIT_PATTERN = re.compile(r"[，,；;。！？!?]")` 与 `_split_clauses()`
  —— **刻意不含「、」**：枚举顿号是"共享谓语"结构（「张三、李四迟到扣2分」），
  拆开会让前半句失去谓语而解析失败。
- 原 `parse()` 主体抽为 `_parse_single(text)`（单子句解析）。
- `parse()` 改为：切分 → **逐子句独立解析** → 顶层取首个子句 + 新增
  `results` / `is_compound` / `clause_count`。

**兼容性设计**：单句路径（1 个子句）除多出 3 个新键外**行为不变**；
新增键对既有消费方只增不减。已验证 `json.dumps` 往返一致
（Redis 缓存 `ttl=300` 序列化路径安全，缓存按引用存储也无害）。

## 🔍 复句严重性定级：结论「快路径不可达；活跃链路在本沙箱无法定级」

按上轮建议，在有规则种子的环境下实测**活跃链路**（增强解析器）的复句行为，共三轮探针（均用完即删）：

| 探针 | 环境 | 结果 |
|---|---|---|
| 1 | 裸测试库 | 复句与单句均 `success=False` / `matched_rules=[]` → 基线不成立 |
| 2 | 种子 `NLPScoringRule` | 仍 `matched_rules=[]` → 规则未被解析器加载（单例内存缓存） |
| 3 | 用户 + 规则 + 强制 `_refresh_cache()`（`cache_time=0`） | 用户已入缓存（`['张三','李四']`），但 **`matched_rules` 仍为空** |

### 根因（环境限制，非产品结论）
`deep_semantic_match`（L2170-2189）综合分 =
`0.2*TFIDF + 0.2*BM25 + 0.3*BERT + 0.3*keyword`，门槛 **`score > 0.15`**。
沙箱中 BERT/TFIDF 信号缺失，仅 keyword 项有值（0.3 × ~0.5 ≈ 0.15，**不 > 0.15**）
→ 规则被全部过滤 → `matched_rules=[]` → `score_change=None` → `success=False`。
**单句同样如此**，故无法区分「解析器主动拒绝复句」与「环境导致全部失败」。

🔄 **更正（同日 #931 实证推翻本段结论）**：上面「沙箱缺 BERT 信号」的解释**不成立**。
#931 接入真实 BERT 后，`weighting_formula` 用例得分由 0.35 变为 **0.65**（+0.3 正是 BERT 贡献），
证明**本测试环境真实 BERT 可用且能正常产出向量**。当时探针 `matched_rules=[]` 的真正原因
是规则没进解析器的 `rules_by_intent` 缓存（或 parse 流程根本没走到 `deep_semantic_match`），
**不是** BERT / TFIDF 缺失。教训：结论要由**受控对照实验**支撑，
本次是把「单句也失败」当作环境证据，却没验证失败究竟发生在哪一层。

### 定论
- **快路径（#930 修复处）不可达**：路由层 `_get_parser()` → `nlp_enhanced_service.get_nlp_parser()`；
  `nlp_service.py` 仅预热、无路由调用 → 复句错分属**潜伏态**，线上不可触发。
- 活跃解析器的复句行为**在本沙箱无法定级**，需在有完整 BERT/TFIDF 的真机环境复现。
- 复句能力**真正的瓶颈在执行侧**：`execute_scoring` 只消费单个 `extracted_name`，
  即便解析器给出多人名也只落一条记录。
- **判断：暂不投入「多人名抽取 + 多条记录执行」**（不可达 + 未定级 + 涉及评分写入事务）。

### 🎁 意外但更有价值的发现：活跃链路真实解析路径**端到端零测试覆盖**
- `test_nlp_enhanced_service.py` 中唯一断言 `success is True` 的用例（L411-422）
  是**预置 `_parse_cache` 的缓存命中桩**，完全不走真实解析。
- 全套件**无一处断言 `matched_rules`**。
- `test_nlp_execute_service.py` 的 `execute_scoring` 用例全部使用 `_make_parser(parse_result)` **桩解析器**。

→ 真实「解析 → 匹配规则 → 出分」链路**一个端到端用例都没有**。这比复句问题更值得补。
⚠️ 但补它同样受上述环境限制（沙箱无 BERT/TFIDF → 匹配恒空），建议**在真机环境**验证，
或先为 `deep_semantic_match` 的各分量（TFIDF/BM25/BERT/keyword）写可注入的单测以绕开环境依赖。

## ✅ 匹配层单测（用户选定「补匹配层单测」）

| 用例 | 固化的契约 |

| `..._no_rules_returns_empty` | 该意图无规则 → 直接 `[]`，不做计算 |
| `..._weighting_formula` | 权重配比 `0.2*TFIDF + 0.2*BM25 + 0.3*BERT + 0.3*keyword`（实测 0.35） |

## ✅ #931 为 deep_semantic_match 接入真实 BERT 相似度（用户决策：功能增强）

### 改动（`services/nlp_enhanced_service.py`）
原 `bert_similarities = np.zeros(len(rules))`（0.3 权重恒为 0、综合分上限实为 0.7）
→ 改为 `self._compute_bert_similarities(text, rule_texts)`。

新增 4 个方法：
- `_get_bert_service_safe()` —— 延迟 import + **函数内取单例**（`services.bert_service.get_bert_service`），
  不可用 / 未初始化 / 异常一律返回 None，**绝不抛出**；函数内取单例也便于测试注入替身。
- `_bert_rule_vectors()` —— **按规则文本签名缓存**规则向量（规则变更少，避免每次请求都过 BERT）
- `_bert_query_vector()` —— 查询向量按文本缓存，容量 512，超限整体清空
- `_compute_bert_similarities()` —— 余弦相似度，含降级与归一

### 关键设计：候选内相对归一（而非绝对余弦）
余弦先 `max(cos, 0)`，再**除以候选集合内的最大值** —— 与同一函数里 BM25 的
`s / max_bm25` 处理保持一致。原因：中文句向量的**绝对余弦普遍偏高（0.5~0.7）**，
若直接用绝对值，0.3 权重会给**每条**规则加约 0.18，几乎所有规则都被推过 0.15 门槛、
完全丧失区分度。相对归一让 BERT 表达"候选之间的相对语义贴近度"。

### 降级安全
BERT 不可用 / 向量缺失 / 形状不符 / 范数为 0 → 一律返回全 0 数组，
与接入前 `np.zeros` 行为**完全一致**，不引入任何新失败模式。

### 测试
⚠️ **重要发现：本测试环境里真实 BERT 是可用的**。接入后首次运行，
`weighting_formula` 由 0.35 变 **0.65**（+0.3 正是 BERT 贡献）——
这既是集成生效的实证，也暴露了原隔离测试不够封闭。

处理：`_stub_components` 增加 `bert_service=None` 参数，**默认关闭 BERT 分量**，
使权重 / 门槛类断言保持单变量隔离；需要验证 BERT 时显式传替身（`_FakeBertService`）。

| 用例 | 验证点 |
|---|---|
| `..._bert_unavailable_falls_back_to_zero` | BERT 不可用 → 归零，与接入前降级行为一致 |
| `..._bert_rescues_lexically_unrelated_rule` | **核心价值**：「上课打瞌睡」↔ 规则「睡觉」字面零重合，接入前综合分恒 0 必漏匹配；接入后 0.3 命中 |
| `..._bert_normalizes_within_candidates` | 候选内相对归一（1.0 / 0.6） |
| `test_bert_rule_vectors_cached_by_signature` | 规则未变时不重复过 BERT（性能护栏） |

ⓘ 踩坑：归一比例**不能取 0.5** —— `0.3*0.5 = 0.15` 恰好等于门槛，
会被「严格大于 0.15」判排除，导致断言 KeyError。改用 0.6（0.18）越过门槛。

### 回归
`test_nlp_enhanced_service.py` 全文件 **46 passed**（37 原有 + 9 新增）；完整 NLP 套件待通报。

### 待观察（未擅自调整）
综合分上限由 0.7 恢复到名义 1.0，匹配会**更宽松**。0.15 硬门槛是经验值，
真实数据上的误匹配率需在真机观察后再决定是否微调 —— **本次未改动门槛**。
