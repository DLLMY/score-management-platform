## CI vitest fork worker OOM 修复（优化收口）

- **现象**：GitHub Actions `ubuntu-latest` 跑 `npm test`（`vitest run`，默认 forks 池）全量 270 用例时，某 fork worker 撞 V8 旧生代堆上限（runner 上默认≈2GB）崩溃 → `FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory` → exit 1（35 文件 261 passed / 1 error）。
- **根因**：`frontend/vitest.config.ts` 设 `pool: process.env.CI ? 'forks' : 'threads'`；forks 池每个 worker 是独立 Node 进程，受 V8 默认堆上限约束；全量并发加载 antd/recharts 等重依赖时单 worker 易溢出（与本地沙箱 OOM 同源）。
- **修复**（`.github/workflows/ci.yml` 的 `frontend` job 加 job 级 `env`，双保险）：
  1. `NODE_OPTIONS: --max-old-space-size=4096` —— 抬高单 worker 堆上限（不影响测试逻辑/结果）。
  2. `VITEST_MAX_WORKERS: 2` —— 限制并发 worker 数，避免多核 runner 上堆峰值叠加打爆容器（vitest 原生支持，`coverage.*.js:380` 直接读 `process.env.VITEST_MAX_WORKERS`）。
- **校验**：ci.yml 结构回读无误（env 与 name/runs-on/steps 同缩进层级，job 级生效）；vitest 源码确认 `VITEST_MAX_WORKERS` 与 `config.maxWorkers` 受支持（无配置项名风险，优于改 `poolOptions`）。

- **触发**：M11 全量 vitest 收口时核对日志，发现两件事：① 我上一轮汇报的"vitest exit 0 / 0 failure"是**误读**——`/tmp/frontend_vitest.log` 里既无 `VITEST_EXIT` 行、又含 3 处 OOM 标记与 `Errors 1 error`；② `Test Files 36 passed | 1 skipped (38)` 只覆盖 37/38，**有 1 个文件结果丢失**。
- **定位手法（可复用）**：`sed 's/\x1b\[[0-9;]*m//g'` 剥 ANSI 后 grep `(✓|↓|×|❯) src/...test.tsx` 得"已报告文件集"，与 `find src -name '*.test.*'` 的磁盘集做 `comm -13` 差集 → 唯一缺失者即崩溃 worker 正在跑的文件。**forks 与 threads 两种 pool 下差集都指向同一个文件** `src/tests/components/PermissionGuard.test.tsx`。
- **真根因**：该文件用例『empty permissions + not logged in redirects』只套 `BrowserRouter`、**无 `<Routes>`**；`PermissionGuard` 返回 `<Navigate to='/login' state={{ from: location }} replace />` 跳转后 guard 不卸载 → 反复 `Navigate` 无限跳转，每轮 `state.from` 嵌套上一个 location，`history.replaceState` 需结构化克隆的对象链持续加深 → 堆内存级数增长直至 worker 崩溃。**forks 表现为 4GB OOM，threads 表现为 `Worker exited unexpectedly`（无 OOM 字样）——同一 bug 两种外观**。生产环境 `/login` 有独立路由会卸载 guard，故非产品缺陷，属测试装配缺陷。
- **实证链**：`-t "___nomatch___"`（跳过全部用例）→ 3.17s exit 0，证明导入/收集阶段无问题；逐用例 `-t` 二分 → 仅该用例 `exit=1 oom=1`，其余 9 个各自 1 passed。单跑该文件限堆 640MB → **66s OOM**（`tests 0ms`，无堆上限时吞内存连 shell 一起拖死）。
- **修复（纯测试装配，不动产品代码/字段/权限/契约）**：该用例改用 `MemoryRouter initialEntries={['/secret']}` + `<Routes>`（`/secret` 挂 guard、`/login` 挂 `<div>登录页</div>`），guard 跳转后正常卸载；顺带把断言升级为**真正校验跳转目标** `getByText('登录页')`（原实现无 Routes 时无法验证跳到哪）。修复后：**10 passed / 129ms / 68MB 堆**（640MB 小堆下亦通过）。
- **ci.yml 注释更正**：`.github/workflows/ci.yml` frontend-test 那段"单 worker 文件数决定重模块总量"的根因注释已被证伪，改写为真根因说明；分片 4 份 + `VITEST_MAX_WORKERS=1` + heap 5120 **保留为纵深防御（明确标注非根因修复）**。YAML 已 `yaml.safe_load` 校验 OK。
- **⚠️ 方法论教训（务必遵守）**：`grep FAIL` / 看 `passed` 数**不足以判定单测闸门通过**。必须同时核对三项：① 日志里的**退出码行确实存在且为 0**；② `Errors 0 error`；③ **报告文件数 == 磁盘文件数**（差集为空）。否则崩溃 worker 的文件会静默从统计中消失，造成"全绿"假象。
- **⚠️ 本地全量单测勿加 `--pool=forks`**：`vitest.config.ts` 已按 `process.env.CI ? 'forks' : 'threads'` 自动选池，`npm test` = `vitest run` 即正确；强制 forks 会放大内存问题且在 Windows+中文路径下 worker 启动慢（本次全量 forks 跑 >11min，threads 约 7m51s）。定向跑少量文件时加 `--pool=forks` 无碍。
- 补充事实：`vitest 4.1.11` **确实支持** `VITEST_MAX_WORKERS` 环境变量（已在 `node_modules/vitest/dist` 内 grep 证实，是唯一的 `VITEST_(MAX|MIN)_*` 变量）；测试文件总数 38 = 32 个 `.test.ts(x)` + 6 个遗留 `.test.js(x)`（config `include: src/**/*.test.{js,jsx,ts,tsx}`）。
