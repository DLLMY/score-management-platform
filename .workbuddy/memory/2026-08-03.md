- `frontend/src/services/api.ts` 的 `request()`（executeRequest:681-690）在收到 `{success,code,data:{...}}` 时**解包为 `rawData.data`**。后端 `users_routes.py` 返回 `APIResponse.success(data={"user":{...}})`，**所以 `api.users.update()` 实际返回 `{user:{...}}`（还包一层单数键），不是扁平 User**。
- `UserList.tsx:543` 的 `handleSubmit` 把返回值直接 `dispatch({type:'UPDATE_USER', payload: updated})`，而 reducer 用 `action.payload.id` 匹配列表 → `{user:{...}}.id` 为 undefined → 列表永远刷不到新数据。新增（:549）同样问题。

## 系统性审计（Explore 子代理，very thorough）
审计全部 `frontend/src/pages/*.tsx` 的 `api.X.update/create/delete` 调用，交叉核对后端 `APIResponse.success(data=...)` 返回结构与前端消费方式。结论：绝大多数页面（约 20+）操作后**重新拉取列表**（安全）；少数页面直接用返回值更新 state 且后端返回值被解包成 `null`/`{singular}`/`{id键}`，存在与 UserList 同类 bug。

## 跨会话复用要点
- **`request()` 解包语义**：成功响应返回 `rawData.data`（即后端 `APIResponse.success(data=X)` 的 X）。若后端 `data={singular:{...}}`，前端拿到的是 `{singular:{...}}`，**不能直接当扁平实体用 `.id`**；若后端只返回 `message`（无 data），解包得到 `null`。
- 前端写操作后**最稳妥是重新拉取列表**（参照 20+ 正常页面），避免依赖返回值结构的隐性契约。
- 排查"修改没生效但报成功"类问题：先看 reducer 是否用 `action.payload.id` 匹配，再看 API 返回值是否被正确解包。
