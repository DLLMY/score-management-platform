## 设备离线的根因与修复（已落工作区，未提交）
1. **celery 5.6.3 + billiard 4.2.4（Windows spawn）的 fast_trace_task bug**：
   `setup_worker_optimizations` 把模块级 `_localized` 置空，但 `use_fast_trace_task=True`，
   导致 `fast_trace_task` 在 `tasks, accept, hostname = _loc` 抛
   `ValueError: not enough values to unpack (expected 3, got 0)`，每个 `process_phonebox_telemetry`
   任务在进业务函数体之前就崩，心跳无法落库。
   - 修复：`celery_app.py` 增加 `worker_process_init` 信号，强制
     `celery_app.use_fast_trace_task = False`，回退到不依赖 `_localized` 的 `trace_task_ret`。
2. **Celery worker 与后端共用 MQTT client_id 撞车**（上一轮已修，`service_init.py` 的
   `_IS_CELERY_WORKER` 守卫，worker 跳过 `init_mqtt`/`init_scheduler`）。
3. **无 Redis 时 `.delay()` 长重试阻塞**：`celery_config.py` 增加 `broker_connection_max_retries=0`
   + `broker_connection_timeout=2`，让 broker 不可达时快速失败、触发既有同步兜底 `_process_telemetry_fallback`。

## 最终根因与修复（2026-10-04 深夜，已实测闭环）
- **压轴根因**：前述 fast_trace_task / client_id / Redis 修复只解决「worker 能否执行任务」，
  但仍有一道**按设备维度的静默丢弃**——`pbB8F8626222D0` 固件心跳 payload **不含 `timestamp` 字段**。
  `mqtt_message_service.handle_heartbeat_message` 构造 `DeviceHeartbeat` 时
  `timestamp = data.get("timestamp")` → None，而 `device_heartbeat.timestamp` 为 `Integer NOT NULL`
  → `sqlite3.IntegrityError: NOT NULL constraint failed: device_heartbeat.timestamp`，
  整条心跳事务回滚 → `device_heartbeat` 行数恒为 0、`Device.last_heartbeat` 永不刷新、前端永远离线。
  `phonebox_001` 固件带 `timestamp` 故一直正常（此前一度误判为「设备级丢弃」）。
  实证：worker 日志 7798 行 `[MQTT Task] 心跳处理失败: NOT NULL constraint failed: device_heartbeat.timestamp`；
  独立 paho 抓包确认 pbB8 心跳字段集为
  `[box_a_status, box_b_status, device_id, device_type, error_count, fw_version, last_error, platform, status, system_state, uptime, wifi_signal]`（无 timestamp）。
- **修复**：`services/heartbeat_service.py` 新增共享助手 `extract_heartbeat_timestamp(data)`
  （缺/空/非整数 `timestamp` 时回退为服务端 Unix 秒级时间戳），两处构造 `DeviceHeartbeat` 统一改用：
